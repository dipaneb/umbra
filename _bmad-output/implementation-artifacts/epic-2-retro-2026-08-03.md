## What Went Well

- **Verification rigor became a standing discipline, not a one-off.** Every new Rust dependency across the epic (`base64`, `uuid`, `sha2`/`sha1`/`md-5`) was checked directly against the crates.io registry API and Context7 docs before use, not trusted from memory or training data. This caught a real, concrete bug before it shipped: the `md-5` crate's three-way naming mismatch (registry name `md-5`, and critically its own `[lib] name = "md5"` making the import `md5` with no dash) was found by an actual failing `cargo build`, not documentation alone.
- **Spec-reading caught a correctness gap neither planning doc mentioned.** Story 2.6 (JWT) surfaced that RFC 7519's `NumericDate` permits non-integer (float) values — a naive `as_i64()`-only claim extractor would have silently dropped `exp`/`iat`/`nbf` for a subset of real-world tokens, quietly defeating FR17's expiry flag. This was found by reading the RFC directly during story drafting, before any code was written.
- **Test fixtures were computed, not remembered.** Story 2.4's SHA-256/512/MD5/SHA-1 expected digests were generated via Python's `hashlib` in-session rather than transcribed from memory, avoiding a class of bug where a hardcoded-but-wrong fixture silently passes.
- **A wrong-library trap was explicitly avoided.** Story 2.6 considered and explicitly rejected the `jsonwebtoken` crate for JWT decoding — it exists primarily to *verify* signatures, which FR18 excludes from v1 scope. Pulling it in for decode-only use would have added unused attack surface and an unnecessary dependency-license review for zero functional gain over ~30 lines of hand-written decode logic.
- **Shared infrastructure kept compounding cleanly.** Tool Registry (AD-5), `ToolError`/`Position` contract (AD-3), `spawn_blocking` dispatch, and `fs_helper.rs` (introduced in 2.2, reused verbatim by 2.5) all extended without rework across five new tools.
- **Manual verification, while deferred throughout development, was confirmed complete for the whole epic during this retrospective** — Epic 2 is genuinely done-done, not just CI-green.

## Challenges

- **The async stale-state race bug — Epic 1's #1 flagged review theme — recurred twice in Epic 2, despite a committed action item to prevent it.** Epic 1's retrospective (2026-07-29) named this as the single most repeated review-feedback pattern of that epic and committed action item #4, "add a 'gate the write, not just the read' check to the dev/review checklist" (owner: Amelia). It stayed open through Epic 2, and the same bug shape hit twice more:
  - **Story 2.3 (UUID):** a version-switch race — `runLatestWins`'s supersede check keyed off a new `onGenerate()` call, not off the `version` radio changing, so a stale v4 response could repopulate a v7-labeled result list after the user switched versions mid-flight.
  - **Story 2.5 (Hash files):** two instances found in one review pass — `DropZone.vue` shared *one global* `runLatestWins` instance across every tool (a drop on Tool B could falsely supersede an in-flight drop on Tool A), and `HashView.vue` ran a second, fully uncoordinated local runner for manual Compute/Paste, meaning a manual compute and a file drop writing to the same state had no ordering guarantee between them at all.
  - **What actually closed the gap** was not the checklist item — it was a genuine architectural fix in Story 2.5's review: `registry.getLatestWinsRunner(toolId)`, one shared per-tool runner used by both the drop dispatcher and the tool's own view. The process-level action item never got enforced in practice; the code-level fix is what worked.
- **Manual verification was deferred on every single story during development**, seven stories running (1.10 through 2.6) — a structural limitation (the dev agent cannot drive a native Tauri/WKWebView window), not a discipline lapse, but it meant the whole epic ran on automated-test-plus-code-review confidence alone until this retrospective's check-in confirmed it was actually done.
- **Shared shell infrastructure needed real rework mid-epic, not just extension.** `registry.dropResult`'s `value` field was hardcoded to `string` in Story 2.2 (built for Base64's string-returning handler) and had to be widened to `unknown` in Story 2.5 when Hash's handler needed to return a structured object — a ripple that touched `Base64View.vue` even though that story wasn't the one being changed.

## Epic 3 Preview: "Natural language ↔ cron"

3 stories, FR19–FR22, not yet started (all `backlog`).

**What Epic 2 hands to Epic 3, confirmed working:**
- Tool Registry, `ToolError`/`Position` contract, `spawn_blocking` dispatch — proven across 5 tools now, no prep needed.
- The `registry.getLatestWinsRunner(toolId)` pattern (Action Item #1) is available if Epic 3 ever needs multi-trigger write coordination — not expected, since this epic has no drop/file handling.

**Structurally different from Epic 2:**
- No file I/O, no drop handling, no JSON-shaped IPC struct work — Epic 3 is a deterministic natural-language grammar parser (`croner` for cron parsing/next-occurrence, per AD-1) plus round-trip validation (AD-9) and a CI-enforced phrase-corpus acceptance gate (Story 3.3), closer in shape to Story 1.4's CI-gate work than to any Epic 2 story.
- Higher honesty stakes: FR21 explicitly treats wrong-but-confident cron output as a bug, not a limitation — silently approximating an inexpressible phrase (e.g. "every third Friday of the month") is the exact failure mode the corpus gate exists to catch in CI, not just in review.
- Build order is dependency-driven: Story 3.1 (cron→English) must land solid before Story 3.2 (English→cron) can round-trip through it per AD-9.

**No epic-update-required situation.** Confirmed clear to start Story 3.1 directly — no shared-infrastructure gaps analogous to Epic 2's window-drop-service/file-save-helper bootstrapping exist for Epic 3.

## Closing Notes

Epic 2 delivered its full scope (FR10–FR18) in 5 days with zero production incidents and a verification discipline that caught real bugs — a dependency-naming mismatch, an RFC edge case, a wrong-library trap — before they ever reached code. The epic's one real lesson is about *closing the loop* on retrospective commitments: Epic 1's checklist-based fix for async races was never actually enforced and the bug came back twice, while the in-review architectural fix (a shared per-tool latest-wins runner) is what actually worked. Going into Epic 3, the standing rule is to prefer structural fixes over process reminders wherever the codebase can enforce the invariant directly.
