# Story 2.2: Turn files into Base64 and back

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want to encode a dropped file to Base64 and decode Base64 back into a saved file,
so that I can produce data URIs and unpack binary API payloads locally.

## Acceptance Criteria

1. **Given** the Base64 tool is active, **when** I drop a file onto the window, **then** the shell's window-level drop service — established by this story — dispatches the file _path_ to the tool's registry-declared drop handler (AD-14), **and** `src-tauri` reads the file and returns its Base64 encoding; raw bytes never ride the JSON IPC bridge above ~64 KB (FR11, AD-15).
2. **Given** valid Base64 content in the tool, **when** I choose "decode to file", **then** the shared save-dialog-plus-write helper in `src-tauri` — established by this story — writes the decoded bytes to my chosen location (FR11, AD-15).
3. **Given** a tool that declares no drop support is active, **when** a file is dropped, **then** a visible no-op indication is shown — the drop is never silently swallowed (AD-14).
4. **Given** a dropped file that cannot be read (permissions, deleted mid-flight), **when** encoding is attempted, **then** a structured `ToolError` is rendered inline (NFR4).

## Tasks / Subtasks

- [x] **Task 1: `umbra-core::base64` — byte-safe encode/decode (AC: 1, 2, 4)**
  - [x] **Refactor, don't duplicate.** Today's `encode(input: &str, url_safe: bool) -> String` is infallible and text-only; `decode(input: &str) -> Result<String, ToolError>` forces decoded bytes through `String::from_utf8`. Neither can handle real file content (arbitrary binary in, arbitrary binary out). Extract the shared logic into two new byte-oriented functions and make the existing text functions thin wrappers around them:
    - `pub fn encode_bytes(bytes: &[u8], url_safe: bool) -> Result<String, ToolError>` — the actual `STANDARD.encode(bytes)` / `URL_SAFE.encode(bytes)` call, **preceded by the size guard** (see next bullet). This is now the single encode implementation.
    - Change `pub fn encode(input: &str, url_safe: bool) -> String` to `pub fn encode(input: &str, url_safe: bool) -> Result<String, ToolError>`, implemented as `encode_bytes(input.as_bytes(), url_safe)`. **This is a breaking signature change** — Story 2.1's code review explicitly deferred adding a size guard to `encode()` "to bundle with Story 2.2"; this refactor is how that deferred item gets closed, since `encode_bytes`'s guard now covers `encode` too via delegation. Update every existing call site and unit test that currently treats `encode()`'s return as a bare `String` (both in `base64.rs`'s own `#[cfg(test)]` block and in `src-tauri/src/commands/base64.rs`'s `base64_encode` command — see Task 2).
    - `pub fn decode_bytes(input: &str) -> Result<Vec<u8>, ToolError>` — move today's alphabet-detection + whitespace-stripping + padding-tolerant-decode logic here verbatim, **stopping before the UTF-8 validation step** (a decoded file can be — and usually is — non-UTF-8; forcing UTF-8 here would make this story impossible). Keep the existing size guard, now applied to this function.
    - Change `pub fn decode(input: &str) -> Result<String, ToolError>` to call `decode_bytes(input)?` then apply the existing UTF-8-validation-and-error-mapping step unchanged (the `base64-not-utf8` error stays exactly where it is today — it's a property of the *text* decode path, not the *file* decode path, since a file's decoded bytes are never expected to be UTF-8 text).
  - [x] **Size guard, unified.** Rename `check_input_size(input: &str)` to operate on a byte length instead of a `&str` (e.g. `fn check_size(len: usize) -> Result<(), ToolError>`), called from both `encode_bytes` (on `bytes.len()`) and `decode_bytes` (on `input.len()`, i.e. the Base64 *text* length — unchanged from today's behavior). Reuse the existing `MAX_INPUT_BYTES` constant/value for both text and file-byte paths — this project has no stated file-size requirement beyond FR9's JSON-specific 10 MB bar, so reusing the same already-reviewed threshold is the pragmatic default rather than inventing a new number. **State this reuse explicitly in a code comment** so a future reader knows it's a deliberate choice, not an oversight.
  - [x] No new dependency needed — `base64 = "0.23"` (already added by Story 2.1) covers everything here.

## Dev Notes

### Architecture compliance for this story

- **AD-1/AD-2 (functional core):** `encode_bytes`/`decode_bytes` are pure functions in `crates/umbra-core/src/base64.rs`, zero I/O, zero Tauri dependency — identical constraint to Story 2.1's `encode`/`decode`. The file-reading and file-writing themselves are explicitly **not** core's job (AD-15) — they live in `src-tauri/src/fs_helper.rs`. [Source: `ARCHITECTURE-SPINE.md` AD-1, AD-2]
- **AD-3 (ToolError contract):** `fs_helper.rs`'s two new error codes (`file-read-error`, `file-write-error`) are deliberately **not** prefixed `base64-*` — they are shared, cross-tool codes, since Story 2.5 (hash files) hits the identical failure mode against a different tool. This is the first story to introduce a `ToolError` code that isn't scoped to one tool; the spine's Deferred section already flags "`ToolError.code` cross-tool namespacing" as an open question with "revisit if two tools are observed picking colliding codes" — this story doesn't collide (it deliberately *shares* one code across two tools' commands), so it doesn't trigger that revisit, but it's worth knowing that section exists. [Source: `ARCHITECTURE-SPINE.md` AD-3; Deferred section]
- **AD-4 (async, off the main thread):** both new commands (`base64_encode_file`, `base64_decode_to_file`) wrap their work in `tauri::async_runtime::spawn_blocking`, matching every existing command in this codebase — a dropped file's read/decode/write can easily exceed the ~100ms bar `json.rs`'s pattern was built around. [Source: `ARCHITECTURE-SPINE.md` AD-4]
- **AD-5 (one Tool Registry):** the `drop` field being populated on Base64's existing registry entry is the only registry change; no new entry, no router/sidebar changes. [Source: `ARCHITECTURE-SPINE.md` AD-5]
- **AD-14 (shell owns OS I/O edges exactly once) — the core of this story:** exactly one `onDragDropEvent` listener, registered once in the always-mounted `DropZone.vue`, dispatching via the registry — see Task 5's "Interaction model" note for the specific (and only-partially-literal) reading of "handler command name" this story implements. No tool registers its own drop listener. [Source: `ARCHITECTURE-SPINE.md` AD-14]
- **AD-15 (files cross IPC as paths; core never touches the filesystem):** the dropped file's absolute path crosses the IPC bridge as a string (from the native drop event, already resolved before any `invoke()` call); `src-tauri` (via `fs_helper.rs`) is the only thing that ever calls `std::fs::read`/`std::fs::write`; the *encoded* Base64 string returned by `base64_encode_file` is text output meant for display/copy, not "raw bytes riding IPC" in the sense AD-15 warns about (that sense refers to binary payloads, which this story's design ensures never cross the bridge — encoding happens entirely on the Rust side after a path-only IPC call, and decoding writes bytes directly to disk without ever sending them back to JS). [Source: `ARCHITECTURE-SPINE.md` AD-15]
- **AD-6 (tools are islands):** `lastDrop`'s shared-`ref`-not-Pinia-store design (Task 5) is this story's explicit reasoning for staying compliant with AD-6's "only `settings`/`registry` stores" rule while still needing *some* shared signal between the shell and the active tool. [Source: `ARCHITECTURE-SPINE.md` AD-6]

### Library/Framework Requirements

- **`tauri-plugin-dialog` (Rust) / `@tauri-apps/plugin-dialog` (JS):** both verified this session at **2.7.2** directly against the crates.io/npm registry APIs (not a search-engine snippet, per this project's stack-verification convention established in Story 2.1 and the spine's own header note) — license `Apache-2.0 OR MIT` / MIT respectively, both permissive, no further license review needed. This exact version was already anticipated in `ARCHITECTURE-SPINE.md`'s Stack table ("`tauri-plugin-dialog` 2.x (2.7.2 observed 2026-07-20)") even though it wasn't yet a real dependency anywhere — this story is what makes that spine entry real.
- **`save()` API (verified via Context7, `/websites/v2_tauri_app`, this session):** `import { save } from '@tauri-apps/plugin-dialog'; const path: string | null = await save({ filters?: [{ name, extensions }] })` — returns the chosen absolute path, or `null` if the user cancels. This story calls it with no filters (no file-type restriction specified by any AC).
- **`onDragDropEvent` API (verified via Context7, same source):** `import { getCurrentWebview } from '@tauri-apps/api/webview'; const unlisten = await getCurrentWebview().onDragDropEvent((event) => { if (event.payload.type === 'drop') { /* event.payload.paths: string[] */ } })`. Call the returned `unlisten()` on unmount. `dragDropEnabled` defaults to `true` on Tauri 2.11.5 (this project's pinned version) and is not currently set in `tauri.conf.json` — no config change is needed for native drop events to reach the window; this story is purely application code.
- **No new Rust dependency for file I/O** — `std::fs::read`/`std::fs::write` (standard library) are sufficient and are what AD-15 intends by "one shared save-dialog-plus-write helper"; `tauri-plugin-fs` is unnecessary and would duplicate what a plain Rust function already does more simply.
- **Capability/permission verification (verified via Context7):** the dialog plugin's `dialog:default` permission bundles `allow-save`/`allow-open`/`allow-message`. Custom application commands (this project's own `#[tauri::command]` functions, including the new `base64_encode_file`/`base64_decode_to_file`/anything in `fs_helper.rs`) are **not** subject to the capability ACL the way plugin-provided commands are — this matches the existing repo's observed state (`json_format`/`base64_encode` need no `json:*`/`base64:*` capability entries today, and `src-tauri/capabilities/default.json` has none).
