# Story 7.8: Clipboard-suggestion surface

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want Umbra to notice when I've copied something it recognizes and surface the right tool,
so that I don't have to remember or hunt for which tool handles it.

## Acceptance Criteria

1. **Given** clipboard content changes (a real clipboard-change event, not a polling timer), **when** the content matches a known shape, **then** a highlighted "Clipboard match" entry appears at the top of the sidebar showing the matched tool's icon, name, and a truncated content preview. [Source: epics.md#Story-7.8, AC1; EXPERIENCE.md:61,84]
2. **Given** clipboard content detection, **when** implemented, **then** it is fully deterministic and local — no AI/ML inference, no new dependency — matching content against shape rules (JWT: three dot-separated base64url segments; JSON: parses successfully; Base64: matches the alphabet with valid padding) in `src/shell/`. [Source: epics.md#Story-7.8, AC2 (:1268, verbatim); PRD FR19 (:77), FR21 (:79); ARCHITECTURE-SPINE.md AD-7 (:81-85)] **Note (flagged during story creation, see Dev Notes "AC2's 'no new dependency' vs. Task 1's new Rust dependency — a disclosed reading, not a silent edit"):** epics.md's literal text says "no new dependency," full stop — this story reads that as scoped to the *shape-matching logic itself* (which is genuinely dependency-free, per Task 4), not as a blanket ban covering AC13's separately-flagged clipboard-change-event risk, which explicitly licenses its own scope decision. Confirm this reading holds before/while implementing Task 1.
3. **Given** a tool that wants clipboard-suggestion eligibility, **when** it's registered, **then** it declares an optional `clipboardMatch: { test: (content) => boolean, specificity: number }` on its Tool Registry entry — `test` is the shape predicate, `specificity` is an author-declared integer (higher = more structurally distinctive) — the shell iterates every registered entry's matcher rather than hardcoding a tool list. [Source: epics.md#Story-7.8, AC3; ARCHITECTURE-SPINE.md AD-5 (:69-73)]
4. **Given** clipboard content that matches more than one tool, **when** detection runs, **then** all matches are candidates, sorted by `specificity`, and — if more exist than the configured limit — only the top N show, each as its own "Clipboard match" callout stacked above Story 7.5's Pinned section, never one callout listing several tools. Ties on `specificity` are broken by stable registry order — deterministic, never random. [Source: epics.md#Story-7.8, AC4]
5. **Given** the Settings Privacy section, **when** viewed, **then** it exposes one control — "Clipboard suggestions to show" — an integer 0–5 (default 3), persisted as `shell.clipboardSuggestionMaxCount`. This single setting satisfies both the INV-1 disclosure requirement and the disable path (`0` = off) — no separate boolean toggle alongside it. **Note (flagged during story creation, see Dev Notes "Settings control shape — a real doc conflict"):** the locked mockup (Screen 03) instead shows a boolean "Suggest from clipboard" toggle, and `EXPERIENCE.md` Flow 5 step 3 says "she disables the clipboard-suggestion toggle." This story's implementation follows epics.md's literal integer-control text as the default (per this project's established epics.md-is-authoritative convention), with the conflict disclosed rather than silently resolved — confirm before/while implementing Task 8. [Source: epics.md#Story-7.8, AC5; PRD FR5 (:48); DESIGN.md Screen 03 mockup; EXPERIENCE.md:161]
6. **Given** `shell.clipboardSuggestionMaxCount` is `0`, **when** clipboard content changes, **then** detection doesn't run at all — not just hidden output, no matching work happens. [Source: epics.md#Story-7.8, AC6]
7. **Given** the surface appears, **when** it renders, **then** its appearance is announced via a polite live-region-equivalent cue, scaling to the count (e.g. "3 tools suggested from clipboard" vs. naming one tool) so a user mid-task elsewhere learns it appeared without needing visual focus there. [Source: epics.md#Story-7.8, AC7; EXPERIENCE.md:61,75,147 (Flow 4); PRD NFR5 (:119)]
8. **Given** multiple suggestions appear, **when** each is keyboard-navigated, **then** every one is individually focusable and reachable in the sidebar's tab sequence. [Source: epics.md#Story-7.8, AC8; PRD NFR5 (:119)]
9. **Given** the user activates a suggestion, **when** the tool opens, **then** the clipboard content is already available to paste in one action (FR4) — not auto-pasted without user action. [Source: epics.md#Story-7.8, AC9; PRD FR4 (:47)]
10. **Given** a new clipboard copy occurs while suggestions are showing, **when** the new content is processed, **then** the entries swap or clear per the new match — never stack. [Source: epics.md#Story-7.8, AC10; EXPERIENCE.md:75]
11. **Given** clipboard content only superficially resembles a shape (false positive), **when** the suggestion is opened, **then** the tool shows its own precise inline-error/no-valid-input state rather than crashing or silently mis-suggesting. [Source: epics.md#Story-7.8, AC11; EXPERIENCE.md:151 (Flow 4 Failure path)]
12. **Given** the clipboard currently holds image data, **when** detection runs, **then** the surface suggests the Bucket (OCR) tool based on a format/MIME check alone — no image bytes are read or processed until the user opens the suggestion. [Source: epics.md#Story-7.8, AC12; ARCHITECTURE-SPINE.md AD-4 (:63-67, "heavy resources initialize lazily on first use" — the directly on-point citation for deferring the image read)]
13. **Given** cross-platform clipboard-change-event availability — flagged as an unresolved engineering risk in `EXPERIENCE.md` — **when** this story implements it, **then** that risk is resolved here; if the event isn't reliably available on a target platform, that's surfaced as an explicit scope decision, never silently dropped. **Resolved during story creation, see Dev Notes "Resolving AC13 — the clipboard-change-event risk":** no OS provides a true push event on every platform — Windows and Linux/X11 do, macOS and Wayland do not. Recommended default: adopt `clipboard-rs` directly as a new `src-tauri` dependency, native events where the OS provides them, a bounded 500ms local poll only where it doesn't (macOS/Wayland) — framed honestly as "OS-native where available, polling only where no alternative exists," which is what this AC's privacy framing is actually guarding against, not the literal absence of any poll anywhere. Confirm this approach (or an alternative) before/while implementing Task 1. [Source: epics.md#Story-7.8, AC13; EXPERIENCE.md:84; PRD FR28 (:92, HEIC-descope precedent for this kind of documented scope call)]

- [x] **Task 4: Write the pure, local shape-matching predicates** (AC: 2, 11, 12)
  - [x] New file, e.g. `src/shell/clipboardMatch.ts`. **No existing TS-side shape-validation logic exists to reuse** — confirmed by reading the current codebase: JWT decoding lives in Rust (`crates/umbra-core/src/jwt.rs`, invoked via command) and Base64 decoding likewise (`crates/umbra-core/src/base64.rs`). Round-tripping every clipboard change through an IPC call to validate shape would be both slower and unnecessary — these predicates only need to classify a *shape*, not fully decode/validate it (full validation still happens when the user opens the suggested tool, satisfying AC11's false-positive requirement naturally). Write new, minimal, synchronous predicates directly in TS:
    - JWT: `content.split(".").length === 3` and each segment matches a base64url charset (`/^[A-Za-z0-9_-]+$/`), non-empty.
    - JSON: `JSON.parse(content)` succeeds (wrap in try/catch, return boolean — discard the parsed value, the tool re-parses on open).
    - Base64: matches the base64/base64url alphabet, **tolerating both padded and unpadded input** — do not require exact padding. This deliberately loosens epics.md's literal "valid padding" wording: `crates/umbra-core/src/base64.rs`'s actual decoder is configured `DecodePaddingMode::Indifferent` and its own doc comment (`:61-63`) explains why — "unpadded Base64URL is the norm for real-world tokens" — and it also tolerates whitespace/line-wraps. A predicate that rejects unpadded input would produce false negatives against content the real Base64 tool decodes successfully on open, directly contradicting the file this story cites as its own mirror source. Match the decoder's actual tolerance, not the AC's shorthand phrasing.
  - [x] Define the content type predicates actually receive — since AC12 needs an "image, no bytes read" case alongside AC2's text-shape cases, and epics.md's literal `test: (content) => boolean` signature doesn't itself specify `content`'s type: use a small discriminated union, e.g. `type ClipboardContent = { kind: "text"; value: string } | { kind: "image" }`. Text-matching tools test `content.kind === "text" && <shape check>(content.value)`; Bucket's matcher is simply `content.kind === "image"`. Record this as a resolved interpretation in Completion Notes — it's a real design call this story is making, not something any source doc spells out structurally.
  - [x] Unit-test each predicate directly in `clipboardMatch.spec.ts`: valid/invalid JWT shapes (including a false-positive-shaped string — three dot-separated segments that aren't valid base64url, and one that is base64url-shaped but not a real token, per AC11), valid/malformed JSON, valid/invalid Base64 (including a string that's alphabet-valid but wrong-length padding).

## Dev Notes

### Resolving AC13 — the clipboard-change-event risk

This is the story's single highest-risk technical unknown, researched directly (not assumed) during story creation per this project's "Dependency version/API drift" convention.

- **The already-installed plugin can't do this.** `@tauri-apps/plugin-clipboard-manager` `2.3.2` (JS) / Rust, already a dependency since Story 4.2's OCR-paste feature, exposes only on-demand `readText`/`writeText`/`readImage`/`writeImage` — confirmed live via Context7 against `/tauri-apps/tauri-docs`; nothing in its docs mentions a change/listen event.
- **No OS provides a true push event everywhere.** Read `clipboard-rs`'s (MIT, actively maintained, `0.3.5` as researched) per-platform watcher source directly: Windows uses the real `WM_CLIPBOARDUPDATE` message (genuine event, no polling); Linux/X11 uses XFixes `SelectionNotify` (genuine event); **macOS has no OS-level clipboard-change notification at all** — its own source comment states plainly that it polls `NSPasteboard.changeCount` every 500ms because the OS gives it nothing else; Wayland has the same gap and also polls every 500ms. This means the AC's "a real clipboard-change event, not a polling timer" text **cannot be honored literally on macOS** — notably the developer's own primary dev/test platform per every prior story's manual-verification notes — by any known mechanism. This is a hard platform limitation, not an implementation gap.
- **Recommended resolution (a real scope decision, matching FR28's HEIC-descope precedent — confirm during implementation, don't silently drop):** adopt `clipboard-rs` directly as a new `src-tauri` dependency (not the community `tauri-plugin-clipboard` wrapper — see Task 1 for why that's the weaker choice), accept native push events where the OS provides them, and accept a short, bounded 500ms local poll only where the OS provides no alternative. Frame this honestly in any user-facing copy/documentation as "reacts to clipboard changes, checking briefly where the OS provides no native signal" rather than either overclaiming a universal real event or silently building a naive always-polling implementation — the actual privacy-optics distinction `EXPERIENCE.md:84` cares about is "reacts to real changes, same-machine, zero network" vs. "continuously watches and phones out," and a bounded local fallback poll still satisfies that distinction even though it isn't a literal OS event on every platform.
- **A rejected alternative, for the record:** writing fully custom native platform code per OS (raw `WM_CLIPBOARDUPDATE` window-message handling, raw XFixes bindings, etc.) directly in this project instead of depending on `clipboard-rs` — rejected as substantially more engineering effort and maintenance surface for the same end result `clipboard-rs` already provides and actively maintains upstream.
