# Story 5.2: Umbra updates itself — with consent and full disclosure

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want the app to offer updates that install only after my explicit confirmation, with the network exception disclosed loudly,
so that staying current never compromises the local-only promise silently.

## Acceptance Criteria

1. **Given** a newer release exists, **when** the app checks the update feed, **then** an app-built confirmation dialog presents the update, and installation proceeds only after explicit user confirmation (FR31, AD-12 — the v2 updater plugin ships no dialog of its own).
2. **Given** the INV-1 carve-out, **when** the README and the app's Settings/about surface are reviewed, **then** both disclose the update check as the sole permitted network call — shipping with only one of the two disclosures violates AD-7 (FR31).
3. **Given** the app's dependency tree and capabilities, **when** audited, **then** `tauri-plugin-updater` is the only network-capable component and the webview still grants no network scope (AD-7).
4. **Given** the user declines an update, **when** the dialog is dismissed, **then** no installation occurs and the app continues normally.

**Boundary with Story 5.1 (already done) and Story 5.3 (not started):** Story 5.1 deliberately stopped short of this story's scope — it generated the updater signing keypair, added the *inert* `plugins.updater.pubkey` and `bundle.createUpdaterArtifacts` to `tauri.conf.json`, and published a real prerelease (`v0.1.0-alpha.1`) whose `latest.json` is already signed and live on GitHub. It explicitly left `tauri-plugin-updater` uninstalled, `plugins.updater.endpoints` unset, and the confirmation dialog unbuilt — that is this story's job. Story 5.3's written network-monitor release checklist (which will observe this story's update check as the one expected connection) is not this story's job — don't write that checklist here.

## Dev Notes

- **This story's Rust-side footprint is two plugin registrations, nothing else.** No `umbra-core` changes, no new `#[tauri::command]`, no `src-tauri/src/commands/` changes. If implementation reveals a need to touch any of those, that's a signal the story has drifted past its own scope (mirrors Story 5.1's own Project Structure Notes caution) — the updater and process plugins are self-contained; this project's job is registering them, configuring `tauri.conf.json`, and building the frontend dialog around their existing JS bindings.
- **Don't build a custom Rust command wrapping the updater in `ToolError`.** Tauri's own official pattern (seen in the more elaborate Context7 example using a `Channel` for progress events and a `PendingUpdate` app-managed state) exists for apps that need fine-grained download-progress UI or server-side pending-update state across multiple IPC round-trips. This story's ACs don't ask for progress events (AD-16 itself says "v1 ships no progress events and no cancellation" for slow commands generally) — the simpler, officially-documented `check()` → `update.downloadAndInstall()` → `relaunch()` JS-only path is sufficient and is what Task 3/4 build. Reaching for the `Channel`-based pattern here would be solving a problem this story doesn't have.
- **AD-16's shared `invoke` helper / `createLatestWinsRunner` do not apply here.** That machinery exists for this project's own `#[tauri::command]` invocations racing each other per-tool. The updater plugin's `check()` isn't invoked through `src/shell/invoke.ts` at all, and with no manual "Check for Updates" button in this story's scope (see Task 4's scope decision), there's no double-invocation surface to guard against — the one auto-check per app-lifetime is inherently single-flight.
- **The window-visibility launch sequence in `src/main.ts` is load-bearing — read it before touching anything launch-adjacent.** It already has a documented `try/finally` specifically to guarantee `getCurrentWindow().show()` is never blocked by a slow/failed async step. `UpdateDialog.vue`'s auto-check must stay entirely downstream of that, mounted-component-`onMounted` is the correct hook precisely because it runs after `mount()`+`show()`, not before.
- **No new persisted state.** No settings.json key, no "skip this version" memory, no last-checked timestamp — none of the four ACs ask for it, and adding one would touch `AD-10`'s audit surface (the Settings pane's "enumerates every persisted key" promise) for no requirement in this story. If a future story wants that, it's a clean, separable addition.
- **Testing:** this story is almost entirely frontend (Vue + two plugin registrations). No new `umbra-core` unit tests are expected (no core logic changes).
