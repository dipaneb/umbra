# Story 6.2: Convert and compress images

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want to convert images between formats and compress them with a quality preview,
so that I can prepare assets without an online converter.

## Acceptance Criteria

1. **Given** a dropped image, **when** I choose a target format among PNG/JPEG/WebP/HEIC, **then** the converted file is produced and saved via the shared save helper (FR28, AD-15).
2. **Given** a lossy target format, **when** I adjust the quality slider, **then** an estimated output size displays before saving, updating with the slider (FR28), **and** the estimate is computed off the UI thread with latest-wins on rapid changes (AD-4, AD-16).
3. **Given** HEIC support, **when** the crate route is evaluated in this story, **then** decode/encode support is verified against AD-11's three-platform compile gate, **and** if HEIC cannot clear that bar, the limitation is surfaced as an explicit scope decision — never silently dropped (NFR3).
4. **Given** an unreadable or unsupported image, **when** conversion is attempted, **then** a structured `ToolError` displays inline (NFR4).

**Interpretation notes, recorded explicitly rather than left implicit:**
- **AC1's "dropped" does not mean wired through the AD-14 window-level drop dispatcher.** Same reasoning Story 6.1 already recorded for PDF input (see its Dev Notes' "Why PDF input bypasses the AD-14 drop dispatcher"): AD-14's dispatcher forwards one path to one fixed registry-declared command, but this story needs a target-format choice and a quality value supplied *before* the operation runs — a bare drop event can't carry that. This story uses `@tauri-apps/plugin-dialog`'s `open()` file picker instead, the same already-used, zero-AD-14-change mechanism Story 6.1 established. Window-level drag-and-drop of a non-PDF image onto the Bucket while its OCR drop-zone is showing still routes to `bucket_extract_text` as today — unaffected by this story.
- **AC2's "a lossy target format" is JPEG only, not JPEG+WebP, given the crate this codebase already depends on.** `image` 0.25.9 (already a workspace dependency, pinned in `Cargo.lock`, used today by `ocr.rs`) ships a `WebPEncoder` that is **lossless-only** — verified against `docs.rs/image/0.25.9`: `WebPEncoder` exposes exactly two public constructors (`new_lossless` and the trait-provided `encode`), no quality parameter, and its own docs state "Right now only lossless encoding is supported." `JpegEncoder::new_with_quality(w, quality: u8)` (1–100) is the only encoder among the four target formats this story's ACs name that actually takes a quality knob. So: PNG and WebP are valid conversion *targets* (FR28's "convert between" clause), always encoded losslessly, with no quality slider shown for them; the quality slider (AC2) applies to JPEG only. This is a precise reading of AC2's own "given a lossy target format" conditional, not a scope reduction — see Dev Notes for the full verification trail.
- **AC3's HEIC evaluation was performed during story creation, not deferred untouched to the developer** — see Task 1, which is the load-bearing task of this story. All three realistic Rust HEIC crate routes investigated in this session carry a real, currently-unresolved blocker (license, publish/maturity, or AD-11 three-platform CI compile risk). The recommended default is to descope HEIC from v1 and record that decision explicitly, per AC3's own wording — but Task 1 requires a live re-verification before locking that in, since this is exactly the kind of pre-1.0/fast-moving dependency landscape the spine's "Dependency version/API drift" convention exists for.

**Not the first story of Epic 6** — Story 6.1 (`6-1-work-pdfs-locally-merge-split-extract`) is `done`, merged to `origin/main` as `97d34d4` (PR #61, squash-merged). `epic-6` stays `in-progress` (no epic-status transition needed).

- [ ] **Task 1: HEIC crate decision (AC3) — do this first, it can reshape Task 2's scope**
  - [ ] **Re-verify live before trusting the findings below** — this story's own research is a starting point, not a substitute, per `ARCHITECTURE-SPINE.md`'s "Dependency version/API drift" convention (any pre-1.0 dependency or a landscape that could move between story drafting and implementation needs a fresh check). Three candidate routes were investigated this session:
    1. **`libheif-rs`** (MIT, latest 2.7.0, requires Rust ≥1.82) — a safe FFI wrapper around `libheif-sys`. By default requires a **system-installed libheif** (not present on any of `ubuntu-latest`/`windows-latest`/`macos-latest`'s default images), which would break AD-11's three-platform CI compile gate outright. It offers an `embedded-libheif` feature to vendor-build libheif from source instead — but libheif's own real codec dependencies for HEVC (the codec HEIC actually uses) are `libde265` (LGPL-2.1, decode) and, for encoding, `x265` (GPL, or a paid commercial license) — both copyleft, which the spine's own dependency-hygiene convention (`ARCHITECTURE-SPINE.md` Consistency Conventions table: "copyleft/GPL needs explicit review") flags as needing a deliberate decision, not a default `cargo add`. Building `x265`/`libde265` from source on `windows-latest` in CI (needs a C/C++ toolchain, cmake, and nasm, none guaranteed present) is also a real risk to the 20-minute CI job timeout (`ci.yml`'s `timeout-minutes: 20`).
    2. **`heic` (Imazen)** — pure Rust, no C/C++ dependency, SIMD-accelerated, decode-only (118/162 HEIF conformance files, 49/49 HEVC conformance vectors passing per its own published results). **Disqualifying: dual-licensed `AGPL-3.0-only OR LicenseRef-Imazen-Commercial`.** AGPL is a strong copyleft license the spine's dependency-hygiene convention explicitly calls out; bundling it into Umbra's All-Rights-Reserved app without purchasing Imazen's commercial license would put the app's own distribution in violation of AGPL's terms. Buying a commercial license is a real option but is a business/cost decision outside a coding story's scope — not something to decide silently here.
    3. **`heic_decoder` (ente-io)** — pure Rust, decode-only, `image` crate integration hooks. **Disqualifying: not published to crates.io** (a direct crates.io API lookup for `heic-decoder` returned 404; its own README instructs installing it as a local **path** dependency, not a versioned registry dependency) and its license could not be confirmed from the repo in this session. The spine's dependency-hygiene convention requires a license check before adding any dependency — an unpublished, unlicensed-per-this-check crate fails that bar regardless of its technical merits.
  - [ ] **None of the three cleanly clears both AD-11's three-platform compile gate and the spine's dependency-hygiene bar within v1 scope.** Recommended decision, to confirm or override after the live re-check above: **descope HEIC from v1** — ship PNG/JPEG/WebP conversion only, and record this explicitly (in this story's Dev Notes/Change Log and, if `FR28`/`epics.md` cite HEIC as already-delivered scope anywhere reader-facing, flag that too) rather than silently shipping three formats and letting "HEIC" quietly vanish from what anyone reviewing the PR expects. This satisfies AC3's own wording exactly ("if HEIC cannot clear that bar, the limitation is surfaced as an explicit scope decision — never silently dropped") — AC3 does not require HEIC to ship, it requires the evaluation and, if HEIC is cut, an explicit record of why.
  - [ ] If a live re-check finds the landscape has changed (e.g. `heic_decoder` published to crates.io with a confirmed permissive license, or `libheif-rs`'s embedded build proves practical and the GPL/LGPL codec dependency gets an explicit, deliberate sign-off), HEIC can be added as a decode-only *source* format (convert HEIC → PNG/JPEG/WebP) — encoding *to* HEIC is out of scope regardless of which crate is chosen, since all three viable candidates found are decode-only. - [ ] **Task 2: Core image module — `crates/umbra-core/src/image_convert.rs` (AC1, AC2, AC4)**

Use `image_convert.rs` / `pub mod image_convert;` instead. Update the Structural Seed's placeholder to match once implemented, per Story 6.1's own "keep documented facts truthful" precedent for its `pdf.rs` resolution.

  - [ ] `pub fn convert(bytes: &[u8], target: TargetFormat, quality: u8) -> Result<Vec<u8>, ToolError>` — decode via `image::load_from_memory` (format-sniffed, the exact pattern `ocr.rs::extract_text` already uses), then encode to `target`:
    - `Jpeg`: validate `(1..=100).contains(&quality)` first — an out-of-range value is a `ToolError` (recommended code: `bucket-image-invalid-quality`), core-layer-authoritative per AD-1 (mirrors `pdf.rs::extract_page_range`'s own core-layer range validation precedent — a frontend slider `min`/`max` is a UX nicety, not a substitute).     - `Png`/`WebP`: `quality` is accepted but ignored (both are lossless-only through this crate, per this story's own AC2 interpretation note above) — document this in a doc comment on the function, not just the story file, so a future reader isn't surprised the parameter is a no-op for two of the three variants.
  - [ ] `pub fn estimate_size(bytes: &[u8], target: TargetFormat, quality: u8) -> Result<u64, ToolError>` — implement as `Ok(convert(bytes, target, quality)?.len() as u64)`. This is a deliberate reuse, not a placeholder: it gives an exact real byte count (the actual encode already ran) rather than inventing and maintaining a separate size-estimation heuristic that could drift from what `convert` actually produces. Do not build a second estimation code path.
  - [ ] Error mapping: undecodable/corrupt input → `ToolError` (recommended code: `bucket-image-unsupported-format`, distinct from OCR's existing bare `bucket-unsupported-format` — follow Story 6.1's own `bucket-pdf-*` precedent for a feature-scoped prefix, here `bucket-image-*`) — never a panic (AC4, NFR4). Cover: PNG→JPEG at a given quality decodes back to a valid JPEG of the expected dimensions; JPEG quality 1 produces smaller output than quality 100 for the same source (proves the quality parameter is actually wired, not ignored); an out-of-range quality (0, 101) with `target: Jpeg` returns `bucket-image-invalid-quality`; the same out-of-range quality with `target: Png`/`WebP` succeeds (quality genuinely ignored for those targets, not silently validated against JPEG's range); `estimate_size` returns exactly `convert(...)?.len()` for the same inputs (proves the reuse, not a coincidence); undecodable bytes (`b"not an image"`) and a truncated/corrupted real image fixture (same truncation-test shape as `ocr.rs`'s own corrupt-image test) both return `bucket-image-unsupported-format`, never panic.

## Dev Notes

- **Story 6.1's AD-15/AD-16 patterns are the direct template for this story** — `bucket_merge_pdfs`'s `output_path` argument (never bytes over IPC) and the "PDF section is a disjoint state group, gets its own local runner(s)" reasoning both apply again here, with one refinement: this story's live quality-slider estimate needs *two* local runners where Story 6.1's three-button PDF section needed one, because a continuously-firing preview and a discrete save action are a genuinely different shape (see Task 4).
- **The `image` crate is already a workspace dependency — no new `Cargo.toml` entry needed** for the recommended (PNG/JPEG/WebP, no HEIC) scope. `image = "0.25"` is already declared in `crates/umbra-core/Cargo.toml` (used by `ocr.rs`), resolved to `0.25.9` in `Cargo.lock` as of this story's drafting (`0.25.10` exists upstream — a patch-level drift, not required reading for this story since no API this story needs has changed between those two patches; re-confirm only if Task 1 or implementation hits something version-specific). Default features (`rayon` + `default-formats`, confirmed live against the crates.io API) already include `png`, `jpeg`, and `webp` codec support — nothing to enable.
- **The crate-root module-naming collision (Task 2) is the sharpest way to get this story visibly wrong on the first attempt** — `image.rs` looks like the obviously-correct name (it's literally what the Structural Seed placeholder says), but declaring `pub mod image;` in a crate that also has `image` as an extern crate dependency is a real Rust namespace collision, not a lint or a style nit. `image_convert.rs` is this story's resolution; update the Structural Seed to match once landed, exactly as Story 6.1 did for its own `pdf.rs` resolution.
- **The WebP-is-lossless-only finding (Task 2, this story's own AC2 interpretation note) is load-bearing, not a footnote** — building a quality slider that silently does nothing for a WebP target (because the encoder ignores it) would be exactly the kind of "vague implementation" this workflow exists to prevent. Gating the slider's visibility on `target === "jpeg"` in the UI (Task 4) is what keeps the frontend honest about this, matching the core layer's own behavior (`quality` accepted-but-ignored for `Png`/`WebP`, documented in a doc comment).
- **HEIC (Task 1) is the one open question this story could not fully close during drafting** — not for lack of trying: three real candidate crates were investigated and each has a concrete, named blocker (AGPL/commercial dual license, unpublished/unconfirmed-license, or a GPL/LGPL-codec-dependent CI-compile risk). This mirrors Story 6.1's own "two real design questions not decided anywhere upstream" pattern (its AD-14 drop-dispatcher and AD-16 runner-shape questions) — the difference is Story 6.1 was able to fully resolve both during drafting, while this story's HEIC question has a real live-verification step (Task 1's "re-verify before trusting these findings") that only the implementing session can close, since crate licensing/publish status is exactly the kind of fast-moving state the spine's own "Dependency version/API drift" convention warns against trusting from a cached story.
- **No `umbra-core` module needs a filesystem touch** — same AD-2/AD-15 reasoning as every prior Bucket story; `image_convert.rs`'s two functions take/return in-memory bytes only.
- **No registry/AD-5 changes required beyond the optional alias additions** — the `bucket` tool registry entry keeps its existing `drop`/`paste` declarations untouched, same reasoning as Story 6.1's own Dev Notes.
- **No new persisted state** — image path, target format, and quality are transient, in-memory, per-session UI state, same as every other tool's working-input state in this codebase (no `AD-10`/`settings.json` involvement).
- **Testing:** follow `image_convert.rs`'s sibling `pdf.rs`'s real-fixture-over-mocks convention for the core layer (in-test-generated images, not committed binaries — same reasoning `pdf.rs` used for in-test-generated PDFs), and `pdf.rs`'s (not `bucket.rs`'s) simpler direct-call test shape for the command layer, since neither new command needs an `AppHandle`.
