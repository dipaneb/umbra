# Story 4.1: Drag an image in, get its text

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want to drop an image into the Bucket and get its text extracted entirely on-device,
so that screenshots of errors and documents become copyable text without touching any cloud OCR.

## Acceptance Criteria

1. **Given** the Bucket tool is active, **when** I drop a PNG, JPEG, or WebP image, **then** its text is extracted by the local ONNX OCR engine and displayed (FR23), **and** the file arrives as a path via the shell drop service — `src-tauri` reads the bytes and hands them to core (AD-14, AD-15).
2. **Given** the OCR implementation, **when** inspected, **then** `umbra-core` defines the OCR trait (image bytes in → recognized text + confidence out) and `oar-ocr` is the adapter behind it — callers, commands, and UI depend on the trait only (AD-8), **and** the PaddleOCR ONNX models are bundled as app resources with `oar-ocr`'s auto-download not enabled (AD-7), **and** the exact model files are chosen and documented in this story, closing the spine's deferred item.
3. **Given** a cold app launch, **when** launch completes, **then** the OCR engine has not initialized — it initializes lazily behind a thread-safe once-cell on first use, and cold launch stays under 2 seconds (AD-4, AD-16, NFR2).
4. **Given** OCR inference is running, **when** the UI is used, **then** inference executes async on the blocking thread pool and the UI stays responsive (AD-4).

**Explicitly out of scope for this story** (do not build ahead of these — later stories own them, per epics.md's own story split):
- Editable result text / one-click copy — FR24, Story 4.2's AC.
- Clipboard-paste (⌘V) input — Story 4.2's AC.
- Explicit "no text found" / corrupt-image messaging beyond a plain structured `ToolError` — FR26, Story 4.3's AC.
- The formal NFR1 network-monitor tour proving zero network activity — Story 4.3's AC (this story still must not enable any auto-download path; that's AC2 above, not the same thing as the release-blocking proof).
- Racing-first-use-initialization test coverage — Story 4.3's AC (this story must still *build* the once-cell guard correctly; 4.3 adds the concurrency test for it).

## Dev Notes

- **This is Epic 4's first story and structurally the most novel one in the project so far** — first bundled ML dependency, first Tauri resource-bundling usage, first lazy-singleton pattern, first command needing `AppHandle`, first new Cargo dependency added mid-epic rather than at scaffold time. Budget more verification time than a typical story; don't pattern-match its size expectations against Epic 2/3 stories.
- **Version drift already happened once, live, during this story's own creation.** The spine pinned `oar-ocr` 0.8.x on 2026-07-20 with an explicit "re-verify at Epic 4 start" warning; by 2026-08-03 (one day before this story was drafted) the crate was at 0.9.0. Task 1 is not optional boilerplate — treat every API detail in this Dev Notes section sourced from `oar-ocr`'s docs as a hypothesis to confirm against the real crate, not a fact to build against blindly. [Source: `ARCHITECTURE-SPINE.md` Stack table, `oar-ocr` row]
- **Two unrelated "downloads" are both named `oar-ocr`/`ort` — don't conflate them:**
  1. `ort`'s own default behavior downloads the ONNX Runtime *shared library binary* at **build time** (`cargo build`), cached by CI per AD-11 (Task 8). This is not a v1-runtime network call and doesn't violate INV-1/AD-7.
  2. `oar-ocr`'s `auto-download` Cargo feature — opt-in, not default — would fetch OCR *model weights* from a hub at **runtime** if enabled. This is exactly the AD-7 risk; Task 1 confirms it stays off.
- **AD-8 (the architectural point of this story):** the OCR trait lives in `umbra-core`, `oar-ocr` sits behind it as the v1 adapter, and nothing outside `ocr.rs` imports `oar-ocr` directly. The spine's own Deferred section flags that a future structured-extraction feature (FR29, Epic 6) might extend or fork this same trait shape — naming the module after the capability (`ocr.rs`), not the tool (`bucket`), keeps that door open without deciding it now. [Source: `ARCHITECTURE-SPINE.md` AD-8, Deferred section]
- **AD-16's amendment is this story's load-bearing precedent, and it's not on `main` yet — see Task 0.** The amendment (dated 2026-08-04, from the Epic 3 retrospective) names `registry.getLatestWinsRunner(toolId)` as the required pattern specifically for "Epic 4's Bucket tool (drag-drop and clipboard-paste both dispatching to the same registry-declared handler, per Story 4.2's AC)" and cites `HashView.vue` as the reference implementation. This closed what was Epic 2's retrospective action item #1, left open through all of Epic 3 because neither cron section needed it. [Source: `ARCHITECTURE-SPINE.md` AD-16 amendment, `_bmad-output/implementation-artifacts/epic-3-retro-2026-08-04.md` Action Items]
- **AD-4/AD-16 (performance):** OCR inference is exactly the kind of >100ms CPU work AD-4 exists for — it must run on `spawn_blocking`, not the async executor's default thread. The once-cell (Task 5) is the same pattern AD-16 already names for "the OCR session" specifically, so this story isn't inventing a new architectural concept, just implementing one the spine already anticipated.
