### Group B — Multi-file queue and drag-and-drop (AC5)

14. **Given** the Images tool accepts no drop today, **when** this story ships, **then** the registry entry gains a `drop` declaration with `multiple: true` (mirroring PDF's `drop: { acceptedMimeTypes: ["application/pdf"], handler: "pdf_open_dropped", multiple: true }` shape from Story 8.8), and `DropZone.vue`/`dropZone.ts`'s existing `paths?: string[]` handling requires no shell-level change.
15. **Given** the shell always invokes a `drop` entry's declared `handler` directly with the full dropped path list (AD-14 — confirmed against `DropZone.vue`'s actual dispatch, not assumed), **when** files are dropped on the Images tool, **then** a new, small command (e.g. `image_ingest_dropped(paths) -> Vec<...>`) validates each path's size the same way `check_file_size` already does and returns a **per-file** outcome — one oversized or unreadable file must not fail the whole drop, unlike `pdf_open_dropped`'s current `?`-propagating shape, which this story deliberately does not copy (a considered divergence, not an oversight, since PDF's own shape would make one bad file blank the entire dropped batch).
16. **Given** files arriving via the native picker (`open({ multiple: true, filters: imageFilters() })`), **when** this story ships, **then** they join the same queue as dropped files through one shared code path — the picker and the drop are two arrival routes into one model, not two.
17. **Given** a populated queue, **when** any item fails at any stage (ingest, estimate, or convert), **then** that item's row shows its own error and every other item's processing continues unaffected — no single bad file empties or halts the batch.
18. **Given** the "Convert all" action, **when** it runs, **then** the user is asked once for a destination **folder** (not a per-file save dialog), each output file is written using the source's basename with the target extension, and a name that already exists in the destination gets an auto-appended numeric suffix (`photo.jpg`, `photo (2).jpg`) rather than a silent overwrite or an interrupting per-file prompt.
19. **Given** AD-16's rule (one runner per independent piece of state), **when** the redesign's queue replaces today's two flat runners (`runImageEstimate`, `runImageConvert`), **then** the scoping is re-derived rather than carried forward: **one runner instance per queue item** (not one shared runner per action-type), each driving that item's own convert action into its own reactive slot — reconverting item A can never supersede item B's in-flight result, and reconverting A a second time correctly supersedes A's own first attempt. *(Amended 2026-09-15, code review: the story's original text specified one shared runner per action-type — batch-estimate, batch-convert. That shape was ruled out during implementation and documented in the Dev Agent Record: `createLatestWinsRunner` is a single-slot primitive, so one shared instance across concurrently-dispatched items would make each item's completion supersede every other item's, which the "no single bad file empties or halts the batch" independence AC17 requires rules out. The per-item design was the correct call; this AC was left unamended at the time, which the review flagged — accepted and corrected here rather than reverting the implementation.)*

### Group C — Resize (new capability, AC6)

20. **Given** no resize capability exists today, **when** this story ships, **then** `image_convert.rs` gains a resize step taking explicit `(width, height)` pixel dimensions — **Option B from the design canvas, developer-confirmed**: the view shows two fields (width × height) with an aspect-lock toggle, locked by default. Locked, editing either field recomputes the other from the source's aspect ratio (view-side, AD-1); unlocked, both are independent and the core resize honors them exactly, including a non-uniform stretch. Either way, core always receives two explicit dimensions — it has no concept of "locked," that is purely the view's convenience.
21. **Given** the lock is on (the default) and the requested dimensions equal or exceed the source's own size, **when** conversion runs, **then** the image is not upscaled — resize is a no-op in that case, so quality is never degraded by stretching. **Given** the lock is off and the user has typed explicit width/height values larger than the source, **when** conversion runs, **then** the requested dimensions are honored exactly, including upscaling — an unlocked, explicit request is a deliberate user choice, not an accidental one, and this story does not second-guess it.
22. **Given** an invalid resize value (zero, negative, or non-numeric) in either field, **when** validated, **then** it is rejected with a new, specific `ToolError` code at the core layer (AD-1: core-layer-authoritative, mirroring `convert`'s own JPEG-quality range validation) — never silently clamped or ignored.

### Group D — Format and quality: AVIF and the background color (AC2, AC6)

23. **Given** `image` 0.25.9's default `avif`/`ravif` feature (already compiled in, zero `Cargo.toml` change), **when** this story ships, **then** `TargetFormat` gains an `Avif` variant using `AvifEncoder::new_with_speed_quality`, and — like JPEG, unlike PNG/WebP — `quality` (1-100) is validated and genuinely applied for AVIF, with the quality control shown whenever AVIF **or** JPEG is the selected target.
24. **Given** AVIF's decode side needs the separate, non-default `avif-native`/`dav1d` feature (a C library), **when** this story ships, **then** AVIF is added as a target **only** — the file picker's and drop's accepted-format filters are **not** extended to `.avif`, and this is stated in the tool's own format hint so the boundary is honest rather than discovered by a rejected file.
25. **Given** JPEG's hardcoded white alpha-flatten (`flatten_onto_white`), **when** this story ships, **then** it becomes `flatten_onto_background(image, color: [u8; 3])`, the view exposes a background-color control (a plain native `<input type="color">`, white by default — Option A from the design canvas), and the chosen color is threaded through to this parameter for every queued file (a batch-wide setting, not per-item).
26. **Given** the background-color control, **when** the selected target format is PNG or WebP (which carry alpha themselves and never flatten), **then** the control is hidden, matching the existing per-format conditional pattern the quality slider already uses.

### Group E — Before/after visual and completion feedback (deferred-work.md:154, gap #2/#3)

27. **Given** a queued item finishes converting, **when** its result is shown, **then** its row shows a thumbnail, both byte counts, and a percentage-saved figure, plus a "Compare" affordance that opens a slider/wipe comparison over the full original vs. converted image (**Option B from the design canvas, developer-confirmed**) — the app's first drag-to-compare interaction primitive.
27a. **Given** Option B is a genuinely new interaction primitive and NFR5 admits no exceptions, **when** the compare view is built, **then** it has a keyboard-operable equivalent (e.g. arrow keys move the divider once it has focus) — dragging is never the only way to move it — **and** the byte counts and percentage-saved figure stated in AC27 are always visible on the row itself, without requiring the compare view to be opened at all.
28. **Given** an item is currently converting, **when** it is in flight, **then** its row shows an announced (`role="status"`) in-flight indicator — not just disabled controls — closing the gap the shipped tool has today (Convert has in-flight feedback for the live estimate but not for the write itself).
29. **Given** the batch completes, **when** every item has settled (done or errored), **then** a summary state is shown (e.g. "3 of 4 converted") and announced once, rather than each item's completion being the only signal.

### Group F — EXIF/GPS: a claim, not a mechanism (AC6, a genuine free find)

30. **Given** this story's live verification that `image_convert.rs`'s `convert()` already discards all EXIF/GPS metadata as a side effect of the `image` crate's decode/encode round-trip (no code change — `image::load_from_memory` never populates an EXIF field, and neither `JpegEncoder` nor the WebP encoder's `exif` field is ever set), **when** this story ships, **then** a regression test locks this in across all shipped target formats (a source image carrying real EXIF/GPS bytes → the converted output has none), and the tool states this honestly in its own copy as a privacy property, not a silent accident.

### Group G — i18n, error voice, and accessibility

31. **Given** Story 8.6's own criterion for `TRANSLATABLE_CODES` ("a fixed, value-free sentence we wrote ourselves"), **when** this story's new `image-*` codes are reviewed against it, **then** each gets an explicit per-code call — folded in only where the message is genuinely ours to translate, not a blanket add (most `image-*` codes wrap the `image` crate's or a background task's own text, the same shape 8.7 found for OCR).
32. **Given** every new user-visible string this story adds (resize label, background-color label, before/after copy, queue-status text, the AVIF-is-output-only hint), **when** it ships, **then** `en` and `fr` both gain it in the same commit (AD-13).
33. **Given** NFR5's no-exceptions keyboard rule, **when** the queue, its per-item remove/retry affordances, and the resize/background controls are built, **then** every one of them is operable by keyboard alone, matching every prior Epic 8 tool's own floor.
