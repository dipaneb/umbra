# Story 7.4: Sidebar gets an active-nav state and token styling

Status: ready-for-dev

## Story

As a privacy-conscious developer,
I want the sidebar to show which tool is currently open and to look like the rest of the app,
so that I always know where I am and the app reads as one coherent product.

## Acceptance Criteria

1. Given the sidebar (`AppSidebar.vue`), When rendered, Then it consumes Story 7.1's tokens (Geist type, spacing, `border-hairline`) and Story 7.1's icon system, replacing the current hardcoded hex values (`#e0e0e0`, `#396cd8`) and raw emoji.
2. Given a tool is open, When its sidebar entry is compared to the others, Then it shows the active-state background tint (`accent-signature-tint` light / dark) per `DESIGN.md`'s Nav item component — exactly one item active at a time.
3. Given the active item, When inspected by assistive tech, Then it exposes its current state via an `aria-current`-style attribute, not just the visual tint — closing the gap flagged in Story 1.5's own deferred-work entry (2026-07-24: "No visual indicator of the currently active tool in the sidebar").
4. Given a non-active item, When hovered, Then it shows a neutral (non-orange) hover affordance — orange stays reserved for the active state per `DESIGN.md`'s "budget of one" rule.
5. Given the sidebar's collapse behavior (`EXPERIENCE.md` IA table: "Collapses to icons"), When collapsed, Then each item retains its full accessible name via a visually-hidden label or equivalent; the collapse control is keyboard-operable and its state persists through a new `shell.sidebarCollapsed` key in the `settings` store (AD-10).
6. Given the Settings link at the bottom of the sidebar, When Story 7.7 lands the update-signal, Then this story's markup provides the anchor point it attaches to; this story does not itself implement the dot.

**Not covered by this story:** the pinned/recent grouping — Story 7.5.

  - [ ] Style `a.router-link-exact-active` (the exact-match class — not the looser `router-link-active`, which also matches ancestor-path routes and would break "exactly one item active at a time" if routes ever nest) with `background: var(--color-accent-signature-tint);` and the label text color per Task's next bullet.

Use `color: var(--color-accent-signature-on-text, var(--color-accent-signature));` — the CSS `var()` fallback resolves to `--color-accent-signature` (which *is* the AA-safe dark-mode value) whenever `-on-text` is undefined, giving the correct color in both themes from one rule.

AC2/AC3's literal wording is tool-scoped, but this is a same-pattern, zero-marginal-cost extension — record it as a deliberate scope decision in Dev Notes, not a silent addition.

## Dev Notes

- **Architecture fit:** Pure frontend, presentation-layer change plus one `settings` store addition. AD-10 (`ARCHITECTURE-SPINE.md`) — `sidebarCollapsed` is namespaced `shell.*` and written only through the `settings` Pinia store, the sole writer of `settings.json`; no Rust-side changes. AD-5 — the sidebar still reads `registry.tools` only, nothing enumerates tools independently; this story changes styling/interactivity around that existing read, not the read itself. No `src-tauri/` changes, no new dependency (reuses `@phosphor-icons/vue`, already installed since Story 7.1, and `vue-router`'s already-in-place `RouterLink`).
- **The single highest-value finding in this story: don't build what vue-router already gives you for free.** Verified directly against the installed `vue-router` (`^5.2.0`) source via Context7: a plain `<RouterLink :to="tool.route">` — the form already in `AppSidebar.vue`, unchanged by this story — automatically applies `router-link-exact-active`/`router-link-active` classes AND renders `aria-current="page"` on the exact-active link, with zero JS. AC3 ("exposes its current state via an `aria-current`-style attribute") is satisfied by *not* switching to `GridHome.vue`'s `custom v-slot` wrapper pattern (which replaces the rendered `<a>` and would need `aria-current` re-added by hand) — the two stories have opposite risk shapes on this exact point.
- **The dark-mode `accent-signature-on-text` gap is the second real risk**, same "token defined in only one theme block" shape Story 7.2's Dev Notes already warned is a recurring gotcha class in this codebase. `--color-accent-signature-on-text` exists only under `:root[data-theme="light"]` (confirmed by reading `tokens.css` directly) — a naive `color: var(--color-accent-signature-on-text)` on the active nav label would silently fall back to the inherited text color in dark mode instead of orange. Fix: `var(--color-accent-signature-on-text, var(--color-accent-signature))`, letting the CSS fallback do the theme-branching in one declaration.
- **Three tokens/values in this story are open decisions with no `DESIGN.md`/`EXPERIENCE.md`-specified value** — resolved here with reasoning, not silently invented, so a future reader can find the "why": the focus-ring color (`--color-accent-signature`, closing a value Story 7.3's code review already deferred by name against this exact file), the neutral hover background (`--color-bg-surface-raised`), and the nav-label typography role (`--font-label-*`, inferred from its "compact UI chrome" role versus `--font-body-*`'s prose role). None of these invent a new CSS custom property — all reuse tokens Story 7.1/7.2 already defined.
- **Existing code to extend, not replace** (confirmed by direct reads):
  - `src/shell/AppSidebar.vue` — current structure (`useRegistryStore()`, `v-for="tool in registry.tools"`, plain `<RouterLink :to="tool.route">`, `resolveIcon(tool.icon)`) stays; this story restyles it and adds the collapse button, it does not restructure the loop or the routing mechanism.
  - `src/stores/settings.ts` — `restoreEnabled`'s exact shape (plain boolean, `?? default` on read, mirrored setter, reset in `clearAll`) is the direct template for `sidebarCollapsed` — closer to it than to `themeOverride`'s union-validated shape.
  - `src/shell/icons.ts` — `resolveIcon`/`IconName` stays scoped to the 7 registry tool ids exactly as documented; the Settings-gear and collapse-toggle icons are sourced by importing directly from `@phosphor-icons/vue` in `AppSidebar.vue`, not by extending `IconName`'s closed union for non-tool icons.
  - `src/shell/SettingsView.vue` — untouched by this story; `sidebarCollapsed` appears under its existing generic "Persisted data" enumeration automatically, confirmed by reading the component directly (Task 1).
- **From Story 7.1/7.2/7.3 (done, direct prerequisites):** 7.1 built the token layer and icon resolver, explicitly deferring the Settings-gear-emoji fix to this story by name in its own Dev Notes. 7.2 built the `[data-theme]` mechanism both light/dark token blocks resolve against, and flagged the "token defined but not actually applied is a silent no-op" gotcha class this story hits again (the `accent-signature-on-text` gap above). 7.3 established the "verify the real interactive mechanism directly, don't assume a wrapper preserves default browser/router semantics" lesson — this story's finding is the mirror image: the *default* `RouterLink`, left alone, is what actually satisfies AC3, and a wrapper would be the regression.
- **`review-accessibility.md` (a UX-phase adversarial review, not this story's own) already named the exact real risk Task 4 exists to close**: "the IA section's icon-collapsed sidebar is never reconciled with the... every control has a screen-reader label... icon-only collapsed nav is one of the most common real-world screen-reader traps." `epics.md`'s AC5 text already resolves this at the requirements level (explicit visually-hidden-label requirement); this story is where that resolution actually gets implemented.
- **Explicitly out of scope:** the pinned/recent grouping (Story 7.5, named directly in the epics text); `CommandPalette.vue`'s identical hardcoded `#396cd8` (a separate, still-untokenized component — not named by AC1, which scopes to `AppSidebar.vue` only); the update-signal dot itself (Story 7.7 — this story only needs to leave the Settings link's markup as a stable anchor point, which it already is as a normal `RouterLink`, no extra work required); any Settings-pane UI for the collapse toggle (the control lives in the sidebar itself, per `EXPERIENCE.md`'s "state persists via `settings` store" — a `settings` store key, not a `SettingsView.vue` control, mirroring how `windowGeometry` is store-only with no Settings UI either).
