# Story 6.1: Work PDFs locally — merge, split, extract

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want to merge, split, and extract text from PDFs entirely on-device,
so that client documents never touch an online PDF service.

## Acceptance Criteria

1. **Given** multiple PDFs dropped into the Bucket, **when** I choose Merge, **then** a single merged PDF is produced in my chosen order and saved via the shared save helper (FR27, AD-15).
2. **Given** a dropped PDF, **when** I specify a page range to split or extract, **then** a new PDF containing exactly those pages is produced (FR27), **and** an out-of-bounds range yields a structured inline error.
3. **Given** a dropped PDF with extractable text, **when** I choose Extract text, **then** the text displays editable with one-click copy (FR27, FR4).
4. **Given** the implementation, **when** inspected, **then** PDF operations live in a new `umbra-core` module behind async commands (AD-1, AD-3), the crate choice (candidate: `lopdf`) is verified current at story start and license-checked for compatibility with an All-Rights-Reserved app, and it compiles on all three platforms (AD-11).
5. **Given** a corrupt or encrypted PDF, **when** an operation is attempted, **then** a structured `ToolError` explains the failure — never a crash (NFR4).

**Interpretation notes, recorded explicitly rather than left implicit:**
- AC2's "split or extract" is one operation, not two: producing a new PDF containing exactly the specified page range. It does not mean "cut the source into two output files" — no AC asks for that.
- AC1/AC2/AC3 all say "dropped." This story deliberately does **not** wire PDF input through the shell's existing AD-14 window-level drop dispatcher — see Dev Notes' "Why PDF input bypasses the AD-14 drop dispatcher" for the concrete reason and the (already-approved, already-used) mechanism used instead. This is a scope decision this story makes and records, the same way Story 5.2 recorded its "no manual Check for Updates button" decision — it is not a silent reinterpretation.

No previous same-epic story exists; per the Epic 5 retrospective's "Epic 6 Preview" section (`_bmad-output/implementation-artifacts/epic-5-retro-2026-08-10.md:58-70`), Epic 6 has **no code-level dependency on Epic 5** and **no unresolved blockers** — the only carryover is that `lopdf`'s version/license must be live-re-verified at this story's start (done — see Dev Notes), which the retrospective explicitly anticipated by name.

### Review Findings

- [x] [Review][Decision] Merge silently drops per-document Catalog/Pages metadata and inherited page attributes — Merging PDFs collapses each source document's `Catalog` into whichever is processed last (`crates/umbra-core/src/pdf.rs:88-95`), silently discarding `AcroForm` (form fields), `StructTreeRoot` (accessibility/tagged structure), `ViewerPreferences`, and `/Info` metadata from every input but the last-processed one. Separately, individual `Page` dictionaries are reparented directly onto a new flattened `Pages` root (`pdf.rs:135-143`) without first materializing any attributes (`MediaBox`, `Resources`, `Rotate`, `CropBox`) a page may have been inheriting from an intermediate `Pages` node in its source document rather than declaring explicitly — such pages can lose correct rendering attributes after merge. AC1 only requires "a single merged PDF... in my chosen order," which this satisfies for page content and order (verified: page ordering itself is correct — `lopdf`'s own `renumber_objects_with` explicitly detects and fixes page-traversal order before assigning object IDs, confirmed against the vendored source at `processor.rs:165-220` — so this is not a page-order bug), but AC1 says nothing about metadata/accessibility/inherited-attribute fidelity. **Resolved 2026-08-10:** documented as a known v1 limitation, not fixed — see Dev Notes.
- [x] [Review][Patch] "Add PDFs…" stays enabled during an in-flight merge and the success handler unconditionally clears the live list, silently dropping files added mid-merge [src/tools/bucket/BucketView.vue:93-98,120-137,263-268] — fixed: "Add PDFs…" now disabled while `pdfMerging` is true.

## Dev Notes

- **Why PDF input bypasses the AD-14 window-level drop dispatcher entirely — a real gap worth understanding, not working around silently.** `src/shell/DropZone.vue`'s drop handler (`onMounted`'s `onDragDropEvent` callback) only ever forwards `routing.paths![0]` — the *first* path — to the tool's single registry-declared `drop.handler`, even when an OS drag delivers multiple paths in one gesture (`event.payload.paths` can already be an array; the dispatcher discards everything past index 0). Separately, a tool's registry entry declares exactly **one** fixed drop-handler command name (AD-5/AD-14) — there's no way for "drop a PDF" and "drop an image" while the Bucket is active to route to two different commands, and Merge inherently needs several files at once while Split/Extract needs a page-range parameter the AC's own wording ("I specify a page range") implies is supplied as a distinct step, not inferred from a bare drop event. None of the three PDF operations fit the "one drop event instantly triggers one fixed one-shot command" shape every existing drop handler (`base64_encode_file`, `hash_compute_file`, `bucket_extract_text`) already assumes. Extending AD-14 itself (e.g. a new `multi: boolean` registry field, changing the dispatcher to forward all paths) would be a real, system-wide architecture change affecting every tool's drop contract — out of proportion to what this one story needs. **This story's decision:** use `@tauri-apps/plugin-dialog`'s `open()` (multi-select for Merge, single-select for Split/Extract and Extract-text) instead — an already-approved, already-used dependency (`Base64View.vue` already imports `save` from the same package) that natively supports exactly what's needed with zero AD-14 changes and zero risk to the five other tools that already depend on the drop dispatcher's current single-path contract. Window-level drag-and-drop of a PDF onto the Bucket while its *existing* OCR drop-zone is showing will still route to `bucket_extract_text`, which will honestly fail with `bucket-unsupported-format` (`image::load_from_memory` can't decode a PDF) — an acceptable, already-correct NFR4 outcome (never silently wrong), not a gap this story needs to close.
- **AD-16 runner scoping — this is the second real instance of the exact shape the spine's own amendment describes, after `CronView.vue`.** The amendment at `ARCHITECTURE-SPINE.md:135-146` distinguishes "one runner per independent piece of state" (a tool-wide `registry.getLatestWinsRunner(toolId)`, `HashView.vue`'s shape — multiple triggers, one shared state) from "multiple genuinely independent state-groups in one view" (local per-group runners, `CronView.vue`'s shape). Bucket's OCR section already uses the registry-scoped runner (`outcome`/`error`, shared between drop and clipboard-paste per Story 4.2). The new PDF section writes to entirely different state and is triggered by explicit button clicks, never by drop/paste — it is a second, disjoint state group in the same view, so it needs its **own** local runner(s), not the registry-scoped one. Getting this wrong (e.g. accidentally sharing the OCR runner) would mean triggering a PDF operation could spuriously mark an in-flight OCR extraction as "superseded," or vice versa — two operations that have nothing to do with each other silently canceling one another.
- **AD-15 is the sharpest way to get this story visibly wrong.** The natural-looking implementation — a command that returns the merged/extracted PDF's bytes as `Vec<u8>` over IPC, with the frontend writing them to disk — directly violates "byte arrays > ~64KB never ride the JSON IPC bridge" (`ARCHITECTURE-SPINE.md:133-134`). `base64_decode_to_file` (`src-tauri/src/commands/base64.rs:63-71`) is the exact existing precedent: the command takes the destination path (obtained via the frontend's own `save()` call) and writes server-side via `fs_helper::write_file_bytes`, returning `Result<(), ToolError>`. Task 3 follows this precedent exactly for `bucket_merge_pdfs`/`bucket_extract_pdf_pages`.
- **No `umbra-core` module needs a filesystem touch.** `pdf.rs`'s three functions take/return in-memory bytes only (`Vec<u8>`/`&[u8]`/`String`) — all path resolution, reading, and writing stays in `src-tauri`'s command layer, per AD-2/AD-15 (core never touches the filesystem).
- **No registry/AD-5 changes required.** The `bucket` tool registry entry (`src/stores/registry.ts`) keeps its existing `drop`/`paste` declarations untouched — PDF operations are new commands the Bucket tool exposes, invoked directly via `invoke()` from the view (same pattern `Base64View.vue`'s manual Encode/Decode buttons already use), not new drop/paste surface. Task 6's alias addition is cosmetic (⌘K findability) and doesn't touch `drop`/`paste`.
- **Known v1 limitation, recorded explicitly per code review (2026-08-10): merge does not preserve per-document Catalog/Pages metadata.** `merge_documents` keeps only the last-processed source document's `Catalog` fields — `AcroForm` (fillable form fields), `StructTreeRoot` (accessibility/tagged-PDF structure), and `ViewerPreferences` from every other input are silently discarded, not merged. The output document has no `/Info` dictionary, so title/author/producer metadata from all inputs is lost. Individual pages are reparented onto a new flattened `Pages` root without materializing any attributes (`MediaBox`, `Resources`, `Rotate`, `CropBox`) they may have been inheriting from an intermediate `Pages` node rather than declaring explicitly, so such pages can lose correct rendering attributes after merge. Page content and order themselves are unaffected (verified against `lopdf`'s vendored `renumber_objects_with` source). Deliberately not fixed in this story — accepted as a documented v1 gap rather than scope creep; a future story can address it if it proves to matter in practice (e.g. materializing inherited attributes before flattening, preserving the first document's `/Info`).
- **No new persisted state.** Nothing here needs `AD-10`/`settings.json` — merge order, staged file lists, and page-range inputs are all transient, in-memory, per-session UI state, same as every other tool's working-input state in this codebase.
- **Testing:** this is the first story to add a new `umbra-core` module *and* a new `src-tauri/src/commands/` file since Epic 4 — follow `ocr.rs`'s real-fixture-over-mocks convention for the core layer, and `base64.rs`'s (not `bucket.rs`'s) simpler direct-call test shape for the command layer, since none of these three commands need an `AppHandle`.
