# Story 8.3: Reimagine the UUID Generator

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the developer,
I want to reconsider the UUID Generator's feature set through open discovery before redesigning its UI,
so that the redesign reflects a deliberately chosen scope, not a visual reskin of whatever shipped first.

## Acceptance Criteria

**This story ships in two gated tasks (epics.md's own shared Epic 8 shape). Task 1's ACs below are real and testable now. Task 2 (redesign) has no ACs yet — writing them before Task 1's decision record exists would be fiction, per epics.md's explicit instruction — they are added to this story file as a follow-up edit (Task 2a) once Task 1 completes, exactly as Stories 8.1 and 8.2 did.**

1. **Given** open scope discovery is run for the UUID tool (`bmad-party-mode` or `bmad-forge-idea` — the developer chooses which for this story; a second, narrower pass may follow), framed explicitly as reconsidering the tool's scope from first principles, **when** discovery concludes, **then** a written decision record exists stating what is kept, cut, and added relative to today's shipped implementation (generate UUID **v4** and **v7**, single or bulk up to **1000**; per-row one-click copy and Copy-all newline-joined; version radio that clears a stale result on switch; a client-side input-shape guard plus server-side `uuid-count-zero` / `uuid-count-too-large` rejections; v7 batch monotonicity via a shared `ContextV7`), with rationale for each call — the existing implementation is reference only, not a decision to preserve by default.
2. **Given** the decision record, **when** it is produced, **then** it states whether **FR13** remains accurate, is revised, or is expanded — Epic 8's own preamble makes this revision each story's own output, not predicted in advance.
3. **Given** any idea considered and cut during discovery, **when** the decision record lands, **then** it is captured as a public backlog candidate (FR35) — filed as an individual, max-context GitHub issue on `dipaneb/umbra` with the `backlog-candidate` label per this project's idea-capture convention (cf. issues #113–#116), each linking back to the decision record — not folded into a PRD rewrite and not silently dropped.
4. **Given** the chosen scope, **when** the decision record completes, **then** it states which parts of the existing `crates/umbra-core/src/uuid.rs` functional core survive as-is (AD-1: core owns every transformation) versus which need new pure functions, **and** whether the `src-tauri/src/commands/uuid.rs` wrapper layer changes, **and** whether `src/tools/uuid/uuidVersion.ts` (the hand-synced TS mirror of the Rust `UuidVersion` enum) and `crates/umbra-core/Cargo.toml`'s `uuid` feature set change — Task 2 builds directly on this split.
5. **Given** Task 1 has not yet produced its decision record, **when** this story starts, **then** Task 2 (redesign, and its own Given/When/Then acceptance criteria) has not begun — no implementation starts before the decision record exists.

Numbering continues from AC5. **Pending the developer's sign-off before Task 2b.**_

6. **Container — enriched toolbar.** **Given** the redesigned UUID view, **when** it renders, **then** it is a single enriched view (no `AppTabs.vue`, no tabs); generation controls (version selector, count field, Generate) sit in one horizontal control strip above the results panel; and output-scoped controls (format control, Copy all, Download) sit in the results-panel header — not with the generation controls.

7. **Epic-7 tokenisation pass.** **Given** `UuidView.vue` is currently 100% pre-Epic-7, **when** the redesign lands, **then** no hardcoded design value remains: `p[role="alert"]`'s `#b00020` → `var(--color-accent-destructive)` (matching `JsonView.vue` / `Base64View.vue`); the result strings render with `--font-code-*`; every layout margin, gap and radius uses `--spacing-*` / `--radius-*`; and styling `src/styles/base.css` already provides for the bare number-input (border, focus-visible ring) is not re-declared.

8. **Version selector with inline taglines.** **Given** the version selector, **when** it renders, **then** each option carries an always-visible tagline — `v4 · random`, `v7 · time-ordered` — with no hover dependency; the control keeps radio semantics for assistive tech and full keyboard operability even if it is visually a segmented control (the `Base64View.vue` direction-switch pattern: real radios in the DOM, visually collapsed, never `display:none`).

9. **`?` explainer opens a Popover.** **Given** a `?` trigger on the version fieldset **legend** (one on the legend, not one per option), **when** the user activates it by pointer or keyboard, **then** a floating surface opens with the "when do I pick v4 vs v7" comparison; `Esc` and an outside click both dismiss it; focus returns to the `?` trigger on close; it is positioned relative to its trigger; and it is styled with DESIGN.md's `floating-surface` tokens, explicitly checked in **light and dark** at a render review (the dark value is a rim-glow, not a drop-shadow — the standing `[ASSUMPTION]`). **[Amended 2026-08-31, code review]** *"focus returns to the `?` trigger on close"* is met for the `Esc` and re-activation paths; on **outside-click** dismissal focus is left where the click landed, per the WAI-ARIA APG for a non-modal popover (`AppPopover` calls `close({ returnFocus: false })` there). The light + dark `--shadow-floating` check on the real surface is **not** done in this story — deferred to the developer's own render-review (see `deferred-work.md`, 2026-08-31); the Popover landed in **slice 3**, not slice 1.

10. **`Popover.vue` is a reusable component whose API is signed off first.** **Given** `Popover.vue` is the app's first floating surface and shared UI, **when** Task 2b starts, **then** its public API and interaction contract have first been **presented to the developer as options with trade-offs and signed off** (per `CLAUDE.md`'s "new shared UI doesn't inherit governance automatically" rule — trigger model, content as slot vs. prop, fixed side vs. auto-flip, popover-only vs. general floating-surface scope); it lives in `src/components/` beside `AppButton.vue` / `AppTabs.vue`; it ships with its own `src/components/Popover.spec.ts`; the version `?` is its first consumer wired in this story; and **no other tool's files are modified** to adopt it here (AD-6). **[Amended 2026-08-31, code review]** the redesign wires a **second** consumer inside `UuidView.vue` — the Download format menu (`AppPopover` with a `.txt`/`.csv`/`.json` list) — accepted as sound reuse of the same shared component; the original *"first and only consumer"* wording is superseded. Still true: no *other tool's* files were touched.

11. **Format affordance — case segmented + two chips, composing.** **Given** the results-panel header when results exist, **when** the format control renders, **then** it is a two-option **case segmented control** (`lowercase` / `UPPERCASE`, mutually exclusive) **plus** two independent toggle chips (`{braces}`, `no hyphens`); the chips compose with the case choice and with each other (e.g. `UPPERCASE` + `{braces}` is expressible); and toggling any of them **re-renders the existing results in place with no new `uuid_generate` call** — generation and formatting are separate.

12. **Formatting is a view-side transform only (AD-1).** **Given** AD-1, **when** any format option is applied, **then** it is a pure `String` transform inside `UuidView.vue` over `umbra-core`'s canonical lowercase-hyphenated output; `crates/umbra-core/src/uuid.rs`, `src/tools/uuid/uuidVersion.ts` and `crates/umbra-core/Cargo.toml`'s `uuid` feature set are all unchanged; and Copy, Copy all and Download every one emit the **currently-formatted** strings, never the canonical form.

13. **Per-row copy restyled to the icon-button pattern.** **Given** the results list, **when** it renders, **then** per-row Copy is the ~24 px icon-button + `useCopyFeedback` pattern (`JsonTree.vue` / `Base64View.vue`): signature-accent "copied" state, **no** separate success colour; `useCopyFeedback` is imported from `src/tools/json/useCopyFeedback` carrying the existing hoist-candidate comment (the hoist to `src/shell/` is **not** done in this story — island discipline); and every copy control has a screen-reader label.

14. **Bulk download — `.txt` / `.csv` / `.json`.** **Given** generated results, **when** the user activates Download and chooses a format, **then** the current (formatted) list is written to a user-chosen path via `@tauri-apps/plugin-dialog`'s `save` (default filename + matching extension) and a **new `uuid_export` command** that routes to `fs_helper::write_file_bytes` (AD-15, atomic temp-then-rename) on `spawn_blocking` (AD-4) returning `Result<(), ToolError>` (AD-3); `.txt` = newline-joined; `.csv` = a single RFC-4180-quoted `uuid` column with a header row; `.json` = a JSON array of strings; `crates/umbra-core/` is untouched; a cancelled save dialog is **not** an error; and a write failure renders inline from `file-write-error`'s structured shape (never by parsing its message).

15. **Deferred-work items folded in, not re-deferred.** **Given** `deferred-work.md` lines 74–82, **when** the redesign lands, **then** a successful batch render is announced to assistive tech via `role="status"` / `aria-live="polite"`; the Generate control is disabled while a generation is in flight (no stacked `spawn_blocking` tasks from rapid clicks); and the hardcoded alert colour is tokenised (via AC7). The remaining app-wide items in that block (unguarded concurrent Copy/Copy-all, the `CommandPalette.spec.ts` ordering coupling) stay deferred and are noted as still-open in the Change Log. **[Amended 2026-08-31, code review]** those two items remain deferred and unaddressed by this story — see the Change Log row dated 2026-08-31 (code review) and `deferred-work.md`.

16. **Preserved behaviour + structure-forced test rewrites.** **Given** the existing suites, **when** the redesign lands, **then** all of the following are unchanged: v4 per-element `Uuid::new_v4()`; v7 one shared `ContextV7` strictly-increasing batch; the client-side input-shape guard as distinct from the server 1000 cap; 0 and `1..=u32::MAX` round-tripping to the server; `uuid-count-zero` rendering its **translated** string while `uuid-count-too-large` renders its raw structured message; version-switch clearing a stale result; a stale in-flight response discarded after a version change; **one** shared `createLatestWinsRunner()` backing generate + both copies + download; and all **8** `crates/umbra-core/src/uuid.rs` tests and all **5** `src-tauri/src/commands/uuid.rs` tests passing unmodified. `UuidView.spec.ts` assertions that break **only** because the DOM changed (the `.results li` selector, button-by-text lookups, the `input[type="radio"][value="v7"]` selector) are rewritten against the new structure and each such rewrite is called out as **structure-forced, not behavioural** (8.2 AC14 precedent); the behavioural assertions (invoke args, translated-vs-raw error text, newline-joined Copy all, stale-response discard, client guard never calling `invoke`) are preserved.

17. **i18n.** **Given** the new strings (taglines, case/chip labels, Download + the three format names, the results-count announcement, the `?` explainer body), **when** they are added, **then** they land in **both** `src/locales/en.json` and `src/locales/fr.json` under `tools.uuid.*`; `src/locales/locales.spec.ts` passes (every string through vue-i18n's real compiler); any literal `{` / `}` shown as UUID brace syntax uses the `{'{'}` / `{'}'}` escape; and `src/shell/toolError.ts`'s `TRANSLATABLE_CODES` is **not** extended — this story introduces no new `umbra-core` error code (the only new command, `uuid_export`, surfaces the pre-existing `file-write-error`).

18. **Format persistence — minimal persisted `uuid.*` setting (AD-10; "B1", developer's call 2026-08-31).** **Given** AD-10 and the developer's Task 2a call to persist the format at minimal depth, **when** the redesign lands, **then** the chosen output format (case + `{braces}` + `no hyphens`) is written to the `settings` Pinia store — the single writer for `settings.json` (AD-10) — under `uuid.*`-namespaced keys (`uuid.formatCase`: `"lower" | "upper"`, `uuid.formatBraces`: bool, `uuid.formatHyphens`: bool), **each with an entry in the store's single-source `DEFAULTS` map** so `init()`'s absent-key fallback, `clearAll()` and `resetKey()` all cover it automatically; the format is read from the store on view mount and written back on change (an immediate `set` + `save`, matching the store's other discrete-value setters — `setThemeOverride`, `setLocale`, `setDateTimeFormat` … — which are **not** debounced; only `writeGeometry` is; **[Amended 2026-08-31, code review]** the earlier *"debounced, like the store's other writers"* wording was inaccurate about the codebase); default = `lower` / braces `false` / hyphens `true` (today's canonical output — an existing user sees no change until they opt in); and the three keys therefore appear, with their per-key **Reset**, in `SettingsView.vue`'s existing "stored data" list with **no new Settings section and no `SettingsView.vue` layout change** (a dedicated tool-owned settings group — "B2" — was explicitly declined: it would be the app's first tool-contributed settings section, a new shared-shell pattern out of scope for 8.3). Version and count are **not** persisted (count is inherently per-task). `uuid.*` is the first non-`shell.` namespace in the store — a deliberate, minimal extension of an existing shared file, not a new mechanism.

Summary: a genuinely small tool — one Vue view (~230 lines) with two controls (v4/v7 radio, count number-input), a `generate(version, count)` pure fn in core with a 1000 cap and two error codes, one thin `spawn_blocking` command, and a 6-key i18n block. Nothing about it is drop-capable, clipboard-suggestion-shaped, or file-touching.

- **FR mapping. FR13** — "Generate UUIDs v4 and v7, single or in bulk (up to 1000), with one-click copy." - **Discrepancies / gotchas found this session — carry into Task 1/2, do not "fix" reflexively:**
  1. **`UuidView.vue`'s `MAX_COUNT = 4294967295` is a client-side *input-shape* guard, not the business cap.** Its comment ("mirrors umbra-core's u32 command parameter") is about the *serialization* ceiling, not core's `MAX_COUNT: u32 = 1000` business rule. The split is deliberate: the client rejects only what can't round-trip cleanly (non-integer, negative, > u32::MAX); 0 and 1..=u32::MAX go to the server, which owns the 1000 rejection. If Task 1 changes the cap or moves it, that's a decision to record, not a silent refactor.
  2. **`countOutOfRange` is a plain `t()` call in the view**, not a `ToolError` path — correctly **not** in `TRANSLATABLE_CODES`. Only Rust-originated `ToolError.code`s belong in that set.
  3. **`uuidVersion.ts` must stay hand-synced** with the Rust `UuidVersion` enum's snake_case encoding. Any version added in Task 2 changes the Rust enum, the `Cargo.toml` `uuid` features, *and* this TS mirror — AC4 calls this out.
  4. **The registry entry has no `clipboardMatch`.** UUID generates; it doesn't parse an existing value. If Task 1 proposes an "inspect/validate a pasted UUID" capability (version + variant + embedded timestamp for v1/v6/v7), that is deterministic parsing (no AD-9/AD-13 "guess" exception needed) — but adding a `clipboardMatch` to the registry entry for Story 7.8's clipboard-suggestion surface is a **shell concern** (AD-6): present it as options with trade-offs, don't decide it silently inside this story.
  5. **`deferred-work.md` lines 74–82 already log 7 code-review items from Story 2.3's review against `UuidView.vue`** — several app-wide (no `aria-live`/`role="status"` on a successful batch render; no in-flight disable on Generate so rapid clicks stack `spawn_blocking` tasks; unguarded concurrent Copy / Copy-all). Task 2 should **fold the UUID-specific ones in rather than re-deferring**; the tokenization pass directly covers the hardcoded `#b00020` alert-colour item (line 77). Re-read that file's UUID block before Task 2b.

- **Architecture boundaries Task 1 must scope against and Task 2 must obey:**
  - **AD-1** — every transformation is a pure function in `umbra-core::uuid`; the view renders. **Presentation formatting is view-owned, never core.** This is load-bearing here: the likeliest "Added" candidates — uppercase, `{braces}`, `urn:uuid:` prefix, hyphenless — are *view-side string transforms on core's canonical lowercase-hyphenated output*, **not** new core functions. Core returns the canonical form; the view formats it. Only genuinely new *generation* logic (more versions, v3/v5 namespace hashing, a UUID *parser*) is new core work.
  - **AD-3** — every command returns `Result<T, ToolError>`; the view renders from `ToolError` structure only (`code`, `position`), never by parsing `message`. Commands are `uuid_<verb>`.
  - **AD-4** — anything that can exceed ~100 ms CPU runs on the blocking pool via `spawn_blocking` (`uuid_generate` already does). A materially larger bulk cap would also need a **virtualized result list** — `@tanstack/vue-virtual` is already a dependency (the JSON tree uses it); don't add a second virtualization lib.
  - **AD-6** — tools are islands. Do not touch another tool's files. Cross-cutting state lives only in the `settings` / `registry` Pinia stores; a new `clipboardMatch` is a registry-shape change (see gotcha 4).
  - **AD-9 / AD-13 honesty** — UUID has no natural-language grammar and no heuristic "guess" today, so no AD-13-style disclosed exception is needed and French rides the existing `vue-i18n` seam like every other tool. A UUID *inspector* (parse → version/variant/timestamp) is deterministic, not a guess — still no exception, but any "this looks like a UUID but isn't quite" state must be a precise inline error per EXPERIENCE.md's honesty bar, not a confident wrong reading.
  - **AD-10** — if Task 2 adds a persisted preference (default version, default count, default output format), it is a `uuid.*`-namespaced key in the `settings` store, enumerated and individually clearable in the sectioned Settings pane (Story 7.6), in addition to the INV-3 all-clear.
  - **AD-16** — one `createLatestWinsRunner()` per *independent* piece of state. Today one shared runner backs generate + both copies (all write `results` / `error`), which is correct as-is. If Task 2 splits the tool into genuinely independent panels (e.g. a Generate panel and an independent Inspect panel), scope **one runner per group** — `CronView.vue`'s two-section split is the cautionary precedent (a tool-wide runner falsely supersedes an unrelated section); `HashView.vue`'s `registry.getLatestWinsRunner(toolId)` is the reference when a drop plus an in-view invoke write the same surface (UUID has no drop, so this is unlikely to apply).
  - **AD-2 / AD-11** — `umbra-core` imports no `tauri` crate and has zero `#[cfg(target_os)]`; CI runs `cargo test --workspace` on all three OSes. Any new `uuid` feature flag must build clean cross-platform.

- **Dependency note (standing verification discipline — Consistency Conventions table).** `uuid` is pinned `1.24` in `crates/umbra-core/Cargo.toml` (`features = ["v4", "v7", "std"]`), resolved `1.24.0` in `Cargo.lock`. Verified current this session via Context7 (`/uuid-rs/uuid`, docs reference `version = "1.24"`). Post-1.0, stable. The crate supports **v1, v3, v4, v5, v6, v7, v8** — each behind its own Cargo feature — plus `Uuid::nil()` and `Uuid::max()` constants. If Task 1 decides to add versions:
  - **v6** (reordered-v1, sortable) and **v1** (timestamp + 6-byte node id) need a `ContextV1` and a node-id decision (random vs. fixed) — a small config surface, not a new UI shape.
  - **v3** (MD5) and **v5** (SHA-1) are deterministic namespace+name hashes — they need **two text inputs (namespace + name)** and a namespace picker (`NAMESPACE_DNS`/`URL`/`OID`/`X500` or a custom UUID), a genuinely different UI shape from the current radio+count, not just another radio.
  - **v8** is free-form vendor bytes; **nil / max** are constants.
  - Each added version = a Cargo feature flip + a `UuidVersion` enum arm + the `uuidVersion.ts` mirror + i18n. Record the exact feature list in the decision record's AD-1 split (AC4) and in the Stack table if it changes.
