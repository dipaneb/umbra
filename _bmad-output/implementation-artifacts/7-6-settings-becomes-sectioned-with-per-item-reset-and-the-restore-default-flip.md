# Story 7.6: Settings becomes sectioned, with per-item reset and the restore-default flip

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a returning Umbra user,
I want Settings organized by what it's protecting and each piece of stored data individually manageable,
so that persistence stays fully transparent as more of it accumulates.

## Acceptance Criteria

1. **Given** the Settings pane, **when** restructured, **then** it's sectioned in this order: Privacy (existing update-check disclosure, unchanged) → Appearance (the dark-mode override from Story 7.2 gets its permanent, token-styled home here; the pinned/recent visibility toggles from Story 7.5 also live here) → Persisted Data (enumerating every `shell.*`/`<tool-id>.*` key currently written to `settings.json`). [Source: epics.md#Story-7.6, AC1]
2. **Given** each key in Persisted Data, **when** listed, **then** it has its own reset action alongside its value — per-item reset, additive to the existing all-clear action, not replacing it. [Source: epics.md#Story-7.6, AC2]
3. **Given** the existing all-clear button, **when** relabeled, **then** its wording distinguishes it from the new per-item reset buttons while keeping identical INV-3 all-clear behavior — see Dev Notes "Resolved: button wording" for the exact strings, since the epics.md text and the locked mockup disagree and a call was made. [Source: epics.md#Story-7.6, AC3; EXPERIENCE.md Voice and Tone; mockups/step4.3-mockups-*.png Screen 03]
4. **Given** a fresh install with no `shell.restoreSessionEnabled` value yet in `settings.json`, **when** settings initializes, **then** `restoreEnabled` defaults to `false` — flipping Story 1.10's shipped `true` default. Existing installs that already have this key written (any value, `true` or `false`) keep it unchanged — the new default only applies where nothing was ever written. [Source: epics.md#Story-7.6, AC4; PRD FR5]
5. **Given** the settings store's single-writer rule (AD-10), **when** this story's new code is audited, **then** every new and existing key still writes through the single `settings` Pinia store — no new persistence mechanism is introduced. [Source: ARCHITECTURE-SPINE.md AD-10]

## Dev Notes

### Architecture guardrails

- **AD-10 (exact text)**: *"the only persistence mechanism is `tauri-plugin-store` writing one `settings.json`. The frontend `settings` Pinia store is its single writer — Rust-side code never writes it. Keys are namespaced `shell.*` / `<tool-id>.*`. The Settings pane enumerates every persisted key with a one-action clear (PRD INV-3)."* [Source: ARCHITECTURE-SPINE.md:99-103] This story's per-item reset is additive to, not a replacement for, that one-action clear (AC2), and must not introduce a second persistence path.
- **INV-3 (exact text)**: *"User data stays on-device and under user control... Convenience persistence is allowed where genuinely useful..., but only stored locally, visible in Settings, and clearable in one action. Nothing is ever persisted silently in a way the user can't see and erase."* [Source: PRD prd.md:35]
- No schema-migration machinery exists yet in this codebase, and none is needed here — `settings.ts` already reads every key as optional-with-default, and this story doesn't rename or retype any existing key, only changes one default value and adds a delete-based reset path. [Source: ARCHITECTURE-SPINE.md:266]
- Stack versions confirmed against the actually-installed packages: Vue 3.5.40, Pinia 4.0.2 (not 2.x), Vue Router 5.2.0, `@tauri-apps/plugin-store` 2.4.4 (installed under `^2` in package.json), Vitest for tests, TypeScript strict. [Source: ARCHITECTURE-SPINE.md:162-186; node_modules/.pnpm/@tauri-apps+plugin-store@2.4.4]

'reset to default' reads as restoring preferences — a different concept from privacy-erasure. The action was renamed toward explicit erase-data phrasing ('Clear stored data') specifically so the copy doesn't quietly weaken INV-3's privacy claim."* [Source: EXPERIENCE.md:41-48] — see Task 3 for how this reconciles with the mockup's more specific two-string wording.
- **IA**: *"Settings | Sidebar / gear | Sectioned pane: Privacy leads, then General/Appearance, then per-tool sections as they accrue persisted state."* [Source: EXPERIENCE.md:25] — "per-tool sections" is future-story territory (no tool persists anything yet); this story's Persisted Data section covers the `shell.*` set generically instead.
- **Screen 03 mockup** (`mockups/step4.3-mockups-light.png` / `-dark.png`, the third of three stacked screens in that one file) is the authoritative visual reference: card-per-row layout, section heading above each group, toggle/description pairs inside Privacy and per-tool cards, a segmented `System | Light | Dark` pill for theme in Appearance (not a `<select>`, though this story doesn't require rebuilding the control type — only relocating and restyling it; if a segmented-pill restyle is in scope, treat it as this story's job per AC1's "gets its permanent, token-styled home here," not a future one). **Caveat**: the mockup's "Suggest from clipboard" toggle and its JWT Inspector per-tool example are both out of this story's scope — clipboard-suggestion is Story 7.8 (still backlog), and the per-tool example is explicitly documented as "illustrative content only, not a locked product decision." ### Previous story intelligence (Story 7.5)

- **Key-addition recipe** this story should keep following: `ref` with sensible default → read as `?? default` → dedicated setter that bails if `!backingStore`, then `store.set()` + `store.save()` → reset inside `clearAll()` → returned from the store. `entries()`'s generic enumeration then surfaces new keys automatically with zero `SettingsView.vue` template changes needed for the *list* (only for the reset button, which is new in this story).
- 7.5 explicitly deferred per-item reset for its own two array keys and two visibility booleans to this story (its own AC5, and its "Not covered by this story" scope note) — Task 2 closes that out for all `shell.*` keys uniformly, not just 7.5's four.
- 7.5's two visibility checkboxes were built directly into the flat `SettingsView.vue` with an explicit inline comment marking their sectioned home as this story's job (see Task 1) — this story relocates, not rebuilds, them.
- Reusable gotchas from 7.5's review round, applicable here too: prefer `v-if` (real DOM removal) over `display:none` for anything that shouldn't be operable when hidden; never use `--color-accent-signature` (orange) for non-primary-nav chrome — this story's controls should use `--color-accent-default`/`--color-text-tertiary` per the UX spec above, not orange; persisted-write handlers need `.catch()`, not silent failure.
- Scoped Conventional Commits convention confirmed across all 5 recent commits: `feat(story-7-N): <lowercase summary>`, squash-merged via PR. Every prior Epic 7 story updated `sprint-status.yaml` and (where relevant) `deferred-work.md` alongside code, and was frontend-only (zero `src-tauri/` diffs) — this story is expected to be frontend-only too.
