# Story 7.6: Settings becomes sectioned, with per-item reset and the restore-default flip

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a returning Umbra user,
I want Settings organized by what it's protecting and each piece of stored data individually manageable,
so that persistence stays fully transparent as more of it accumulates.

## Acceptance Criteria

1. **Given** the Settings pane, **when** restructured, **then** it's sectioned in this order: Appearance (the dark-mode override from Story 7.2 gets its permanent, token-styled home here; the pinned/recent visibility toggles from Story 7.5 also live here) → Data (the all-clear action, always visible; the enumerated `shell.*`/`<tool-id>.*` key list stays hidden behind a "Show stored data" disclosure, off by default) → Privacy last (existing update-check disclosure, unchanged). [Source: epics.md#Story-7.6, AC1 — **amended 2026-08-17**, see Dev Notes "Post-implementation UX correction round"]
2. **Given** each key behind the "Show stored data" disclosure, **when** listed, **then** it has its own reset action alongside its value — per-item reset, additive to the existing all-clear action, not replacing it. [Source: epics.md#Story-7.6, AC2]
3. **Given** the existing all-clear button, **when** relabeled, **then** its wording distinguishes it from the new per-item reset buttons while keeping identical INV-3 all-clear behavior — see Dev Notes "Resolved: button wording" for the exact strings, since the epics.md text and the locked mockup disagree and a call was made. [Source: epics.md#Story-7.6, AC3; EXPERIENCE.md Voice and Tone; mockups/step4.3-mockups-*.png Screen 03]
4. **Given** a fresh install with no `shell.restoreSessionEnabled` value yet in `settings.json`, **when** settings initializes, **then** `restoreEnabled` defaults to `false` — flipping Story 1.10's shipped `true` default. Existing installs that already have this key written (any value, `true` or `false`) keep it unchanged — the new default only applies where nothing was ever written. [Source: epics.md#Story-7.6, AC4; PRD FR5]
5. **Given** the settings store's single-writer rule (AD-10), **when** this story's new code is audited, **then** every new and existing key still writes through the single `settings` Pinia store — no new persistence mechanism is introduced. [Source: ARCHITECTURE-SPINE.md AD-10]

## Dev Notes

### Post-implementation UX correction round (2026-08-17)

The first implementation followed AC1's original text literally: Privacy first, then Appearance, then an always-visible "Persisted Data" section listing every key as raw `key: JSON.stringify(value)` pairs. The developer reviewed the working result directly (not a code diff) and raised three real, end-user-facing problems, none of which any AC or Dev Notes source had flagged:

1. **Privacy-first buries the sections a user actually touches.** Nobody opens Settings to read prose about network calls; leading with it pushes Appearance and Data — the two sections with real interactive controls — below a wall of text. Resolved: Privacy moved to last.
2. **The Persisted Data section leaked implementation detail no end user asked for.** Showing every `shell.*` key as a raw `key: value` pair (visibly JSON-shaped) is genuinely useful for *debugging the app*, not for using it — a regular user has no reason to know settings are stored as JSON at all, let alone see the literal key names. Resolved: the section (renamed "Data") now shows only a one-line description and the always-visible "Clear all stored data" button by default; the enumerated list and per-item reset buttons are gated behind a new "Show stored data" checkbox, off by default.
3. **The prose read as AI-generated**, specifically flagged via its em dash usage (`"...first — nothing installs silently"`). Resolved: the Privacy paragraph was rewritten without an em dash, tightened to two short sentences.

Two structural options were considered for exposing the technical detail to whoever actually wants it (a curious user, or the developer debugging): a directly-editable `settings.json` file (VS Code/IDE-style), or a UI disclosure toggle. The file-editing route was rejected — Umbra isn't an IDE and has no existing file-opening affordance, so adding one just for this would be a new capability, not a UI tweak. The disclosure toggle was chosen: `showAdvanced`, a local `ref(false)` in `SettingsView.vue`, **deliberately not persisted** — it's a one-off reveal action, not a preference worth remembering between Settings visits, and persisting it would need its own `shell.*` key that would then itself appear in the very list it's meant to gate.

`epics.md`'s Story 7.6 AC1 was amended in place to match (dated note, not a silent rewrite — same convention Story 7.1 set for DESIGN.md corrections). This story's own AC1 and Task 1 text were updated to match here too.

### Architecture guardrails

- **AD-10 (exact text)**: *"the only persistence mechanism is `tauri-plugin-store` writing one `settings.json`. The frontend `settings` Pinia store is its single writer — Rust-side code never writes it. Keys are namespaced `shell.*` / `<tool-id>.*`. The Settings pane enumerates every persisted key with a one-action clear (PRD INV-3)."* [Source: ARCHITECTURE-SPINE.md:99-103] This story's per-item reset is additive to, not a replacement for, that one-action clear (AC2), and must not introduce a second persistence path.

Nothing is ever persisted silently in a way the user can't see and erase."* [Source: PRD prd.md:35]
- No schema-migration machinery exists yet in this codebase, and none is needed here — `settings.ts` already reads every key as optional-with-default, and this story doesn't rename or retype any existing key, only changes one default value and adds a delete-based reset path. [Source: ARCHITECTURE-SPINE.md:266]
- Stack versions confirmed against the actually-installed packages: Vue 3.5.40, Pinia 4.0.2 (not 2.x), Vue Router 5.2.0, `@tauri-apps/plugin-store` 2.4.4 (installed under `^2` in package.json), Vitest for tests, TypeScript strict.
