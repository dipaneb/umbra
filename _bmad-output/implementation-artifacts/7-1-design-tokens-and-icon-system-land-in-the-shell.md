# Story 7.1: Design tokens and icon system land in the shell

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the developer,
I want `DESIGN.md`'s color/type/spacing/radius/elevation tokens implemented as CSS custom properties, plus a real icon system, wired into the app's global styles,
so that every later Epic 7/8 story consumes one source of truth instead of hardcoded values and raw emoji.

## Acceptance Criteria

1. **Given** `DESIGN.md`'s token tables (colors, typography, spacing, rounded, components), **when** the shell's global stylesheet is inspected, **then** every token exists as a CSS custom property under `:root`, named to match `DESIGN.md` (e.g. `--color-accent-signature`, `--font-body-size`).
2. **Given** dark-mode token values (the `-dark` suffixed entries in `DESIGN.md`), **when** tokens are wired, **then** they activate via a `prefers-color-scheme: dark` media query only — no manual light/dark class yet; a user-facing override is Story 7.2's job, not this one's.
3. **Given** Geist Sans and Geist Mono (`DESIGN.md` Typography), **when** fonts are loaded, **then** they are bundled as local font files (SIL OFL 1.1, no attribution/royalty requirement) — never fetched over the network, so the NFR1/INV-1 network-monitor tour doesn't regress.
4. **Given** the app's root layout, **when** this story completes, **then** `body` adopts `--color-bg-base`/`--color-text-primary` as an end-to-end smoke test that the token layer resolves correctly — but no other shell component (sidebar, settings, palette, update dialog) is retrofitted yet; that's each subsequent story's own scope.
5. **Given** the Tool Registry's `icon` field, **when** this story starts, **then** an icon system is chosen and documented with rationale, verified current and license-checked for NFR7 (All-Rights-Reserved bundling) at story start, following this project's existing convention for open technical picks (e.g. Story 6.1's `lopdf` candidate verification), **and** the registry's `icon` field is repurposed from a shorthand display string to an icon-name key resolved through the chosen system — AD-5 stays the single source; Stories 7.3 (Grid-home) and 7.4 (Sidebar) both consume this mechanism rather than each inventing their own.

**Interpretation notes, recorded explicitly rather than left implicit:**

- **AC5's icon library is `@phosphor-icons/vue`, not the epic's own originally-named Lucide candidate — a developer decision, confirmed before drafting.** Live-verified against the npm registry this session: `@phosphor-icons/vue` 2.2.1, **MIT**, peer `vue: >=3.2.39` (this project declares `vue: ^3.5.13`, resolved to `3.5.40` in the installed tree per `ARCHITECTURE-SPINE.md`'s Stack table — compatible either way). Tree-shakeable named exports (`import { PhHash } from "@phosphor-icons/vue"`, confirmed against the package's own current README/docs via Context7 — **not** the `/compact` entry point, which bundles everything into one file and defeats tree-shaking). MIT clears NFR7's bundling bar the same way Story 6.1/6.2's MIT-licensed picks did. `phosphor-vue` (unscoped, 1.4.2) is the deprecated legacy package name — do not use it.
- **AC5's registry-field repurposing is real scope, not a drafting error — a discrepancy with `DESIGN.md` was found and deliberately overridden, developer-confirmed.** `DESIGN.md`'s own Card component spec (line 178, `status: final`) currently describes the icon-badge as "monospace-style shorthand — e.g. `{}`, `64`, `#`, `JWT`" — which is what the registry's `icon` field values already are today (`registry.ts`'s `icon: "{ }"`, `"64"`, etc.), not a placeholder awaiting real icons. Nothing in `DESIGN.md`, `EXPERIENCE.md`, or the Step 4.3 design-brief working notes explores an SVG icon library anywhere. Raised to the developer directly during story drafting: **decision is to follow AC5 as written** — build the real Phosphor icon system and repurpose the registry's `icon` field to icon-name keys — **and update `DESIGN.md`'s Card/Components sections to match this decision as part of this story** (Task 6 below), the same "resolve the discrepancy, don't silently drop either side" discipline this project already applies to `ARCHITECTURE-SPINE.md`'s dated AD amendments. `DESIGN.md` is treated as `status: final`, so this is a dated, explicit amendment — never a silent rewrite of what it used to say.
- **Dark-mode tokens are one custom property redefined under a media query, not two permanently-live properties.** `DESIGN.md`'s frontmatter lists light/dark as separate keys (`bg-base` vs. `bg-base-dark`), but AC2's "activate via `prefers-color-scheme: dark`" means each CSS custom property keeps one name (e.g. `--color-bg-base`) whose *value* is redefined inside `@media (prefers-color-scheme: dark) { :root { ... } }` — never two separately-named properties that a component would have to switch between itself. A literal reading of AC1 + AC2 together could produce the wrong (two-property) shape; this note exists so it doesn't.
- **AC1's "components" token table is landed as primitives already covered elsewhere, plus exactly one genuinely new value — not a full component-token abstraction layer.** Every entry under `DESIGN.md`'s `components:` key (`button-primary`, `button-default`, `button-destructive`, `card`) composes only from colors/rounded/spacing already covered by AC1's primitive tokens — nothing new to declare, and AC4 explicitly excludes retrofitting any of Button/Card as actual components this story. The one exception is `floating-surface.shadow` / `.shadow-dark`, a real literal value with no primitive to compose from — landed as a single `--shadow-floating` custom property, redefined for dark mode per the note above. `card.shadow: none` needs no property (there's nothing to encode).
- **AC5's registry data-type change collides with AC4's "sidebar/palette not retrofitted" boundary — a real, unavoidable tension resolved as a narrow rendering-mechanism fix, not a retrofit.** Both `AppSidebar.vue:15` and `CommandPalette.vue:123` currently render `{{ tool.icon }}` as raw text. Task 5 changes every registry entry's `icon` value from a shorthand display string (`"{ }"`, `"64"`, etc.) to an `IconName` key (`"json"`, `"base64"`, etc.). Left as-is, both components would silently start displaying the literal string `"json"`/`"base64"`/etc. instead of the old shorthand tag the moment this story ships — a real, user-visible regression neither `AppSidebar.spec.ts` nor `CommandPalette.spec.ts` currently asserts against (confirmed: neither file's test suite checks the icon's rendered text). "Not retrofitted" (AC4) is read narrowly here to mean *no color/spacing/dark-mode/layout styling work* — it does not mean "ship a known text-rendering regression in two components AC4 itself implies should keep working." The fix (Task 5b) is the smallest possible: swap `{{ tool.icon }}` for `<component :is="resolveIcon(tool.icon)" />` in both files, using Task 4's own resolver — nothing else in either file changes.

**Not the first story with a `Not the first story` note needed — this IS the first story of Epic 7.** `epic-7` is set to move `backlog` → `in-progress` as part of finalizing this story's creation (per the `bmad-create-story` workflow's own epic-status-transition step — not yet applied as of this draft; `sprint-status.yaml` still shows `epic-7: backlog`). No previous-story-in-epic intelligence exists; this story instead draws on Stories 6.1/6.2's process conventions (see Dev Notes) and the Epic 5 retrospective's general "resolve a placeholder, update the source doc to match" discipline.
