# Story 5.3: The privacy promise, proven at every release

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the developer (whose "Trusted" success metric depends on it),
I want a written, executed network-monitor procedure gating every release,
so that NFR1 is a verified fact on every version, not a slogan.

## Acceptance Criteria

1. **Given** a written release-checklist procedure, **when** followed, **then** a network monitor observes the app while every tool is exercised, and the only permitted connection is the user-confirmed update check (NFR1).
2. **Given** a release PR, **when** it is prepared, **then** the executed checklist result is recorded in the PR, and the release does not ship without it (AD-12).
3. **Given** the current release, **when** this story completes, **then** the procedure has been executed against it at least once with a passing result.

**Boundary with Story 5.1/5.2 (both done):** Story 5.1 built the tag-driven build/sign/notarize pipeline; Story 5.2 built the app-built update-confirmation dialog and did the *static* AD-7 audit (`cargo tree`/`Cargo.lock` inspection proving `tauri-plugin-updater` is the only network-capable dependency). Both stories explicitly deferred the *physical* network-monitor tour — an actual `nettop`/Little Snitch-style capture during live use — to this story, and named it by name when doing so (Story 5.2's own boundary note: "Story 5.3's written network-monitor release checklist... is not this story's job"; Task 6: "the real, physical network-monitor tour... is Story 5.3's job, not this story's — `cargo tree` proves the dependency graph, not runtime behavior"). This story turns that ad-hoc, one-off precedent (already exercised once for the Bucket specifically in Story 4.3) into a written, repeatable, all-tools procedure tied to every release going forward — it does not re-do 5.1/5.2's static dependency audits.

**Scope note on the OCR carve-out:** NFR1's PRD text names a *conditional* second carve-out ("a one-time first-use model download... only if architecture rejects bundling the ONNX OCR model"). Architecture chose bundling (AD-7: "OCR models ship bundled as app resources... `oar-ocr`'s auto-download explicitly disabled"), so that conditional carve-out never materializes — epics.md's own restated NFR1 confirms this explicitly ("OCR models are bundled per AD-7 — the conditional second carve-out is resolved away"). The checklist this story writes must therefore expect **exactly one** permitted connection type (the update check), not build in tolerance for a second one that doesn't exist.
