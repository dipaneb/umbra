## What Went Well

- **The honesty-bar architecture held, including on itself.** Story 3.1's central decision — hand-writing `describe()` in `umbra-core` instead of calling `croner`'s own built-in description function — set up a project-controlled vocabulary contract that Story 3.2's NL parser reuses directly (not a second, independent renderer). This is what makes the AD-9 round-trip check a genuine safety net rather than a tautology: parser and describer structurally cannot describe the same field values differently.
- **Story 3.3 turned a runtime property into a provable one.** The corpus (44 hand-traced phrases: 31 must-convert, 13 must-honestly-fail) moved AD-9 from "true because the code happens to enforce it" to "true continuously, because CI fails if it stops being true." An independent re-verification pass caught one wrong test row before it shipped (the comma-after-single-weekday grammar gotcha).
- **A real content gap didn't stall delivery.** The "addendum" phrase corpus that FR21/epics.md cite as this feature's acceptance basis does not exist in the repository — confirmed by repo-wide search in both Story 3.2 and Story 3.3. Rather than blocking on it, Story 3.2 built a provisional test set and Story 3.3 explicitly took ownership of originating the real corpus from the grammar actually implemented, with a clean, well-documented handoff between the two stories.
- **Dependency-verification discipline held again.** Consistent with Epic 2's retro finding, the `croner` crate's own docs.rs page contained an internally contradictory claim about a public field; rather than trusting either secondhand source, the dev read the vendored crate source directly to resolve it with ground truth before building against it.
- **The async latest-wins race class did not recur.** Both cron sections (`onExplain`/`onPaste`/`onParseSchedule`/`onPasteSchedule`) use independent per-action `createLatestWinsRunner()` instances, correctly, because neither section has more than one write-trigger to the same state — the JWT precedent held.

## Challenges

- **Three separate review-caught instances of "confident, plausible-looking output that was quietly wrong"** — exactly the failure mode this epic exists to eliminate:
  - Story 3.1: a calendrically-impossible schedule (e.g. Feb 30th) rendered a confident description while `next_runs` silently returned zero matches, with no error.
  - Story 3.1: business-hours phrasing understated the actual firing window by nearly an hour (`9-17` read as "to 5:00 PM," but the range fires through 5:59 PM).
  - Story 3.2: step values outside a field's valid range weren't bounds-checked — `"every 90 minutes"` generated a cron expression that actually fires hourly, and `"every 30 hours"` one that fires daily, both contradicting their own rendered description. The round-trip check alone couldn't catch this, since it only compares two descriptions built from the same struct, never the struct against real cron semantics.
  - All three were caught in code review before merge — reviewed and resolved as a working safety net, not escalated to a process action item (team consensus this session).
- **One Epic 2 retrospective action item stayed open through the entire epic.** "Document `registry.getLatestWinsRunner(toolId)` as the required pattern for multi-write-trigger tools" (owner: Charlie/Winston) was never addressed during Epic 3 — correctly, per Epic 2's own retro, since neither cron section ever needed multi-trigger coordination. It surfaces again now because Epic 4's Bucket tool (drag-drop and clipboard-paste both writing to the same extraction state) is exactly the shape this pattern exists for.
- **Stale documentation references to a confirmed-nonexistent source file.** `epics.md` and the PRD still cite "the addendum's canonical phrase corpus" as FR21's acceptance basis in four places, even though its absence is now a confirmed, permanent fact rather than an open question — a minor hygiene gap, not a blocker.
