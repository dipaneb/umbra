# Story 5.1: A signed, notarized Umbra anyone can download

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer (and the recruiters auditing the pipeline),
I want every release built, signed, and notarized by a tag-driven pipeline and published on GitHub,
so that a fresh Mac opens Umbra with zero warnings and no hand-built artifact ever circulates.

## Acceptance Criteria

1. **Given** a version tag is pushed, **when** the release workflow runs, **then** `tauri-action` builds, signs with the Developer ID certificate, notarizes with Apple, and publishes a versioned GitHub Release (FR30, FR32, AD-12), **and** the release includes `latest.json` for the updater.
2. **Given** the published artifact, **when** downloaded and opened on a fresh Mac (macOS 13+, Apple Silicon), **then** the app opens with no Gatekeeper bypass required (FR30).
3. **Given** the pipeline's secrets, **when** audited, **then** the signing certificate, notarization credentials, and updater keypair exist only in GitHub Actions secrets — never in the repo (AD-12), **and** the updater private key is backed up offline in two places before the first release ships (AD-12).
4. **Given** the repo's history, **when** reviewed, **then** releases are tag-driven only, and Conventional Commits are in effect so a changelog can be generated later (FR32).

**Explicitly out of scope for this story** (belongs to Story 5.2, "Umbra updates itself"):
- Adding `tauri-plugin-updater` as a runtime dependency (Cargo.toml / package.json).
- The `plugins.updater.endpoints` array and the app-built update-confirmation dialog.
- Any in-app or README disclosure of the update check as a network exception (AD-7/INV-1 carve-out) — there is no update *check* to disclose until Story 5.2 adds one.
- Story 5.3's written network-monitor release checklist and Story 5.4's landing page.

This story's job is narrower: prove a version tag produces a signed, notarized, downloadable GitHub Release, and that the updater *artifacts* (`latest.json`, signed update bundles) exist for Story 5.2 to consume later — not that the app can check for or install updates yet.

## Dev Notes

- **This is the first story whose "done" doesn't mean "fully verified in this session."** Every prior story's manual verification was a GUI smoke test achievable by the developer at their own desk. This one depends on a real Apple Developer ID certificate, a real tag push, and a real second Mac — none of it something a coding session can provision. Structure Completion Notes to separate "coding work complete" from "AC1–AC3 verified" cleanly; don't conflate the two the way earlier stories didn't need to.
- **Story 5.1 vs. 5.2 boundary is easy to blur — don't.** It's tempting to also add `tauri-plugin-updater` and wire up an update-check dialog while "already in the release/updater code" — resist it. Story 5.2's own AC explicitly builds the app-built confirmation dialog and the INV-1 carve-out disclosure; adding the plugin dependency here would be solving a problem this story doesn't own yet and would pre-empt design decisions (dialog UX, disclosure copy) that belong to that story.
- **Signing ≠ the updater plugin.** `bundle.createUpdaterArtifacts` and `TAURI_SIGNING_PRIVATE_KEY` operate entirely at build/bundle time (the Tauri CLI signs the artifacts it produces); nothing about them requires the app itself to have `tauri-plugin-updater` installed or to check for updates at runtime. This is what makes the Task 1 boundary (pubkey in config now, plugin dependency later) safe rather than premature.
- **`ci.yml`'s SHA-pinning and dense-comment conventions are load-bearing, not optional style** — every existing `uses:` step there is pinned to a full commit SHA with a version comment, and non-obvious steps (the `ORT_CACHE_DIR` env var, the `awalsh128` rejection) carry paragraph-length comments explaining *why*, not just *what*. `release.yml` is this project's second CI surface; match that bar, don't introduce a laxer one.
- **`APPLE_PASSWORD` is an app-specific password, not the Apple ID login password** — this is the single most common real-world way this exact pipeline shape fails silently-confusingly (an auth error deep in `notarytool`'s output, not an obvious "wrong password" message). Said twice in this file (here and Task 3) deliberately.
- **No test suite exists for a GitHub Actions workflow file** — "testing" this story means YAML validity + not breaking the existing `cargo`/`pnpm` suites via the `tauri.conf.json` edits, not new unit tests. Don't invent a testing task that doesn't map to anything real.

### Privacy correction (2026-08-08)

This session initially committed and pushed both `docs/release-secrets.md` and this
story file's own Debug Log/Completion Notes with the developer's real full legal name
and a literal absolute local filesystem path (`/Users/<real-username>/...`) embedded in
plain text, then pushed both to the public remote (PR #40) **without asking first** —
a real process failure, called out directly by the developer, not a minor style note.
Two separate mistakes, not one: pushing a new doc to the shared repo without the
developer having said they wanted it there at all, and separately, that doc (plus this
story file) containing real PII regardless of the push question.

**What actually happened, for anyone reading this file's history later:** a
pre-existing `PreToolUse` hook (`.claude/hooks/guard-commit-privacy.sh`, added
2026-07-22 in commit `edf2f18`, well before this session) is specifically designed to
block a `git commit` whose staged diff contains this machine's home-directory path.
Manually re-tested during this correction: the hook's logic is correct and *would* deny
such a commit when actually invoked. It did not fire during this session's actual
`git commit` calls, and this session has no visibility into why the harness didn't
invoke it — that's flagged here as an open question for the developer to investigate,
not something resolved or explained away.

**Remediation applied:** both files' current content (this file and
`docs/release-secrets.md`) had the real name and real path replaced with placeholders
(`<Your Name>`, `<Team ID>`, and generic example paths). The developer then explicitly
requested the original values also be purged from git history, not just fixed forward
— done by soft-resetting this branch to its last clean commit (`934f3aa`, before the
leak was introduced) and recommitting the already-sanitized working tree as a single
clean commit, then force-pushing (`--force-with-lease`) to `origin`. The four
intermediate commits that ever contained the leaked strings
(`79abc99`, `b4dbbcb`, `bde03e2`, and this fix itself, `edf5f50`) no longer exist on
this branch or on `origin` as of that force-push. **Residual exposure this can't
retroactively close:** the leak was live on the public remote for roughly 80 minutes
(commit `79abc99` pushed 2026-08-08 17:41 CEST → the fix pushed 19:00 CEST) before any
rewrite happened, during which anyone could have viewed, cloned, or cached it — GitHub
itself may also retain the old commit SHAs reachable via direct URL for a period after
a force-push, and any local clone/fork made during that window still has the original
history. Treat the exposed data (a full name and a local username) as having been
briefly public, not as fully undone.
