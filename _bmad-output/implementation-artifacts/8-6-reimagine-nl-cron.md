## Story

As the developer,
I want to reconsider the NL ↔ Cron tool's feature set through open discovery before redesigning its UI,
so that the redesign reflects a deliberately chosen scope, not a visual reskin of whatever shipped first.

### Container, layout, bidirectional binding

6. **Given** the redesigned `src/tools/cron/CronView.vue`, **when** it renders, **then** it is a **single bidirectional grid** — no `AppTabs.vue`, no `AppButton` of any variant, no `primary`-orange control anywhere, no natural-language / phrase `<textarea>`, no `.english-only-notice` node, no bare `<hr>` two-section split. Layout order, top to bottom: `h1` → description caption → editable **expression line** (with a copy icon-button) → the **5-field grid** (Minute · Hour · Day of month · Month · Day of week, in cron order) → the **live panel** (one-line prose · per-field breakdown rows · next-3-runs). The only interactive controls are the expression-line `<input>`, the five `CronFieldEditor` instances, and the two `useCopyFeedback` copy icon-buttons.

7. **Given** the expression line — a single-line `<input>` in `--font-code-*`, seeded on `0 9 * * *` at mount (never empty, never `* * * * *`) — **when** the user types or pastes into it (native `Cmd/Ctrl+V` works; no paste button), **then** after a **200 ms debounce** (`src/shell/debounce.ts`, `debouncedX.cancel()` in `onUnmounted`) it is sent to `cron_explain`, and on a successful parse **all five field editors repopulate** from the parsed fields (expression → fields). There is **no Explain button** and **no Convert button**.

8. **Given** any of the five field editors, **when** the user changes one of its controls, **then** the view **recomposes the expression line view-side** (`fieldValues.join(' ')` — string assembly is view-side JS per the decision record's AD-1 split, immediately round-trip-validated by the resulting `cron_explain` call) and re-runs `cron_explain` — **immediately** for a discrete control change (segment, `<select>`, Advanced toggle), **debounced 200 ms** for keystrokes in an Advanced raw-grammar `<input>` (fields → expression). Each field editor holds **one string value** as its single source of truth; the three controls are pure views onto it.

9. **Given** the redesigned tool, **when** it is exercised in any way, **then** `cron_parse_schedule` is **never invoked**, no `phrase`/NL input exists in the DOM, and the four old `createLatestWinsRunner()` instances (`runExplain` / `runPaste` / `runParse` / `runPasteSchedule`) are replaced by **one local `createLatestWinsRunner()`** backing the single `cron_explain` call site, driven by the debounced watcher — a superseded in-flight result is discarded (AD-16). **Not** `registry.getLatestWinsRunner("cron")` (cron has no `DropZone.vue` write-surface). The documented "known caveat" (separate runner instances racing on shared state) dissolves with the single-state-group design.

### The hybrid field editor

10. **Given** the new component `src/tools/cron/CronFieldEditor.vue` (a cron island component — no cross-tool reuse), **when** one instance renders for a field, **then** it exposes **three stacked controls** over one string value:
    - **(a) Segmented `Every | Specific`.** `Every` sets the value to `*`. `Specific`, when the value is currently `*`, seeds a sane bare value (`0` for Minute, `0` for Hour, `1` for Day of month, `1` for Month, `1` for Day of week) and moves focus to control (b).
    - **(b) Value input** — visible only when the value is not `*`. Minute / Hour / Day of month → a plain `<input>` (one bare value). **Month** and **Day of week** → a **name-aware `<select>`** (Jan–Dec / Sun–Sat) that writes the canonical numeric value into the field string.
    - **(c) `▸ Advanced` disclosure** → a raw text `<input>` prefilled with the field value, accepting the plain field grammar (`1,3,5`, `1-5`, `*/15`, `10-50/5` and combinations). It is authoritative while open. It **auto-expands and stays expanded** whenever the field value contains `,`, `-` or `/` (so a pasted `*/15 9-17 * * 1-5` lands with Minute, Hour and Day-of-week showing their Advanced input). **Auto-expand only** — it never auto-collapses.

11. **Given** the Day-of-week `<select>`, **when** it displays a value, **then** both `0` and `7` resolve to **Sunday** in the display; the `<select>` always writes one canonical numeric form into the field string.

12. **Given** a rendered field editor, **when** the live panel has a value, **then** the field editor shows its own per-field breakdown phrase inline (from `fields[i]`), and the same five phrases render as rows in the live panel — one shared source (`CronExplanation.fields`), never a second renderer. No field editor ever shows a fallback / shrug phrase for its field.

### New core work (`crates/umbra-core/src/cron.rs`)

13. **Given** the trimmed 5-field expression, **when** `explain_at` runs, **then** a **new project-owned pure function** parses each field into a `FieldExplanation` (field name + an instrument-voice phrase) and returns `Vec<FieldExplanation>`. It shares parsing shape with `FieldSpec` where sensible and **does not** call `croner`'s internal pattern representation (same project-owned principle as `describe()` — AD-9's round-trip stays a real safety net, not a tautology).

14. **Given** the return-shape change, **when** it lands, **then** `CronExplanation` grows **`fields: Vec<FieldExplanation>`** and **`description_generic: bool`** (true when `describe()` would return only `fallback_description`); `FieldExplanation` is a new `serde` struct with `snake_case` fields. `src/tools/cron/cronExplanation.ts` grows the matching `fields: FieldExplanation[]` + `description_generic: boolean` (with its existing "keep in sync by hand" comment), and its **`ScheduleParseResult` interface is deleted**. The view **suppresses the one-line prose** when `description_generic` is true (the breakdown rows carry the explanation); it shows the prose one-liner otherwise.

15. **Given** the per-field breakdown, **when** a field is explained, **then** its phrase follows this instrument-voice spec (reusing the existing `weekday_name` / `month_name` / `ordinal` / `join_with_and` helpers; "through" denotes an inclusive range; exact wording adjustable at the slice render-review):

    | shape | Minute | Hour | Day of month | Month | Day of week |
    | --- | --- | --- | --- | --- | --- |
    | `*` | every minute | every hour | every day | every month | every day of the week |
    | `5` | minute 5 | hour 9 | the 15th | June | Monday |
    | `0,15,30` | minutes 0, 15 and 30 | hours 8, 12 and 18 | the 1st, 15th and 28th | January, June and December | Monday, Wednesday and Friday |
    | `1-5` | minutes 0 through 29 | hours 9 through 17 | the 1st through the 15th | March through August | Monday through Friday |
    | `*/15` | every 15 minutes | every 2 hours | every 3 days | every 2 months | every 2 days of the week |
    | `10-50/5` | every 5 minutes from minute 10 through 50 | every 3 hours from hour 9 through 21 | (same shape) | (same shape) | (same shape) |

    Each row renders as `Day of week: Monday through Friday`.

16. **Given** a **6-field** (seconds-precision) expression, **when** it reaches `explain` / `explain_at`, **then** it is rejected with a **new value-free code `cron-six-field-unsupported`** whose English message is a fixed authored sentence (*"This tool handles standard 5-field cron expressions. Seconds-precision (6-field) expressions aren't supported yet."*). This code **is added to `TRANSLATABLE_CODES`** (`src/shell/toolError.ts`) with `errors.cron-six-field-unsupported` keys in `en.json` + `fr.json` — it is the one `cron-*` code that is our own value-free sentence, not `croner`'s runtime text. The stale comment block in `toolError.ts` (*"Every `cron-*` code is also deliberately excluded … the parser is English-only"*) is rewritten: the English-only-parser rationale is gone with the parser. Rendered `role="alert"`; the grid and live panel hold the last valid state.

17. **Given** input larger than a cap, **when** it reaches core, **then** `crates/umbra-core/src/cron.rs` defines **`const MAX_INPUT_BYTES: usize = 1024`** (a standard 5-field expression is one short line; even the most pathological legitimate one is ~360 bytes, so 1 KB can never reject a real expression) with a byte-length guard at the top of `explain` and the new field-parse entry point, returning a new **`cron-input-too-large`** `ToolError` (embeds the cap in prose → **stays OUT of `TRANSLATABLE_CODES`**, matching `hash-`/`json-`/`jwt-input-too-large`); unit tests at cap / over cap / normal-unaffected. The expression-line `<input>` carries a mirrored `.length` ceiling (defense-in-depth — the Hash 8.4 / JWT 8.5 pattern). Over-cap renders **`role="status"`** (calm, not a red alert): *"Expression too long. This tool handles standard cron expressions up to 1 KB."*

The `MUST_CONVERT` / `MUST_HONESTLY_FAIL` corpus runs as a `cargo test -p umbra-core` gate and a regression fails CI. **This is FR21's honesty bar with teeth — the redesign must keep it exactly as strong.** The safety net is only genuine because `build_result` builds `expected_description` from the *same* `time_clause`/`day_clause` helpers `describe()` calls — do **not** introduce a second independent English renderer. The corpus **grows with every phrasing bug report, permanently** — a stated maintenance rule (Story 3.3 AC / AD-9).
  3. **Cron is *the* tool the AD-13 localization rule was amended for.** On 2026-08-23, the French-UI release shipped OCR localization but **deliberately deferred the NL→cron leg** — the parser + `describe()` are hand-written English grammars, AD-9 round-trips by string-equality, and "the cron tool is separately slated for a full revamp, making a French grammar built against its current shape throwaway work." **This story is that revamp.** The amendment requires the deferral stay *disclosed* (`tools.cron.englishOnlyNotice` + "in English" kept explicit in the French `description`), not hidden. The redesign may move/reword/re-style that disclosure — but it **cannot silently drop it or imply non-English input works**. If the redesign's scope credibly includes a path to a localizable parser, that is a large architectural conversation to surface with the developer, not assume.
  4. **No clipboard-suggestion hook, unlike JWT.** Cron has no `clipboardMatch`. A cron expression (`* * * * *`) is far more ambiguous against arbitrary clipboard text than a JWT's three base64url segments. Adding a `clipboardMatch` (and/or a `shortcut`) is a plausible "Added" candidate but a **shell concern** (AD-6) — present as options with specificity/false-positive trade-offs, don't wire it silently. `EXPERIENCE.md` Flow 3 already has `⌘K` "cron" → type "every Monday at 9am" → `0 9 * * 1` as a named step in the 5-minute demo.
  5. **`describe()` is a project-owned templater by deliberate choice.** It only recognises the field vocabulary the corpus needs (wildcard / single / list / range / step) and falls back to `"Runs on schedule \"{expr}\""` rather than guessing. Any "richer descriptions" ambition (per-field breakdown, `@daily` macros, 6-field seconds) means *expanding a verified vocabulary with new corpus rows first* — not swapping in `croner`'s own describer, which would make the AD-9 round-trip a tautology.
  6. **`next_runs` is only ever 3, rendered view-side via `formatDateTime`.** Epoch seconds `i64` across IPC (Consistency Conventions table, named explicitly alongside JWT `exp`/`iat`/`nbf`). Humanising, relative time, "show more upcoming runs", timezone labelling — all **view-side** (AD-1). Only genuinely new *parsing/description* logic is new core work.
  7. **No size cap.** `cron.rs` has no `MAX_INPUT_BYTES`; neither `<textarea>` has a ceiling. If Task 2 moves to live as-you-type conversion (the 8.2/8.3/8.4/8.5 direction), it wants a debounce **and** a length ceiling, and a decision on whether a real cap belongs in core (JSON/Base64/Hash have one; JWT added one in 8.5 as its *only* core change).
  8. **Both commands already `spawn_blocking` (AD-4)** — out of consistency, not measured need. The NL→cron path is the heaviest (grammar parse + a full `explain_at` round-trip through `croner`), still sub-millisecond. Keep both on the blocking pool.

- **Architecture boundaries Task 1 must scope against and Task 2 must obey:**
  - **AD-1** — every transformation is a pure function in `umbra-core::cron`; the view renders. **Presentation formatting is view-owned, never core.** Load-bearing here: humanising `next_runs` (epoch `i64` → locale datetime), any relative-time / "next run in…" strings, timezone labelling, and "show N upcoming runs" are all *view-side*. Only genuinely new *parsing / description* logic — an expanded `describe()` vocabulary, a new grammar clause, 6-field handling, a per-field breakdown struct — is new core work. Epoch values stay **unix seconds as `i64`** across IPC (Consistency Conventions table, named explicitly for cron next-run times).
  - **AD-9** — **NL→cron never ships an unverified guess.** Every NL→cron result round-trips through `describe()` by string-equality before display; only a consistent round-trip is shown. The canonical phrase corpus (must-convert + must-honestly-fail) runs as an automated `umbra-core` test; a corpus regression fails the build. **This story does not weaken, bypass, or make optional any part of that.** A corpus change is a red test added *before* the parser changes.
  - **AD-13** — **localization ships as one unit or not at all.** The 2026-08-23 amendment recorded the NL→cron leg as a *disclosed, deliberate* deferral pending this revamp. The redesign keeps the English-only limitation **honestly disclosed and visible**; it does not silently drop the notice or imply non-English input works. Any move toward an actually-localizable parser is a large architectural conversation to have with the developer, not a silent scope expansion.
  - **AD-2 / AD-11** — `umbra-core` imports no `tauri` crate and has zero `#[cfg(target_os)]`; CI runs `cargo test --workspace` on all three OSes. Any new crate must build clean cross-platform.
  - **AD-3** — every command returns `Result<T, ToolError>`; the view renders from `ToolError` structure only (`code`, `position`, `context`), never by parsing `message`. Commands are `cron_<verb>`.
  - **AD-4** — anything that can exceed ~100 ms CPU runs on the blocking pool via `spawn_blocking`. Both cron commands already do. The NL→cron round-trip is the heaviest path — keep it on the blocking pool.
  - **AD-6** — tools are islands. Do not touch another tool's files. Cross-cutting state lives only in the `settings` / `registry` Pinia stores. A `clipboardMatch` / `src/shell/clipboardMatch.ts` addition is a **shell concern** — present as options. `croner` describer reuse is not an option (see AD-9).
  - **AD-7** — **zero network surface except the updater.** `croner` is offline and pure. Any new crate gets the `cargo tree -i reqwest` audit **plus** a direct read of its own dependency list (the Stack table's Story 5.2 / 7.8 precedent).
  - **AD-10** — if Task 2 adds a persisted preference (a remembered default direction, a 12h/24h next-run display toggle, "show N upcoming runs"), it is a `cron.*`-namespaced key in the `settings` Pinia store — **Stories 8.3 (`uuid.*`) and 8.4 (`hash.*`) established this exact pattern**: add each key to the store's single-source `DEFAULTS` map so `init()`, `clearAll()` and `resetKey()` cover it automatically, validate the stored value on load, read on mount, write an immediate `set` + `save` on change (discrete-value setters are **not** debounced), and it surfaces in `SettingsView.vue`'s existing "stored data → reset" list with **no new Settings section**.
  - **AD-16** — one `createLatestWinsRunner()` per *independent* piece of state. Today four **local** runners, two per section. **Correct on the section axis; the "known caveat" is that each section still uses two instances instead of one shared per group.** Scope **one local runner per group** (`registry.getLatestWinsRunner("cron")` is wrong — cron has no `DropZone.vue`-reachable write-surface). If Task 2 collapses each section to a single input + live conversion, that naturally becomes one runner per section.
