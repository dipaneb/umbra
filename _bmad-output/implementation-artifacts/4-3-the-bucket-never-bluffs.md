# Story 4.3: The Bucket never bluffs

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want the Bucket to state failures and empty results explicitly — and to provably never phone home,
so that I can trust both its answers and its privacy promise.

## Acceptance Criteria

1. **Given** an image in which the engine finds no text, **when** extraction completes, **then** the tool explicitly states that no text was found — never a blank result pane (FR26).
2. **Given** a corrupt or unreadable image, **when** extraction is attempted, **then** a structured `ToolError` displays inline explaining the failure (FR26, NFR4, AD-3).
3. **Given** two extraction requests racing on first use, **when** both trigger engine initialization, **then** the `OnceLock`-guarded initialization runs exactly once and both requests share it (AD-16).
4. **Given** a network monitor observing the app, **when** the Bucket is exercised — including the very first use, **then** zero network activity occurs; the bundled-models promise is verified, not assumed (AD-7, NFR1).
5. **Given** the v1 scope, **when** reviewed, **then** OCR supports English only, and the French coupling rule (French lands in UI + OCR + NL→cron together, or not at all) is recorded for any future localization (FR25, AD-13).

**Explicitly out of scope for this story** (already satisfied by prior stories, not re-verified here):
- The oversized-input guard (`bucket-input-too-large`) — built and tested in Stories 4.1/4.2.
- Latest-wins supersession across drop/paste — built and tested in Story 4.2 (AC4 there).
- The raw-RGBA/clipboard input path itself — Story 4.2's scope; this story only adds empty/failure/init-race coverage on top of it.

  - [x] **Do not race the shared production `OCR_ENGINE` static.** `cargo test` runs this crate's tests in parallel within one process by default (no `test-threads=1`/serial config exists anywhere in this repo — confirmed absent from `Cargo.toml`, any `.cargo/config.toml`, and `.github/workflows/ci.yml`'s plain `cargo test --workspace --no-fail-fast`), and `bucket.rs`'s existing tests already call `ocr_engine(&app)` (every `bucket_extract_text_command_*` test, plus the clipboard tests). By the time any new test runs, `OCR_ENGINE` is almost certainly already initialized by another test running concurrently — so racing it directly cannot reliably exercise the actual not-yet-initialized race window, and a counter on it would only prove "no *additional* init happens once already-initialized," not AC3's real claim.
  - [x] Instead, test the exact mechanism `ocr_engine()` relies on **in isolation**: inside the new test, declare a fresh, test-local `static TEST_INIT_CALLS: AtomicU32` and a fresh, test-local `OnceLock<()>` (or `OnceLock<u32>`), then spawn several `std::thread`s synchronized on a `std::sync::Barrier` so they all call `.get_or_init(...)` at the same instant; the closure increments `TEST_INIT_CALLS` before returning. Assert `TEST_INIT_CALLS.load(Ordering::SeqCst) == 1` after all threads join. This proves `OnceLock::get_or_init`'s exactly-once-under-race guarantee holds for the same pattern `ocr_engine()` uses, deterministically and independently of test execution order or real ONNX model load time — no shared global state, no test-isolation fighting, no `serial_test` dependency needed.
