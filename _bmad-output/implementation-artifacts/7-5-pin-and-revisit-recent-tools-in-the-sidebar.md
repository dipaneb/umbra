# Story 7.5: Pin and revisit recent tools in the sidebar

Status: done

## Story

As a privacy-conscious developer,
I want to pin frequently-used tools and see recently-opened ones,
so that I can reach my most common tools without scanning the full list.

## Acceptance Criteria

1. Given a tool in the sidebar's full list, When I trigger its pin action (a control revealed on hover/focus, keyboard-operable per NFR5), Then it moves into a "Pinned" section at the top of the sidebar, persisted via a new `shell.pinnedTools: string[]` key in the `settings` store (AD-10).
2. Given tools I've opened recently, When they aren't pinned, Then a "Recent" section (last 5) appears between Pinned and the full list, tracked automatically from navigation — no manual action — via a new `shell.recentTools: string[]` key, most-recent-first, with pinned tools excluded to avoid duplication.
3. Given the full tool list, When Pinned/Recent sections exist, Then every tool still appears in the full list below them (AD-5 — nothing hidden, just grouped), matching `EXPERIENCE.md`'s "full tool list *plus* a pinned/recent section," not a replacement.
4. Given a pinned tool, When I unpin it, Then it returns to the full list and may reappear in Recent per the normal recency rule.
5. Given Story 7.6's Settings persisted-data enumeration, When it lists `shell.*` keys, Then `pinnedTools` and `recentTools` appear there with their own per-item reset — consistent with AD-10's transparency contract, not a special case.
6. Given the Settings pane (Story 7.6), When its Appearance/General section is viewed, Then two independent toggles exist — "Show pinned tools" and "Show recent tools" (each default on) — persisted as `shell.pinnedToolsVisible` / `shell.recentToolsVisible` in the `settings` store, separate from the `pinnedTools`/`recentTools` data arrays themselves.
7. Given either toggle is switched off, When the sidebar renders, Then that section is hidden, but its underlying data keeps being tracked and persisted unchanged — unpinning nothing, still recording navigation into `recentTools` in the background — so switching the toggle back on immediately shows accurate, undisturbed state rather than an empty list. The toggle controls visibility only, never data.

**Not covered by this story:** the *sectioned, token-styled home* for the two new checkboxes in Settings — Story 7.6's job, per AC6's "Given the Settings pane (Story 7.6)" wording and 7.6's own AC1 ("the pinned/recent visibility toggles from Story 7.5 also live here [Settings' Appearance section]"). This story does build the two checkboxes themselves, minimal and unstyled, directly in the current flat `SettingsView.vue` — see the resolved scope note in Dev Notes, which follows Story 7.2's directly analogous precedent (7.2 shipped a working `<select>` theme toggle into the flat `SettingsView.vue` with a "this control's sectioned home is Story 7.6's job" comment; 7.5 does the same for these two checkboxes). Per-item reset UI for any of this story's four new `shell.*` keys is Story 7.6's job (AC5). The three-section "Pinned / Recent / All Tools" mockup (`step4.3-mockups-*.png`, Screen 01) is explicitly disclaimed by `EXPERIENCE.md` as illustrative-only, not locked IA — this story's actual source of truth for section order/behavior is the AC text above, not the mock.

## Dev Notes

- **Architecture fit:** Pure frontend change — a `settings` store addition (four new `shell.*` keys, AD-10) plus `AppSidebar.vue` restructuring and one new line in `main.ts`'s existing router hook. No `src-tauri/` changes, no new dependency (`@phosphor-icons/vue` already installed since Story 7.1). AD-5 stays intact: pin/recent state is pure `id` membership in `settings`, never written into `ToolRegistryEntry` itself — the registry remains the single source of tool *metadata*, `settings` the single source of this story's user *state* (AD-6).
- **This is the first array-typed persisted `shell.*` key in the codebase.** Every existing key (`restoreSessionEnabled`, `lastTool`, `windowGeometry`, `themeOverride`, `sidebarCollapsed`) is a scalar or a single object — there's no direct precedent to copy for reading/validating a persisted array. Task 1 defines the read-time validation (drop anything that isn't a string) explicitly so this isn't invented ad hoc mid-implementation.
- **The single highest-value resolved ambiguity in this story: AC6/AC7's split between this story and Story 7.6, resolved by direct precedent, not first-principles guessing.** AC6 names "the Settings pane (Story 7.6)" only as the owner of the checkboxes' *permanent, sectioned, token-styled home* — not as the owner of building any control at all. The controlling precedent is Story 7.2 (dark-mode), which faced the identical shape of split and resolved it by shipping a real, working, unstyled `themeOverride` `<select>` directly into the current flat `SettingsView.vue`, with an inline comment ("Minimal mechanism only — this control's sectioned, token-styled home is Story 7.6's job, not this one's") — confirmed still present in the shipped code. Story 7.6's own AC1 text reinforces the same relationship for this story specifically: "the pinned/recent visibility toggles from Story 7.5 also live here [Settings' Appearance section]" — implying the toggles already exist by the time 7.6 runs, 7.6 just relocates/restyles them. **Resolved: 7.5 builds two real, working, unstyled checkboxes in `SettingsView.vue` (Task 4) plus the two boolean store keys and the sidebar's conditional show/hide logic (Task 1, Task 3); 7.6 later gives those same checkboxes a sectioned, token-styled home**, exactly mirroring 7.2→7.6's relationship for the theme control. Do not defer the checkboxes themselves to 7.6 — that would leave AC7 unverifiable through the app's own UI until 7.6 ships, unlike every other Epic 7 story's ACs, which are fully exercisable by the story that introduces them.
