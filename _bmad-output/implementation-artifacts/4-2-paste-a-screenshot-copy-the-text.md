# Story 4.2: Paste a screenshot, copy the text

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a privacy-conscious developer,
I want to paste a screenshot and copy out its text in seconds,
so that the everyday "error dialog → search/share as text" flow is instant and offline.

## Acceptance Criteria

1. **Given** an image on the clipboard, **when** I paste (⌘V) with the Bucket active, **then** the image is dispatched like a drop to the Bucket's registry-declared handler, crossing the bridge via Tauri's raw IPC body — the sanctioned AD-15 exception for clipboard image bytes (FR23, AD-14).
2. **Given** a completed extraction, **when** the result displays, **then** the text is editable in place and copyable with one click via the shell clipboard service (FR24, FR4).
3. **Given** a typical error-dialog screenshot on Apple Silicon, **when** extraction runs (after first-use initialization), **then** it completes in under ~3 seconds, verified by measurement in the story (FR24).
4. **Given** a new drop or paste while an extraction is in flight, **when** results return, **then** the newest request wins and the superseded result is dropped on arrival (AD-16).

**Explicitly out of scope for this story** (later stories own them):
- Explicit "no text found" / corrupt-image messaging beyond the plain structured `ToolError` this story already surfaces — FR26, Story 4.3's AC.
- The formal NFR1 network-monitor tour proving zero network activity — Story 4.3's AC.
- Racing-first-use-initialization test coverage for the OCR engine singleton — already built by Story 4.1, formally tested by Story 4.3.

## Dev Notes

- **The load-bearing finding of this story, verified against ground truth this session (installed `node_modules/@tauri-apps/plugin-clipboard-manager/dist-js/index.d.ts` and `@tauri-apps/api/image.d.ts`, not docs):** `readImage()` returns already-decoded raw RGBA pixels (`Image.rgba()` + `Image.size()`), not a compressed PNG/JPEG/WebP byte stream. Story 4.1's `OcrEngine::extract_text(&self, image_bytes: &[u8])` was built for compressed, format-sniffable bytes (`image::load_from_memory`). This story's Task 1/2 must resolve that mismatch explicitly — it's a real architectural gap neither the epics nor the spine anticipated in this much detail, not a hypothetical to skip past.
- **AD-16's amendment (2026-08-04, Epic 3 retrospective) was written specifically anticipating this story.** It names `registry.getLatestWinsRunner(toolId)` as the required pattern for "Epic 4's Bucket tool (drag-drop and clipboard-paste both dispatching to the same registry-declared handler, per Story 4.2's AC)," citing `HashView.vue` as the reference implementation. Story 4.1 deliberately built nothing that would preempt this — its own Dev Notes flag that this story (4.2) is the one that adds the second write-trigger. Route the paste dispatch through the exact same `getLatestWinsRunner("bucket")` instance the drop dispatch already uses. [Source: `ARCHITECTURE-SPINE.md` AD-16 amendment]
- **AD-15's raw-IPC-body exception is explicitly named for this exact case** ("clipboard-pasted image bytes via raw IPC body" is the one sanctioned exception to "files cross IPC as paths"). This is the first command in the codebase using `tauri::ipc::Request` directly instead of typed command parameters — budget real verification time here, the same way Story 4.1 budgeted extra time for its own "first of its kind" patterns (bundled resources, `AppHandle`-needing commands).
- **Regression risk unique to this story, not present in any prior Bucket work:** a naive global ⌘V listener would break ordinary text-paste across the entire app (every tool's inputs, and this story's own new editable output field). No prior story's keyboard handling (⌘K) had this problem, because nothing else in the app currently listens for a key combo that's *also* the OS's universal paste shortcut. Treat this as a hard constraint, not a nice-to-have — see Task 4 and Task 6's regression test.
- **Capabilities/ACL gap, confirmed via the vendored plugin's own permission TOML, not guessed:** `clipboard-manager:allow-read-image` must be added to `src-tauri/capabilities/default.json`; it is not covered by the existing `allow-read-text`/`allow-write-text` entries.
- **Reuse, don't duplicate:** the OCR engine singleton (`OCR_ENGINE`, `ocr_engine()`), the `OarOcrEngine` adapter, `OcrOutcome`, `MAX_INPUT_BYTES`, and `registry.getLatestWinsRunner`/`dropArgsProviders`-style registry wiring all already exist from Story 4.1 and this project's established shell patterns — this story extends input paths and UI, it does not rebuild plumbing.
- **NFR4/FR26 boundary, same as Story 4.1:** this story must not crash or hang on a malformed clipboard payload (map to `ToolError`), but polished "no text found" / "corrupt image" UX copy is Story 4.3's AC, not this one's.
- **Cross-platform screenshot formats are already normalized before this story's code ever runs — confirmed by reading the plugin's own Rust source, not assumed.** `tauri-plugin-clipboard-manager`'s `read_image()` (`desktop.rs`) delegates to the `arboard` crate, whose `get_image()` absorbs every OS's native clipboard image representation (macOS TIFF/PNG pasteboard data, Windows CF_DIB/CF_DIBV5, Linux X11/Wayland PNG targets) and always returns `ImageData { width, height, bytes }` with `bytes` already decoded to RGBA8. `Image::new_owned()` just wraps those bytes unchanged — no format branch exists in the plugin, and none needs to exist in this story's code either; the RGBA-not-compressed-bytes finding above (Task 1) holds identically on all three platforms. AD-11's CI matrix (`cargo test` required on `ubuntu-latest`/`windows-latest`/`macos-latest`) gives real cross-platform proof of Task 2's RGBA-decode logic even though no CI runner can drive an actual OS paste gesture — that stays a manual check (Task 7), same limitation this project already accepts for drag-and-drop.
- **Incidental finding, not applicable to this story's actual code path but worth recording:** `desktop.rs`'s `Clipboard::read_image()` carries an explicit warning that calling it off the main thread matters on Linux ("underlying libraries may deadlock... when trying to copy data copied from this app"). This story's frontend calls the plugin's JS `readImage()` (an IPC command into the plugin's own already-correct implementation), so it doesn't trigger this directly — flagged only in case any future Rust-side code in this codebase ever calls `arboard`/the clipboard API directly instead of going through the plugin's command.

- **Task 3, the real architectural discovery of this story:** an `async fn` command taking `tauri::ipc::Request<'_>` directly cannot satisfy `respond_async_serialized`'s `Send + 'static` future bound — Rust's async-fn lifetime elision makes the returned future's opaque type capture `Request`'s borrowed lifetime regardless of whether the body actually holds the reference across an `.await` point (this is the documented limitation behind tauri-apps/tauri#2533, confirmed by reading the `tauri-macros` codegen and `InvokeResolver::respond_async_serialized`'s bound directly, not by trusting the issue title). Resolved with a plain (non-`async`) `#[tauri::command(async)]` function — `request: Request<'_>` is extracted into owned data (`Vec<u8>`, two `u32`s) synchronously before any future is constructed, then a `impl Future<Output = Result<...>> + Send + 'static` built only from that owned data is returned. Validated empirically via `cargo check` and the full IPC-round-trip tests (Task 6), not just reasoned through — this is exactly the kind of thing the story's own Dev Notes warned not to skip verifying.
- Width/height cross the bridge as `x-image-width`/`x-image-height` request headers, parsed via `request.headers().get(name)?.to_str()?.parse::<u32>()` — the header approach researched pre-implementation held up with no need for the binary-prefix fallback.
- `MAX_INPUT_BYTES` is reused as-is against the raw RGBA buffer's length (not a new, smaller constant) — a deliberate scope choice per the story's own note: uncompressed RGBA is denser than compressed bytes of the same size (100MB caps out around 25 megapixels), but that's a reasonable default for FR24's "typical screenshot" scope, not an oversight.
- **New dev-dependency:** `image = "0.25"` added to `src-tauri/Cargo.toml` under `[dev-dependencies]` — needed to decode the shared PNG fixture into raw RGBA for the new command's tests. Same crate + version `umbra-core` already depends on directly (not a second image-handling library); `Cargo.lock` updates accordingly, no new transitive dependency surface.
