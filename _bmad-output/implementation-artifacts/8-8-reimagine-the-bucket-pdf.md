# Story 8.8: Reimagine the Bucket — PDF

## Story

As the developer,
I want to reconsider the PDF tool's feature set through open discovery before redesigning its UI,
so that the redesign reflects a deliberately chosen scope, not a visual reskin of whatever shipped first.

4. **Given** Story 8.7 handed this story **two items in writing**, **when** the decision record completes, **then** each has an explicit named decision — a fold-in with a shape, or a deferral with a reason. These are not discovery inputs to be weighed for relevance; they are inherited obligations recorded so they would be hand-offs rather than hopes (`8-7-ocr-decision-record.md`, *Upstream corrections owed* #5 and *Command and error-code renames*):

   - **4a — The `bucket_*` → `pdf_*` rename.** Three commands (`bucket_merge_pdfs`, `bucket_extract_pdf_pages`, `bucket_extract_pdf_text`) and five error codes (`bucket-pdf-corrupt`, `bucket-pdf-encrypted`, `bucket-pdf-too-few-files`, `bucket-pdf-invalid-range`, plus the two **shared** codes below) still carry the scaffold's name. **AD-3 requires `<tool>_<verb>`, and there is no tool called bucket** — the registry entry was deleted by 8.7. 8.7 renamed only its own so the verbatim PDF/Images move stayed mechanically verifiable; the debt was accepted on the record and assigned here. **The shared-code trap, stated explicitly:** `bucket-input-too-large` and `bucket-internal` are raised by **both** `commands/pdf.rs` and `commands/image.rs` (8.7 verified this and deliberately left the pair live rather than renaming across two tools mid-move). 8.8 cannot unilaterally retire them — it can add `pdf-*` codes at its own call sites and leave the `bucket-*` pair for Images, or coordinate with 8.9. **Decide which, and say so**, or 8.9 inherits an ambiguity instead of a decision.
   - **4b — PDF tier 2: make the scan case honest.** `noTextInPdf` currently reads *"No text was found in this PDF."* For a scanned page that is **true and useless** — the text is visibly right there as pixels, and the sentence invites the user to conclude the tool is broken. The proposed replacement is on the record: *"This PDF is a scan — its pages are images, so there's no text layer to read."* `lopdf` is already in the tree and can distinguish "no text layer" from "genuinely empty document". **Tier 3 (rasterize + OCR the page) is cut**, with a full cost sheet, to [#132](https://github.com/dipaneb/umbra/issues/132) — do not reopen it in this story's discovery without reading that cost sheet first (`8-7-ocr-decision-record.md`, *The PDF tiers*). **The sequencing argument that decided it:** ship tier 2's honest message, see how often it fires in real use, *then* decide whether to spend a doubled bundle and a second native C++ dependency on tier 3.

5. **Given** the PDF tool accepts **no drag-and-drop**, while `EXPERIENCE.md:82` states that it does, **when** the decision record completes, **then** it **re-decides** the question on today's facts and — if drop is adopted — names the **shell** change it requires. **This is a re-decision, not the discovery of an oversight**, and framing it correctly is the point of this AC:

   - **Story 6.1 decided this deliberately and recorded why, at length.** Its own AC-preamble flags that AC1/AC2/AC3 all say *"dropped"* and states the tool would not wire PDF through the AD-14 dispatcher, *"the same way Story 5.2 recorded its 'no manual Check for Updates button' decision — it is not a silent reinterpretation."* **Read `6-1-work-pdfs-locally-merge-split-extract.md`'s Dev Notes section *"Why PDF input bypasses the AD-14 drop dispatcher entirely"* before forming a view.** Do not re-derive it, and do not report it as a bug that was missed.
   - **But one of its three load-bearing reasons is now dead, and that is what reopens the question.** 6.1 reasoned that *"a tool's registry entry declares exactly **one** fixed drop-handler command name (AD-5/AD-14) — there's no way for 'drop a PDF' and 'drop an image' while the Bucket is active to route to two different commands."* **Story 8.7 deleted the `bucket` entry and gave PDF its own.** There is no longer any routing ambiguity to avoid: a `pdf` entry can declare one handler that only ever receives PDFs. This is the *"rationale died, decision survived"* pattern (8.6's lesson) — except here it is the rationale for a **deliberate omission**, so the honest question is whether the decision survives its own reasoning.
   - **Tier 1 sharpens it further.** 8.7 made the OCR tool answer a dropped PDF with *"PDFs open in the PDF tool"* — the app now actively redirects a drop gesture to a tool that cannot receive one. 6.1's fallback position (*"a PDF dropped on the Bucket fails honestly via `bucket-unsupported-format`"*) has been replaced by a signpost pointing at a closed door.
   - **6.1's other two reasons still stand and still cost.** Split/extract needs a page-range parameter *"supplied as a distinct step, not inferred from a bare drop event"*, and multi-file merge needs a dispatcher change.

   **The shell constraint, which 6.1 already identified and which has not changed.** `DropZone.vue:141` does `const path = routing.paths![0]`. `routeDrop()` returns the full `paths` array, and the dispatcher **discards every file after the first**. Dropping several PDFs onto a merge queue is the most obvious drop use for this tool, and today it would pass exactly one. Multi-file drop is therefore an **AD-14 shell change** (`src/shell/DropZone.vue`, `src/shell/dropZone.ts` + its spec) affecting every tool's drop contract, not a tool-island change — the same class of boundary stretch 8.7 had to make explicit, and it must be named in Task 2a's AC set before being touched. **Single-file drop needs no shell change**: `registry.dropArgsProviders` (present since Story 2.2) already lets a view supply extra arguments at drop time, which covers the page-range objection for a single dropped file. The merge queue is where the real cost sits, and the two cases can be decided separately.

   **Whatever is decided, `EXPERIENCE.md:82` must end this story true.** It currently reads *"Bucket (OCR) and **PDF** tools accept drag-and-drop of files/screenshots as an alternative to a file picker"* — written 2026-08-15, five days **after** 6.1 shipped its picker-only decision, so the UX spec was authored against an intent the code had already declined. Either the tool gains drop, or that line is corrected. It does not get to stay ambiguous through a story whose whole subject is this tool.

### Group A — Core (`crates/umbra-core/src/pdf.rs`)

8. **Given** a PDF's bytes, **when** the core is asked for its page count, **then** it returns `get_pages().len()` as a `u32` without extracting any text, and a document that fails to load returns a `ToolError` rather than a count of zero — *"zero pages"* and *"could not read this file"* are different answers and must not collapse.

9. **Given** a loaded document, **when** per-page text is requested, **then** the core uses `extract_text_chunks_with_limit` (**not** the unbounded `extract_text_chunks`), reusing the same bomb-safe decompression cap the existing `extract_text` path already applies, and returns one result **per page** so a single unreadable page cannot fail the whole document.

10. **Given** per-page text, **when** the core classifies the document, **then** it returns exactly one of three states — **`Scanned`** (the document has pages and **no** page yields non-whitespace text), **`Partial`** (at least one page yields text), **`Empty`** (the document has no pages) — and this classification is **core-owned**, not re-derived in the view, because it is the same judgement `noTextInPdf` depends on.

11. **Given** a set of 1-indexed page numbers, **when** pages are deleted, **then** validation happens **in core before** calling `delete_pages`, exactly as `extract_page_range`'s does and for the same reason: `lopdf`'s `delete_pages` silently no-ops on out-of-range numbers rather than erroring (re-verified against vendored 0.45.0 source this story), so core is the only layer that can turn a bad request into an error. **Deleting every page is rejected** — a zero-page PDF is not a useful output.

12. **Given** a set of page numbers and a quarter-turn count, **when** pages are rotated, **then** the core writes `/Rotate` on each page dictionary as an integer normalised to `0 | 90 | 180 | 270`, **adding to any existing `/Rotate`** rather than replacing it (a page may already carry one), and a page that inherits `/Rotate` from an ancestor node has the resolved value materialised on the page itself before writing — otherwise the rotation is silently wrong for exactly the documents gap #13 already describes.

13. **Given** a permutation of a document's pages, **when** they are reordered, **then** the core rewrites the page tree so the new order is the document's real page order, and the result is **verified by extracting text and asserting position**, not by asserting that the file parses — matching how `merge_documents` is already tested.

14. **Given** every `ToolError` this module raises, **when** the rename lands, **then** the four PDF-only codes are `pdf-corrupt`, `pdf-encrypted`, `pdf-invalid-range`, `pdf-too-few-files`, **and** `pdf-too-few-files` / `pdf-invalid-range` carry their runtime values in the structured `context` field rather than baked into the message prose — this is what makes them eligible for `TRANSLATABLE_CODES` under 8.6's criterion (AC38), and it is the option 8.7 did not have for its wrapped-library errors.

15. **Given** the dependency, **when** the story completes, **then** both `Cargo.toml`s pin `lopdf = { version = "0.45", default-features = false }`, `Cargo.lock` resolves 0.45.0, and **`default-features = false` carries an in-file comment stating the new reason** — 0.45.0's defaults are `["chrono-clock", "rayon"]`, so the `time` 0.3.45 break that originally forced the flag can no longer occur, and the flag is kept because those features are unused here. A future reader must not delete it believing the workaround is stale, nor keep it believing a fixed break is live.

### Group B — Command layer (`src-tauri/src/commands/pdf.rs`, `src-tauri/src/lib.rs`)

16. **Given** AD-3's `<tool>_<verb>` rule and the fact that no tool called `bucket` exists, **when** the rename lands, **then** every PDF command is `pdf_*` — `pdf_merge`, `pdf_extract_pages`, `pdf_extract_text` — registered under those names in **both** `lib.rs:21`'s `use` line and its `generate_handler!` list, with **no** `bucket_*` alias left behind.

17. **Given** the new verbs, **when** they cross IPC, **then** each is its own `#[tauri::command] pub async fn` on `spawn_blocking` (AD-4) returning `Result<T, ToolError>` — `pdf_open` (path → page count + classification), `pdf_page_text` (path + page range → per-page text), `pdf_delete_pages`, `pdf_rotate_pages`, `pdf_reorder_pages` — and every command that produces a file takes an `output_path` and writes server-side via `fs_helper::write_file_bytes`, **never** returning bytes across the JSON IPC bridge (AD-15).

18. **Given** `bucket-input-too-large` and `bucket-internal` are raised by **both** `commands/pdf.rs` and `commands/image.rs`, **when** the rename lands, **then** `commands/pdf.rs` raises **new** `pdf-input-too-large` and `pdf-internal` codes at its own call sites, and the `bucket-*` pair is **left untouched and still live for the Images tool**. This is duplication, not migration — 8.7's own precedent — and **Story 8.9 owns retiring the pair**. `commands/image.rs` is not edited by this story.

19. **Given** `check_file_size()`, **when** an oversize file is passed to any command, **then** it is rejected **without reading the file**, and the existing per-command tests proving that for merge and extract-text are extended to cover every new command — the guard is worthless if a new verb forgets to call it.

### Group C — The view (`src/tools/pdf/PdfView.vue` and its island)

20. **Given** the tool is opened with no document, **when** it renders, **then** it shows **one** resting surface — a dashed drop target (the HashView/OcrView drop language, used literally) carrying the drop label, a `Choose PDF…` `AppButton`, and a sentence stating that several PDFs can be dropped to merge them. There are **no** longer three independent file pickers.

21. **Given** a document is opened, **when** the surface renders, **then** it shows the file's **basename**, its **page count**, and a list of its pages — each row carrying **a rendered thumbnail of that page** *and* that page's first line of text. **Amended 2026-09-10:** this AC previously specified a text-only list and stated that thumbnails were out of scope. The developer rejected that — thumbnails serve **recognition** (*"the table page"*, *"the signature page"*), which a text label cannot, and the text list is sparse because heading-bearing pages are a minority. The rasterizer is now in scope (AC43–AC47). The text label is **kept** alongside the thumbnail: a heading you can read beats a picture of one, and it is the fallback when rendering is unavailable (AC46).

22. **Given** the page list, **when** it is driven from the keyboard alone, **then** every selection operation is reachable — arrow keys move row focus, `Space` toggles the focused row, `Shift`+click and `Shift`+arrow extend a range, `⌘A` selects every page when focus is inside the list — and the selected count is exposed as an announced status. **NFR5 admits no exceptions**; a selection model that needs a mouse fails this AC outright.

23. **Given** a non-empty selection, **when** the verb bar renders, **then** it offers exactly **Extract to new PDF**, **Rotate**, **Move up**, **Move down** and **Delete**, each acting on the selection; **Delete uses the Default (black) treatment, not destructive red** — `DESIGN.md:149` rules that removing pages before saving is low-stakes and reversible, and that ruling is not re-derived here. With an empty selection the bar shows the document-scoped actions instead (**Read text**, **Merge with…**).

24. **Given** merge takes *many* documents while every other verb takes *one*, **when** several PDFs are dropped or chosen, **then** the view enters a **merge queue** state — a distinct, mutually-exclusive state of the same view, **not** a tab and **not** a second surface — listing each document by basename with its page count, reorder and remove controls, and a single **`Merge PDFs`** button using the **`primary`** `AppButton` variant. `DESIGN.md:183` names *"Merge PDFs"* as the worked example of that variant and permits **one primary per screen at most**; this is that one.

25. **Given** any file path shown in the UI, **when** it renders, **then** only the **basename** is displayed, with the full path available via `title`. **No absolute path reaches the screen.** `CLAUDE.md` treats `/Users/<name>/…` as personally-identifying and this repo enforces that on its own commits; a public-portfolio app must not print it in a screenshot.

26. **Given** the view's heading structure, **when** it renders, **then** heading ranks descend without skipping. Today the view goes `<h1>` → `<h3>` with no `<h2>` — introduced when Story 8.7 promoted the section's `<h2>` to this routed view's `<h1>` and left the inner headings untouched. NFR5.

27. **Given** the view is 100% pre-Epic-7, **when** the redesign lands, **then** it contains **no hardcoded colour, radius, font-family or `em`-based spacing** — every value resolves through `tokens.css` — and **no plain `<button>` where an `AppButton` or the 24px ghost icon-button anatomy applies.**

28. **Given** any copy affordance, **when** a copy succeeds, **then** it confirms via `useCopyFeedback` (hoisted to `src/shell/` by Story 8.7 — an import, not an infrastructure decision), and marks the key **only after** the clipboard write resolves.

29. **Given** an operation of unbounded duration, **when** it is in flight, **then** the view renders a real in-flight state **and** announces start and completion through a live region — `EXPERIENCE.md:70` states this as the general rule, not an OCR-only exception. **No determinate progress bar**: neither `lopdf` nor the page-text pass reports a fraction, and a bar filling at an invented rate is the tool bluffing about its own internals (8.7's ruling, applied here).

30. **Given** an operation that writes a file, **when** it completes, **then** the view says so, naming the written file by **basename** — today merge and extract-pages write a file and say nothing at all, and the user's only evidence is opening Finder (`deferred-work.md:154`, assigned to this story by name).

31. **Given** an error, **when** it renders, **then** it appears with the operation that raised it and does not remove the way back in. The single shared `pdfError` ref is replaced: today an error raised by merge is silently cleared by an unrelated click in another flow.

32. **Given** AD-16's rule — *one runner per independent piece of state* — **when** the container changes, **then** runner scoping is **re-derived, not carried forward**, and the in-file comment justifying it is rewritten. The current comment reasons against `registry.getLatestWinsRunner("bucket")` and an in-flight OCR extraction, **neither of which exists**. The resolved shape: **two** local runners — one for the open document's read state (open, page text), one for write operations (extract/delete/rotate/reorder/merge) — because a page-text pass and a save must not supersede one another. AD-16's amendment also binds: a runner fences against a newer **request**, not newer **input**, so any task publishing derived state mid-flight re-checks its snapshot via `isLatest()`.

### Group D — Drag-and-drop (shell, AD-14 — named, not absorbed)

33. **Given** a tool may need more than one dropped file, **when** the registry entry declares it, **then** `drop` accepts an **additive** `multiple: true` flag, and **only** the `pdf` entry sets it. Tools that do not declare it receive exactly today's behaviour.

34. **Given** the dispatcher at `DropZone.vue`, **when** a drop lands, **then** a `multiple` tool's handler receives **`paths`** (the full array) and every other tool's receives **`path`** (the first, as today), and `registry.dropSourcePath` is widened in the same additive way. **This is the shell change this story owns**: `registry.ts:262` types the published signal as `{ toolId, path: string }` with **two live consumers** — `HashView.vue:502` and `OcrView.vue:360` — and both must keep working unchanged.

35. **Given** the `pdf` registry entry, **when** the story completes, **then** it declares `drop` with `multiple: true`, and its aliases cover the new verbs in **both** locales (`rotate`, `delete`, `reorder`, `pivoter`, `supprimer`, `réorganiser` alongside the existing five). `name: "PDF"` **stays** — Story 8.7 marked it provisional; leaving it is the recorded decision, not an oversight.

36. **Given** `dropZone.spec.ts:126` constructs its "tool that refuses drops" fixture as `{ ...ocrTool, id: "pdf", drop: undefined }`, **when** PDF gains drop, **then** that fixture **no longer names `pdf`** — it names a tool that genuinely declares no `drop`. The test passes either way, which is precisely why it must be caught deliberately: an assertion that keeps passing while ceasing to describe the app is the failure mode Story 8.7's review found seven instances of.

### Group E — The third inherited hand-off (AC4c)

37. **Given** Story 8.7's AC25 hands this story *"carrying the file across"*, **when** a PDF is dropped on Image to Text, **then** its message becomes an **offer that carries the file** — accepting it opens the PDF tool **with that document already loaded**, not an empty view demanding the user re-pick the file they just dropped. The developer's 2026-09-07 reason for deferring this (*"it cannot route to somewhere that is not built yet"*) is retired by AC20/AC21. **The mechanism is shell-owned** (AD-6: neither tool reads the other's state) — a one-shot signal in the registry store, published before the route change and consumed on mount, the same shape `dropSourcePath` already uses.

### Group F — Error voice and localisation (AD-13)

38. **Given** 8.6's criterion — *a fixed, value-free sentence we wrote ourselves* — **when** it is applied per code, **then** `pdf-encrypted` joins `TRANSLATABLE_CODES`; `pdf-corrupt` does **not** (it wraps `lopdf`'s own error text); and `pdf-too-few-files` / `pdf-invalid-range` join it **only because AC14 moved their runtime values into `context`**. This requires `toolErrorMessage()` to pass `err.context` as `t()` params — a `toolError.ts` change, with `toolError.spec.ts` updated alongside it (Story 8.7's review flagged the spec being modified while only the `.ts` was listed). **Every exclusion is recorded in the file's own comment with its reason; "not yet done" is not an acceptable reason.**

39. **Given** every new user-visible string, **when** the story completes, **then** `en` and `fr` are at full parity in the same commit (AD-13), and any string containing `{` or `}` uses the `{'{'}` / `{'}'}` escape — `locales.spec.ts` compiles every string and will catch it, but it is written correctly the first time.

40. **Given** the honest scan message, **when** a `Scanned` document is opened, **then** the tool says *"This PDF is a scan — its pages are images, so there's no text layer to read."* and **does not** say "no text was found", which is true and useless for a page whose text is visibly present as pixels. Page operations remain available and are not disabled by this state.

### Group G — Documentation and upstream

41. **Given** `docs/release-checklist.md:133` documents the PDF tool's manual QA step against Story 6.1's three actions, **when** the redesign lands, **then** that step describes what actually ships, and the AD-7 network-audit procedure's PDF entry stays accurate.

42. **Given** `src-tauri/src/commands/image.rs:46` and `:66` reference `bucket_merge_pdfs` and `bucket_extract_pdf_text` **in comments**, **when** the rename lands, **then** those references are stale. **This story does not edit that file** (AC18 — it is Story 8.9's), so the staleness is **recorded here and in the decision record as owed to 8.9**, not silently left for a future reader to trip over.

### Group H — Page rendering (`pdfium-render`) — added 2026-09-10

43. **Given** the tool renders page previews, **when** the dependency is added, **then** it is **`pdfium-render` 0.9.4** with **default features** (`pdfium_latest`, `image_latest`, `thread_safe`) and **explicitly not** the `static` or `bindings` features. On the default path `build.rs` is a **no-op** and the crate compiles **no C++** — it `dlopen`s a prebuilt library at runtime via `libloading`. Enabling `static` would reintroduce exactly the build-time C++ exposure that blocked Story 4.1 (`clipper2c-sys`), so the exclusion is deliberate and carries an in-file comment saying why.

44. **Given** AD-2 forbids `umbra-core` touching the filesystem, **when** rendering is implemented, **then** the `Pdfium` handle is owned by **`src-tauri`**, loaded **once and lazily** — never on the launch path, because it is a native library load and NFR2's 2 s cold launch is not negotiable (AD-4). **`crates/umbra-core/src/pdf.rs` gains no rasterize function** and keeps every structural operation; structure code never reaches for Pdfium and rendering never reaches for `lopdf`.

45. **Given** a 400-page document, **when** previews are produced, **then** they are rendered **per visible range**, not all at once, at a bounded thumbnail width, and the result crosses IPC as an encoded image rather than raw RGBA. **AD-15's ceiling binds:** a thumbnail is small, but four hundred of them are not — the volume is the constraint, and the fetch policy is the same bounded, streaming one AC9/AC29 already establish for page text.

46. **Given** the library is loaded at **runtime**, **when** it is missing, unreadable, or its ABI does not match the crate's pinned `pdfium_7881` feature, **then** the tool **degrades to the text-derived page list and says why** — it does not crash, render blank frames, or silently show an empty list. NFR4 admits no crash and no silently-wrong result, and a runtime-bound library is the one dependency in this app that can fail *after* a successful build.

47. **Given** the prebuilt libraries come from **`bblanchon/pdfium-binaries`** — a community project, not Google — **when** they are bundled, **then** the fetch is **checksum-pinned**, the provenance is named in `docs/release-checklist.md`, and the **AD-7 network audit is re-run** for the new dependency (`cargo tree -i reqwest`), since AD-7 states that any dependency change reopens Story 4.3's audit. Pdfium itself is BSD-3-Clause and `pdfium-render` is MIT OR Apache-2.0 — both cleared — but **the licence being clean is not the same as the build being trusted**, and this AC exists to keep those two questions separate.

### Known gaps in the shipped PDF path — each needs an explicit call in the decision record

Treat it as a re-decision with a documented prior, not as a defect.
2. **No success confirmation after any completed operation** (`deferred-work.md:154`, open since Story 6.2's code review). Merge and extract-pages write a file and then say **nothing at all** — no "Saved", no path echo, no state change. Adopting it here is now an import, not an infrastructure decision.
5. **Zero design-token adoption, zero `AppButton`.** The whole view is pre-Epic-7. **`DESIGN.md` names this exact tool twice, in binding terms:** (a) `:183` — *"Button — Primary/Signature… One per screen, at most — this is the 'main CTA,' **e.g. 'Merge PDFs.'**"* This view's Merge button **is** the worked example of the primary variant in the design system. Both are already-made design decisions this tool has never honoured; do not re-derive them.
6. **Raw absolute filesystem paths rendered in the UI** (`<p>{{ pdfExtractPagesPath }}</p>`, and every merge `<li>`). Long, unwrapped, and — given `CLAUDE.md`'s standing rule about `/Users/<name>/…` being personally-identifying — a surface a screenshot in a public README or a demo would leak a real username through. Basename-with-tooltip is the obvious alternative. **Not just cosmetic in this repo's context.**
7. **The client-side page-range guard cannot know the page count**, so `end > totalPages` round-trips to Rust to fail. The tool never tells the user how many pages the document has, before or after choosing a file — the single cheapest piece of information the merge and range flows both lack, and `lopdf`'s `get_pages()` already computes it.
8. **`bucket-pdf-*` codes are absent from `TRANSLATABLE_CODES`** — a French user gets English error text. **Apply 8.6's stated criterion per code** (*a fixed, value-free sentence we wrote ourselves*), the way 8.7's record did rather than blanket-adding: `bucket-pdf-encrypted` (*"PDF is encrypted with a password and cannot be processed"*) is **ours and value-free → qualifies**. `bucket-pdf-too-few-files` and `bucket-pdf-invalid-range` embed runtime counts in prose (`"got {n}"`, `"page range {s}-{e} is invalid for a {n}-page document"`) → **do not qualify as written**, but both are *our* sentences, so rewriting them to carry their values in params (or in the structured `context` field) is a live option 8.7 did not have for its wrapped-library errors. `bucket-pdf-corrupt` wraps `lopdf`'s own error text → **does not qualify**. Note 8.7's reframing: this is usually a **voice** gap before it is a translation gap.

Page *content* and *order* are correct (verified against `lopdf`'s vendored `processor.rs`). **Why it belongs in this story's discovery:** AC1 of 6.1 asked only for "a single merged PDF in my chosen order," and that bar was met — but a redesign that adds page thumbnails, rotation, or any structural editing raises the fidelity bar the limitation sits under, and NFR5's accessibility floor sits awkwardly against silently dropping `StructTreeRoot`. Fold in, defer, or disclose in-product — but call it.

### Architecture constraints binding this story

| Rule | What it binds here |
| --- | --- |
| **AD-1** | Core owns the transformation; locale/path/size formatting is view-owned. |
| **AD-2 / AD-15** | `umbra-core` never touches the filesystem. Files cross IPC as **absolute paths**; `src-tauri` owns every read/write. Byte arrays above ~64 KB never ride the JSON IPC bridge — hence `output_path` on merge and extract-pages. The clipboard-RGBA and asset-protocol exceptions are OCR's; **do not add a third here.** |

| **AD-4** | PDF work runs on the blocking pool (`spawn_blocking`) and never on the launch path — cold launch stays under 2 s (NFR2). |
| **AD-5** | The Tool Registry is the **only** source of tool metadata. A `drop` declaration, a rename or an alias change is a registry change (AC5). |
| **AD-6** | Tools are islands; no tool reads another's state. A multi-file drop would stretch this into the **shell**, as 8.7's did — name it in the AC set, do not absorb it. |
| **AD-7** | Zero network surface except the updater. **Any dependency change re-opens Story 4.3's network audit** — directly relevant to AC6/gap #11's `lopdf` question. |
| **AD-13** | Localization ships as one unit. Any new user-visible string needs `en` + `fr` in the same commit (gap #8). |
| **AD-14** | The shell owns OS I/O edges **exactly once**. `DropZone.vue` is the single generic dispatcher; tools never register document-level listeners. **Amended by 8.7's code review** to permit a *mount-scoped* `window` keydown listener for view-local shortcuts, with `OcrView.vue` named as the precedent and mount-scoping as the condition — read that amendment before adding any shortcut here. |
| **AD-16** | Latest-wins supersession; **one runner per independent piece of state.** The current single `runPdf` across three disjoint state groups is exactly the shape the amended rule questions. Also binding: *a latest-wins runner fences against a newer **request**, not newer **input*** — a view that writes derived state back from a request's own snapshot must re-check the snapshot still matches the live value. |

The single most relevant predecessor — same shared origin, same discovery shape, and it made the decisions this story inherits. Ten transferable lessons, in descending order of what they would cost to relearn:
