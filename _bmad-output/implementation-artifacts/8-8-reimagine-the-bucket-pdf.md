   - **But one of its three load-bearing reasons is now dead, and that is what reopens the question.** 6.1 reasoned that *"a tool's registry entry declares exactly **one** fixed drop-handler command name (AD-5/AD-14) — there's no way for 'drop a PDF' and 'drop an image' while the Bucket is active to route to two different commands."* **Story 8.7 deleted the `bucket` entry and gave PDF its own.** There is no longer any routing ambiguity to avoid: a `pdf` entry can declare one handler that only ever receives PDFs.    **The shell constraint, which 6.1 already identified and which has not changed.** `DropZone.vue:141` does `const path = routing.paths![0]`. `routeDrop()` returns the full `paths` array, and the dispatcher **discards every file after the first**. Dropping several PDFs onto a merge queue is the most obvious drop use for this tool, and today it would pass exactly one. Multi-file drop is therefore an **AD-14 shell change** (`src/shell/DropZone.vue`, `src/shell/dropZone.ts` + its spec) affecting every tool's drop contract, not a tool-island change — the same class of boundary stretch 8.7 had to make explicit, and it must be named in Task 2a's AC set before being touched. **Single-file drop needs no shell change**: `registry.dropArgsProviders` (present since Story 2.2) already lets a view supply extra arguments at drop time, which covers the page-range objection for a single dropped file. The merge queue is where the real cost sits, and the two cases can be decided separately.

Either the tool gains drop, or that line is corrected. It does not get to stay ambiguous through a story whose whole subject is this tool.

### Group A — Core (`crates/umbra-core/src/pdf.rs`)

8. **Given** a PDF's bytes, **when** the core is asked for its page count, **then** it returns `get_pages().len()` as a `u32` without extracting any text, and a document that fails to load returns a `ToolError` rather than a count of zero — *"zero pages"* and *"could not read this file"* are different answers and must not collapse.

9. **Given** a loaded document, **when** per-page text is requested, **then** the core uses `extract_text_chunks_with_limit` (**not** the unbounded `extract_text_chunks`), reusing the same bomb-safe decompression cap the existing `extract_text` path already applies, and returns one result **per page** so a single unreadable page cannot fail the whole document.

10. **Given** per-page text, **when** the core classifies the document, **then** it returns exactly one of three states — **`Scanned`** (the document has pages and **no** page yields non-whitespace text), **`Partial`** (at least one page yields text), **`Empty`** (the document has no pages) — and this classification is **core-owned**, not re-derived in the view, because it is the same judgement `noTextInPdf` depends on.

    **Amended 2026-09-13 at the Group A code review — what an *unreadable* page counts as:** a page whose text `lopdf` cannot decode at all (a font encoding it does not support, a content stream it rejects) is **evidence of nothing** and votes neither way. `Scanned` therefore requires **at least one readable-but-blank page**, and a document whose *every* page is unreadable reports **`Partial`** — the state whose rendering makes no claim — rather than `Scanned`, because AC40's "This PDF is a scan" sentence would be a false statement about a text document the tool simply could not read. The first build fell through to `Scanned` after the loop, which the review caught; the three-way shape is kept (decision: option (b) of three, chosen over a fourth `Unreadable` state that would need its own sentence in both locales).

11. **Given** a set of 1-indexed page numbers, **when** pages are deleted, **then** validation happens **in core before** calling `delete_pages`, exactly as `extract_page_range`'s does and for the same reason: `lopdf`'s `delete_pages` silently no-ops on out-of-range numbers rather than erroring (re-verified against vendored 0.45.0 source this story), so core is the only layer that can turn a bad request into an error. **Deleting every page is rejected** — a zero-page PDF is not a useful output.

12. **Given** a set of page numbers and a quarter-turn count, **when** pages are rotated, **then** the core writes `/Rotate` on each page dictionary as an integer normalised to `0 | 90 | 180 | 270`, **adding to any existing `/Rotate`** rather than replacing it (a page may already carry one), and a page that inherits `/Rotate` from an ancestor node has the resolved value materialised on the page itself before writing — otherwise the rotation is silently wrong for exactly the documents gap #13 already describes.

13. **Given** a permutation of a document's pages, **when** they are reordered, **then** the core rewrites the page tree so the new order is the document's real page order, and the result is **verified by extracting text and asserting position**, not by asserting that the file parses — matching how `merge_documents` is already tested.

14. **Given** every `ToolError` this module raises, **when** the rename lands, **then** the PDF-only codes are `pdf-corrupt`, `pdf-encrypted`, `pdf-invalid-range`, `pdf-too-few-files` — **amended 2026-09-11 (AC38's slice): a fifth, `pdf-cannot-delete-all-pages`, split off from `pdf-invalid-range`.** Deleting every page is not an out-of-range request — every page asked for exists — and one `errors.<code>` lookup cannot carry two sentences, which is the exclusion `toolError.ts` already records for `ocr-malformed-request`. Split rather than excluded, so both halves translate. **And** `pdf-too-few-files` / `pdf-invalid-range` carry their runtime values in the structured `context` field rather than baked into the message prose — this is what makes them eligible for `TRANSLATABLE_CODES` under 8.6's criterion (AC38), and it is the option 8.7 did not have for its wrapped-library errors.

15. **Given** the dependency, **when** the story completes, **then** both `Cargo.toml`s pin `lopdf = { version = "0.45", default-features = false }`, `Cargo.lock` resolves 0.45.0, and **`default-features = false` carries an in-file comment stating the new reason** — 0.45.0's defaults are `["chrono-clock", "rayon"]`, so the `time` 0.3.45 break that originally forced the flag can no longer occur, and the flag is kept because those features are unused here. A future reader must not delete it believing the workaround is stale, nor keep it believing a fixed break is live.

### Group B — Command layer (`src-tauri/src/commands/pdf.rs`, `src-tauri/src/lib.rs`)

16. **Given** AD-3's `<tool>_<verb>` rule and the fact that no tool called `bucket` exists, **when** the rename lands, **then** every PDF command is `pdf_*` — `pdf_merge`, `pdf_extract_pages`, `pdf_extract_text` — registered under those names in **both** `lib.rs:21`'s `use` line and its `generate_handler!` list, with **no** `bucket_*` alias left behind.

17. **Given** the new verbs, **when** they cross IPC, **then** each is its own `#[tauri::command] pub async fn` on `spawn_blocking` (AD-4) returning `Result<T, ToolError>` — `pdf_open` (path → page count + classification), `pdf_page_text` (path + page range → per-page text), `pdf_delete_pages`, `pdf_rotate_pages`, `pdf_reorder_pages` — and every command that produces a file takes an `output_path` and writes server-side via `fs_helper::write_file_bytes`, **never** returning bytes across the JSON IPC bridge (AD-15).

    **Amended 2026-09-11 — two additions the Group H rewrite forces, caught by the file-surface sweep rather than at implementation time:** (a) a **sixth** command, **`pdf_render_pages`** (path + page range + bounded width → encoded PNG per page), because AC45 requires previews to cross IPC and this enumeration named no command to carry them; and (b) `pdf_open`'s response **also carries the renderer-availability flag** (`render::is_available()`), rather than a seventh command — the view needs it to choose between thumbnail rows and AC46's text-only rows, and folding it into the open response avoids a second round trip for a value that cannot change during a session. Both are `pdf_*` per AC16 and `spawn_blocking` per AD-4 like the rest.

    **Amended 2026-09-13 at the Group A code review — a command that shipped unauthorised:** a **seventh** command, **`pdf_open_dropped(paths) -> Vec<PdfDroppedDocument>`**, is the `pdf` entry's AD-14 drop handler — the one command in this tool that takes **`paths`** rather than `path`, because it is what AC34's `multiple: true` branch invokes. It opens every dropped file in one round trip (count + classification each, path echoed back so the view pairs results to files without relying on array order). **A file that will not open fails the whole drop**: queueing the four that worked out of five would let a merge silently omit a file the user believed included (NFR4), while refusing is recoverable and names the problem. It is `pdf_*` (AC16), `spawn_blocking` (AD-4), and `check_file_size` covers it (AC19). Recorded here because the review found it in the code and in the slice-5 Change Log but in no AC — the same "authorised, not absorbed" rule AC52 applied to `pdf_begin_edit` / `pdf_save_copy`.

18. **Given** `bucket-input-too-large` and `bucket-internal` are raised by **both** `commands/pdf.rs` and `commands/image.rs`, **when** the rename lands, **then** `commands/pdf.rs` raises **new** `pdf-input-too-large` and `pdf-internal` codes at its own call sites, and the `bucket-*` pair is **left untouched and still live for the Images tool**. This is duplication, not migration — 8.7's own precedent — and **Story 8.9 owns retiring the pair**. `commands/image.rs` is not edited by this story.

19. **Given** `check_file_size()`, **when** an oversize file is passed to any command, **then** it is rejected **without reading the file**, and the existing per-command tests proving that for merge and extract-text are extended to cover every new command — the guard is worthless if a new verb forgets to call it.

    **Amended 2026-09-13 at the Group A code review — one deliberate exemption, asserted rather than assumed:** **`pdf_save_copy` does not call `check_file_size`.** The cap bounds what the *parser* is asked to decode, and `pdf_save_copy` never parses — it byte-copies the app's own working copy to the user's chosen path. Applying the *input* cap there re-checked a file the app itself produced, and a `lopdf` re-save can be larger than the original (object streams are written back as individual objects), so an original just under 100 MB became a document the user had edited, could see in the grid, and could not save. The exemption has its own test (`pdf_save_copy_is_exempt_from_the_input_size_cap`) so it stays a decision. The three page edits remain capped: they parse. The review also found the "every command" test covering 8 of 12; `pdf_open_dropped`, `pdf_render_pages` and `pdf_begin_edit` were added to it.

### Group C — The view (`src/tools/pdf/PdfView.vue` and its island)

20. **Given** the tool is opened with no document, **when** it renders, **then** it shows **one** resting surface — a dashed drop target (the HashView/OcrView drop language, used literally) carrying the drop label, an `Open PDF…` `AppButton` (*amended 2026-09-13 at the Group B code review: the AC said `Choose PDF…`; the shipped, render-reviewed label is `Open PDF…`, which says what happens rather than what you do — the AC follows the label, per 8.7's lesson 3*), and a sentence stating that several PDFs can be dropped to merge them. There are **no** longer three independent file pickers. The target shows the same drag-over state (solid signature border, tinted fill, "Drop to open") `OcrView` and `HashView` show.

21. **Given** a document is opened, **when** the surface renders, **then** it shows the file's **basename**, its **page count**, and a list of its pages — each row carrying **a rendered thumbnail of that page** *and* that page's first line of text. **Amended 2026-09-10:** this AC previously specified a text-only list and stated that thumbnails were out of scope. The developer rejected that — thumbnails serve **recognition** (*"the table page"*, *"the signature page"*), which a text label cannot, and the text list is sparse because heading-bearing pages are a minority. Page rendering is now in scope (AC43–AC47). The text label is **kept** alongside the thumbnail: a heading you can read beats a picture of one, and it is what the row degrades to when rendering is unavailable (AC46). **Amended 2026-09-11:** unchanged in substance — the rows still carry thumbnails — but rendering now comes from the OS on macOS and Windows rather than a bundled rasterizer, so **on a platform with no renderer (Linux) every row is the text label alone.** That is the AC46 path, not a separate design.

22. **Given** the page list, **when** it is driven from the keyboard alone, **then** every selection operation is reachable — arrow keys move row focus, `Space` toggles the focused row, `Shift`+click and `Shift`+arrow extend a range, `⌘A` selects every page when focus is inside the list — and the selected count is exposed as an announced status. **NFR5 admits no exceptions**; a selection model that needs a mouse fails this AC outright.

    **Amended 2026-09-13 at the Group B code review — the keys were written for a list and AC54 made it a grid:** `ArrowUp`/`ArrowDown` move by one *visual row* (the column count is read from the grid's own layout), `ArrowLeft`/`ArrowRight` by one cell, `Home`/`End` to the first and last page; `Shift` extends with any of them. In the list model `ArrowDown` moved one cell to the *right* of a seven-column grid.

23. **Given** a non-empty selection, **when** the verb bar renders, **then** it offers exactly **Extract to new PDF**, **Rotate**, **Move up**, **Move down** and **Delete**, each acting on the selection (**amended 2026-09-11**: the five verbs are unchanged, but AC52 settles what three of them DO — rotate, move and delete edit the document in place and prompt for nothing; only Extract to new PDF produces a new file and keeps its dialog); **Delete uses the Default (black) treatment, not destructive red** — `DESIGN.md:149` rules that removing pages before saving is low-stakes and reversible, and that ruling is not re-derived here. With an empty selection the bar shows the document-scoped actions instead (**Read text**, **Merge with…**).

24. **Given** merge takes *many* documents while every other verb takes *one*, **when** several PDFs are dropped or chosen, **then** the view enters a **merge queue** state — a distinct, mutually-exclusive state of the same view, **not** a tab and **not** a second surface — listing each document by basename with its page count, reorder and remove controls, and a single **`Merge PDFs`** button using the **`primary`** `AppButton` variant. `DESIGN.md:183` names *"Merge PDFs"* as the worked example of that variant and permits **one primary per screen at most**; this is that one.

25. **Given** any file path shown in the UI, **when** it renders, **then** only the **basename** is displayed, with the full path available via `title`. **No absolute path reaches the screen.** `CLAUDE.md` treats `/Users/<name>/…` as personally-identifying and this repo enforces that on its own commits; a public-portfolio app must not print it in a screenshot.

26. **Given** the view's heading structure, **when** it renders, **then** heading ranks descend without skipping. Today the view goes `<h1>` → `<h3>` with no `<h2>` — introduced when Story 8.7 promoted the section's `<h2>` to this routed view's `<h1>` and left the inner headings untouched. NFR5.

27. **Given** the view is 100% pre-Epic-7, **when** the redesign lands, **then** it contains **no hardcoded colour, radius, font-family or `em`-based spacing** — every value resolves through `tokens.css` — and **no plain `<button>` where an `AppButton` or the 24px ghost icon-button anatomy applies.**

28. **Given** any copy affordance, **when** a copy succeeds, **then** it confirms via `useCopyFeedback` (hoisted to `src/shell/` by Story 8.7 — an import, not an infrastructure decision), and marks the key **only after** the clipboard write resolves.

29. **Given** an operation of unbounded duration, **when** it is in flight, **then** the view renders a real in-flight state **and** announces start and completion through a live region — `EXPERIENCE.md:70` states this as the general rule, not an OCR-only exception. **No determinate progress bar**: neither `lopdf` nor the page-text pass reports a fraction, and a bar filling at an invented rate is the tool bluffing about its own internals (8.7's ruling, applied here).

30. **Given** an operation that writes a file, **when** it completes, **then** the view says so, naming the written file by **basename** (**amended 2026-09-11**: after AC52 this covers the two verbs that still produce a file — Extract to new PDF and Merge PDFs — plus *Save a copy…*; an in-place edit announces completion instead, since it writes no file the user chose) — today merge and extract-pages write a file and say nothing at all, and the user's only evidence is opening Finder (`deferred-work.md:154`, assigned to this story by name). **"Says so" means shown *and* announced** (*clarified 2026-09-13 at the Group B code review*): the first build put the sentence in the `sr-only` live region only, so a sighted user still saw nothing change — the exact gap this AC was written against. It now also renders visibly, and is cleared when the next operation starts.

31. **Given** an error, **when** it renders, **then** it appears with the operation that raised it and does not remove the way back in. The single shared `pdfError` ref is replaced: today an error raised by merge is silently cleared by an unrelated click in another flow.

32. **Given** AD-16's rule — *one runner per independent piece of state* — **when** the container changes, **then** runner scoping is **re-derived, not carried forward**, and the in-file comment justifying it is rewritten. The current comment reasons against `registry.getLatestWinsRunner("bucket")` and an in-flight OCR extraction, **neither of which exists**. The resolved shape: **two** local runners — one for the open document's read state (open, page text), one for write operations (extract/delete/rotate/reorder/merge) — because a page-text pass and a save must not supersede one another. AD-16's amendment also binds: a runner fences against a newer **request**, not newer **input**, so any task publishing derived state mid-flight re-checks its snapshot via `isLatest()`.

### Group D — Drag-and-drop (shell, AD-14 — named, not absorbed)

33. **Given** a tool may need more than one dropped file, **when** the registry entry declares it, **then** `drop` accepts an **additive** `multiple: true` flag, and **only** the `pdf` entry sets it. Tools that do not declare it receive exactly today's behaviour.

### Group H — Page rendering (OS-native backends) — added 2026-09-10, **rewritten 2026-09-11**

**Why this group was rewritten before a line of it was built.** The 2026-09-10 version specified `pdfium-render` 0.9.4 plus a bundled, checksum-pinned `libpdfium` binary from `bblanchon/pdfium-binaries`. Before fetching anything, the developer directed a **Step 0 pass — "does the OS already give us this?"** — which the 2026-09-10 amendment had skipped entirely, going straight from *"`lopdf` cannot rasterize"* to *"therefore add a rasterizer dependency."* The pass found that **two of the three target platforms ship a PDF renderer in the OS**, reachable through crates **already in the dependency tree via Tauri**. The dependency, the ~10 MB-per-platform binary, the checksum-pinned fetch, the CI fetch step and the `tauri.conf.json` bundling are therefore **all cut**. Decision record §1.5/§1.6 carry the superseded reasoning; this group carries what ships. **Second "rationale died, decision survived" instance in this story that the story caused itself** — previews survive, the rasterizer that was going to deliver them does not.

**Verified 2026-09-11 against the local macOS SDK, the vendored crate sources and Microsoft's generated bindings — not from recollection.** (The AD-7 baseline in AC47(c) was captured 2026-09-10, before the rewrite.)

| Platform | OS renderer | Reachable from Rust via | Status |
| --- | --- | --- | --- |
| macOS | Core Graphics (`CGPDFDocument`/`CGPDFPage`, the engine behind Preview.app) | `objc2-core-graphics` 0.3.2 — **already in the tree** | ✅ ships |

| Linux | **none — no OS-level PDF rendering API exists** | Poppler is GPL, MuPDF is AGPL — both licence-incompatible with this app | ❌ no-renderer path |

43. **Given** two of three platforms render PDF in the OS, **when** rendering is added, **then** it adds **no new crate to the dependency tree** — `objc2-core-graphics` (macOS) and `windows` (Windows) are already compiled here via Tauri, so both are declared as **platform-scoped** `[target.'cfg(target_os = "…")'.dependencies]` entries enabling **features only**. **No `pdfium-render`, no bundled native binary, no checksum-pinned fetch, no CI fetch step, no `tauri.conf.json` bundle entry.** The bundle grows by **0 MB**, which is the point: the superseded version roughly doubled it, and the decision record's own §1.5 called that *"a product decision about 'small, offline, yours', not a technical one."* The platform-scoped declarations carry an in-file comment recording that Linux has no OS API and that its two candidate libraries are copyleft — so a future reader does not read the gap as an oversight.

44. **Given** AD-2 forbids `umbra-core` touching the filesystem and **AD-11 forbids it any `cfg(target_os)` branch at all**, **when** rendering is implemented, **then** it lives **entirely in `src-tauri/src/render/`** and **`crates/umbra-core/src/pdf.rs` gains no rasterize function**, keeping every structural operation. **The `cfg` switch appears in exactly one file of runtime source** — `render/mod.rs` — and no other shipped code branches on operating system: `commands/pdf.rs`, the view and the core all call one platform-blind interface. (*Scoped 2026-09-13 at the Group A code review:* `src-tauri/build.rs` has carried `cfg(target_os = "windows")` since Story 4.1 for the Windows resource embed. It is a build script, not shipped code, and this story adds no second switch anywhere — but the earlier absolute wording, repeated in `lib.rs` and `render/mod.rs`, was false as written and has been corrected in all three places.) Structure code never reaches for a renderer and rendering never reaches for `lopdf`. No renderer work runs on the launch path (AD-4; NFR2's 2 s cold launch).

45. **Given** a 400-page document, **when** previews are produced, **then** they are rendered **per visible range**, not all at once, at a bounded thumbnail width, and the result crosses IPC as an **encoded PNG** rather than raw RGBA. (*Made literal 2026-09-13 at the Group B code review:* an `IntersectionObserver` over the unloaded cells requests whatever is on screen, in batches of at most 24, tracked per page; batches are fenced by document identity, never by a latest-wins runner — the first build had one sentinel below the *last* row of the whole document, so pages 25–399 stayed blank until the very bottom, and every batch could cancel the one before it.) **AD-15's ceiling binds:** a thumbnail is small, but four hundred of them are not — the volume is the constraint, and the fetch policy is the same bounded, streaming one AC9/AC29 already establish for page text.

46. **Given** rendering can be unavailable, **when** it is, **then** the tool **degrades to the text-derived page list and says why** — never a crash, never blank frames, never a silently empty list (NFR4). **This is the *no-renderer* path, not the *Linux* path**, and the distinction is normative: it is reached both by a platform with no backend (Linux, always) *and* by a page that fails to render on a platform that has one (macOS/Windows, occasionally). One code path, one set of tests, exercised on **every** platform in CI — not dead code that only a Linux user would ever see. AC21's text label is what it degrades to, which is why that label is kept rather than replaced by the thumbnail.

    **Clarified 2026-09-13 at the Group A code review — where "says why" applies:** the reason is surfaced **once, at the build level** — `pdf_open`'s `canRenderPreviews: false` is what the view reads to explain that this build has no renderer. For the **per-page** case on a platform that has one, `pdf_render_pages` omits the failed page from its result and the row falls back to its text label **silently**: a per-row reason has no home in the grid, and a page that will not draw is not something the user can act on. The backends still compose a reason string (it is what `render_page` returns), and the command discards it deliberately — recorded here so the discard reads as a decision, not an oversight.

### Group J — Motion — added 2026-09-11 from a render review

**Raised by the developer at slice 1's render review, and it was a genuine gap rather than a later slice:** a repo-wide check found **no AC in this set mentioning motion**, and **neither `DESIGN.md` nor `EXPERIENCE.md` has a motion section at all**. The convention nonetheless exists in code — seven files (`AppPopover`, `Base64View`, `HashView`, `JsonTree`, `OcrView`, `UuidView`, and now this view) carry `prefers-reduced-motion` blocks, and durations cluster in two bands: **120–140 ms** for micro-feedback and **180–220 ms** for navigation pulses, with `OcrView.vue:969`'s `filter 320ms` standing alone as a **state-change** duration.

50. **Given** reordering a merge row changes its position between one frame and the next — so nothing indicates which file moved or where it went, and merge queues routinely hold near-identical names (`invoice-2026-Q1.pdf` / `invoice-2026-Q2.pdf`) — **when** a row is moved, **then** it **visibly travels** to its new position via a `<TransitionGroup>` FLIP, at **`transform 310ms cubic-bezier(0.32, 0.72, 0, 1)`**, and the motion is **disabled under `prefers-reduced-motion: reduce`** per the seven-file convention above.

    - **Neither value is invented.** The curve is the house curve for a sliding element, already driving the Base64 direction-switch thumb (`Base64View.vue:992`); its start tangent is ≈2.25 and its end tangent is horizontal, i.e. **it is already an ease-out** — the `ease-out` keyword is deliberately **not** additionally applied, being an alternative value of the same property that would replace the curve with a weaker one. The duration is the developer's render-review call, chosen above the micro-feedback band and beside `OcrView.vue:969`'s 320 ms, on the reading that a row changing place is a **state change**, not a click acknowledgement.
    - **Slide only.** Three richer treatments were built and compared live (added emphasis tint; lift-and-settle; and the no-motion baseline) and the developer chose plain slide. Recorded so the alternatives are not re-proposed as novel.
    - **This AC has a data-shape precondition, and it is the whole reason the animation was impossible before**: `<TransitionGroup>` runs FLIP only where `:key` identifies a row as *the same row relocated*. The shipped key was `path + index`, which **changes when the row moves**, so Vue destroyed and recreated the row and there was nothing left to animate. The merge list therefore holds **`{ id, path }`** with a monotonic id. `path` alone will not serve — the same file may legitimately be added twice (a cover sheet merged onto both halves of a document), and duplicate keys break reconciliation in their own way. **The IPC contract is unchanged**: the command layer still receives an ordered list of paths.
    - **Regression-guarded, and the guard was verified to fail without the fix** rather than assumed: the spec asserts the moved row is the **same DOM node** (`Object.is`) after a move, which no other assertion in the file detects and which jsdom — running no transitions at all — would otherwise hide completely.

51. **Given** AC50 settles a motion question the design system never wrote down, **when** the story completes, **then** the gap is **recorded as owed to `DESIGN.md`, not silently absorbed**, and the decision is stated as binding on **both** reorder surfaces this story ships — the merge queue (AC24) **and** the page list, where AC23's reorder verb faces the identical question at **four hundred rows rather than three**. A per-row FLIP that is free at n=3 is not free at n=400, so AC45's per-visible-range policy governs there and the motion applies to the rendered window, not the whole document. **Implemented on the page grid 2026-09-13 at the Group B code review (developer's call, option b of two):** edits are applied to the grid *locally* with stable row identities — a row keeps its id, text and thumbnail and only its position is renumbered — so the grid is a `TransitionGroup` that animates a move with the same `reorder` motion the queue uses, and a move no longer blanks twenty-four thumbnails to re-fetch them. `DESIGN.md` is otherwise locked, so this is a follow-up entry rather than an edit in this story — the same treatment Story 8.4's `--color-accent-success` addition received.

### Group K — The editing model — added 2026-09-11 from the slice-4 render review

**The AC set specified a surface but never specified what a verb DOES to the document, and slice 4 filled that silence with the wrong answer.** Every page verb prompted for a save location and wrote a new file — the old three-flow export model wearing the new surface's clothes. The developer rejected it on sight: *"if I select a page and click rotate, it prompts me to save the file instead of just rotating the page."* Worse, the page list never reloaded, so the tool looked broken even when the operation had succeeded. Recorded as an **AC gap, not a bug**: no AC said edits apply in place, so nothing was violated — which is exactly why it needs saying now.

52. **Given** the tool's premise is *open a document and act on it*, **when** a page verb runs, **then** it **applies to the document in place and prompts for nothing**, and the page list reloads so the change is visible immediately.

    **Amended 2026-09-13 at the Group B code review:** (a) "reloads" means the grid is updated **locally** (the same transformation the command applied to the file) and then *verified* by re-reading the working copy's page count — if the two ever disagree the grid is rebuilt from the file, because a wrong grid is worse than a blank one; (b) the selection **follows the pages it named** across a rotate or a move (so rotating or moving again acts on the same block) and is **cleared** only by a delete, whose pages no longer exist; (c) **unsaved edits are never discarded silently** — closing, a single-file drop, a hand-off and opening another file all ask first when the working copy is dirty (`ask()` from the dialog plugin; the `unsavedChanges` string that existed in both locales without a caller now has one); (d) "Merge with…" always **queues the open document first, as its working copy**, so its edits are what get merged, shown under the name the user opened; (e) an edit started on document A never touches document B if A was closed while it was in flight; (f) "Move up"/"Move down" are boundary-disabled like the queue's arrows.

    - **The original file is never written to.** A **working copy** is taken lazily on the first edit (`pdf_begin_edit`, sweeping stale copies on the way *in* — a crash never runs a close handler, so cleanup that only happens on exit eventually stops happening), every later edit reads and writes that copy, and **`pdf_save_copy` is the one place the edited document leaves the app**. It is *"Save a copy…"*, not *"Save"*, because the user opened a file they never asked us to overwrite — and this is what makes `DESIGN.md:149`'s ruling that deleting pages is *"trivially reversible"* literally true rather than aspirational.
    - **The split that decides whether a verb prompts:** a verb that **edits this document** (rotate, delete, move up/down) applies in place; a verb that **produces a new file** (Extract to new PDF, Merge PDFs) genuinely needs a destination and keeps its dialog. AC23's five verbs are unchanged; what changed is what three of them do.
    - **The selection is cleared after an edit.** Deleting shifts every later page down and reordering moves them outright, so a selection carried across an edit points at pages the user did not choose — silently, and only after the first affected page.
    - **Two commands beyond AC17's enumeration**, authorised here rather than absorbed: `pdf_begin_edit(path) -> String` and `pdf_save_copy(path, output_path)`. Both are `pdf_*` (AC16), both `spawn_blocking` (AD-4), and `check_file_size` covers both (AC19).
    - **Reading and writing the same path is safe and is asserted**, not assumed: the command reads the file completely before writing, and `fs_helper::write_file_bytes` writes a temp then renames, so a failure partway through cannot truncate the working copy.

53. **Given** a real filename is often long (`CourrierCaisse__0038_MTB23_SMB188_85073d94-…`), **when** a merge-queue row renders at any window width, **then** it **stays on one line** and the name ellipsises. The row inherited `flex-wrap: wrap` from the pre-Epic-7 view, whose comment worried about French labels crowding a narrow window — but wrapping "solves" that by breaking the row's own controls onto a second line, which reads as a second queue entry and makes the order harder to follow. The name takes `flex: 1 1 0`, **not `1 1 auto`**: with an `auto` basis it claims its full intrinsic width first and only then shrinks, which is what lets a long name shove the controls out of the row before the ellipsis ever engages.

### Group L — The page grid — added 2026-09-11 from the second render review

**Raised by the developer against the shipped slice-4 surface:** *"the previews are way too small."* They proposed a print-dialog layout — one large preview with the actions in a right rail — and asked whether to replace the list, keep it, or ship both. A four-layout comparison was built and driven against one errand (*select the signature page, the table page, and page 21*); the developer chose the grid with a size control.

**Why the print-dialog layout was not taken, recorded so it is not re-proposed as novel:** a print dialog exists to **review one document before committing**, and this tool exists to **survey pages and select some**. In a one-big-preview layout, reaching three specific pages means paging through the document to each of them — worse than the list, not better. The instinct behind it is real, but it answers *"is this the page I think it is?"* — **inspection**, not selection. That is a grid-plus-inspector shape (option C in the comparison), deliberately **deferred**: build the grid, use it, and add the inspector only if the grid alone leaves the question open.

**Two views were considered and rejected.** This redesign's whole premise was *one surface instead of three*; a view switcher walks that back and costs two code paths and two test suites permanently. A **size control** is a different thing — one view with a density preference, which is what Preview and Acrobat both ship.

54. **Given** a vertical list spends ~48px of a 1100px-wide window on the one thing that helps a user recognise a page, **when** the document surface renders, **then** pages lay out as a **responsive grid** whose track width follows a **three-step size control** (S / M / L), and that choice **persists** via the settings store under **`pdf.previewSize`** (AD-10), exactly as `uuid.format*` and `hash.case` do — a density re-picked every session is a chore, not a preference.

    - **Three named steps, not a slider.** A slider persists a pixel value nobody chose deliberately, and the grid has only three densities worth having.
    - **The accessible name is supplied explicitly.** The cell shows a bare page number — repeating "Page" twenty-four times is noise once previews carry the meaning — so each cell carries `aria-label="Page N — <first line>"`. Without it a screen reader announces *"1, Heading 1"*, which is **worse than the list this replaced**; and at size S, where the text label is visually hidden, it is the only place that text survives at all.
    - **Selection stays a two-signal state** (a ring on the preview *and* a tinted, bolded page number), per the same rule OcrView's confidence markers follow, so it survives a greyscale screenshot.
    - **`SettingsView.vue` is NOT edited**, and this was verified rather than assumed: `persistedEntries` reads the store's own contents (`settings.entries()`) rather than a hardcoded list, so `pdf.previewSize` appears there with a per-key reset automatically (PRD INV-3). What *is* wired by hand — and what a new key silently misses — is the `resetKey` case and the `clearAll` reset, both covered by a test.
    - **AC21 is amended by this AC**, not contradicted: rows become cells, the thumbnail grows, and the text label moves **under** the preview rather than beside it. It is still kept, and still the fallback when rendering is unavailable (AC46).

55. **Given** the grid sits in a window with real height to claim, and previews are raster images on a display whose pixels may not be CSS pixels, **when** the document surface renders, **then** (a) the grid **takes the height the window actually has** rather than a fixed slice of it, and (b) previews are requested in **device pixels**, so they are sharp at every size step.

    - **(a) The height.** The grid carried `max-height: 520px`, which on a laptop spent roughly half the window on nothing. `.main-pane` is `flex: 1` inside a `height: 100vh` flex shell, so there is genuine height to take — the same claim `OcrView.vue` already makes for its image. `min-height: 0` on each flex ancestor is the part that matters: without it the grid grows to fit every page and pushes the window into a second scrollbar instead of scrolling inside itself. `align-content: start` stops a single row of cells stretching to fill the height it just claimed. **A tall display is not a reason to cap this** — more height means more rows, not bigger cells, because the track width is set by the size step.
    - **(b) The blur, and why it looked size-dependent.** Previews were rendered at a fixed 160px and displayed in cells of 104 / 148 / 208 CSS px — but a CSS pixel is not a device pixel, and on a 2× Retina display the largest cell is **416 real pixels**. The browser was upscaling 160 → 416, a factor of 2.6. The smallest step hid it (upscale ≈ 1.3) and the largest made it unreadable, which is exactly the reported symptom. The view now asks for `cellWidth × devicePixelRatio`, read **live** rather than captured once, since moving the window between a Retina display and an external 1× monitor changes it.
    - **`MAX_THUMBNAIL_WIDTH` raised 320 → 640**, because the old ceiling silently clamped the largest cell's honest request (416) back down to 320 — the clamp was itself part of the blur. 640 covers the largest cell at a 3× ratio (208 × 3 = 624) with nothing to spare: it is a ceiling, not a target, and AC45's bound still holds.
    - **Changing the size step re-renders the previews already on screen.** Without it the control meant to fix the blur reintroduces it — S → L would keep the small images and stretch them. Only previews re-fetch; page text is resolution-independent. Chunked, because "already loaded" can be two hundred pages by the time someone changes their mind about density, and a stale batch is discarded wholesale if the size, the document or the request moved under it.
    - **Regression-guarded, and the guards were verified to fail without the fix:** jsdom reports `devicePixelRatio` 1, so the tests set it explicitly — without that they would pass against the very bug they exist to catch.

### Known gaps in the shipped PDF path — each needs an explicit call in the decision record

1. **No drag-and-drop, and `EXPERIENCE.md:82` says otherwise.** See AC5 for the full framing. **Unlike 8.7's gap #1, this is not an unimplemented spec — it is a recorded decision whose main reason 8.7 invalidated.** 6.1 declined the AD-14 dispatcher deliberately and wrote down three reasons; the registry split killed one of them, tier 1's redirect undermined the fallback, and two still stand. Treat it as a re-decision with a documented prior, not as a defect.
2. **No success confirmation after any completed operation** (`deferred-work.md:154`, open since Story 6.2's code review). Merge and extract-pages write a file and then say **nothing at all** — no "Saved", no path echo, no state change. **Post-commit security review, 2026-09-12 — the three findings deliberately left open, with reasoning.** All three are one issue wearing three labels: `insecure-temp-file`, `symlink-follow-write` / `symlink-follow-read`, and `information-disclosure`, all pointing at the working-copy directory.

**They are real, and only on Linux.** `std::env::temp_dir()` is per-user and mode 700 on macOS (`$TMPDIR` → `/var/folders/…/T/`) and on Windows (`%TEMP%` in the user profile), so neither is exposed. On Linux it is `/tmp`, world-writable: another local user can pre-create `umbra-pdf-edits` as a directory they own or as a symlink, at which point `create_dir_all` succeeds silently, the user's PDF is written somewhere the attacker chose, and is read back from there. Working copies also persist with the default umask (0644), so a local user can read them.

**Why they are not fixed in this story.** The attacker must already have a local account on the machine, which is a materially different threat model from anything else this app defends against, and the fix is not a one-liner: it needs `cfg(unix)` handling — create with mode 0700, reject a pre-existing entry that is a symlink or not owned by us — in `commands/pdf.rs`. This story just shipped an architecture claim that `render/mod.rs` holds **the codebase's only `cfg(target_os)` switch**; `cfg(unix)` is not the same predicate, but it is close enough that adding one here without a ruling would blur a boundary this story spent Group H establishing.

**One honest trade to note in review:** the age-based sweep *lengthens* the exposure window from "until the next document is opened" to 24 hours. It is not strictly worse — a user who never opened a second PDF kept the old copy forever — but it is different, and it is a deliberate choice of another session's unsaved work over a shorter exposure.
