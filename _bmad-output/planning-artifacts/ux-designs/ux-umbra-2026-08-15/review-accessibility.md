# Accessibility Review — Umbra EXPERIENCE.md

## Overall verdict

The Accessibility Floor section states an unambiguous commitment (full WCAG 2.1 AA, every flow keyboard-drivable with no exceptions, visible focus on every tab stop, every control screen-reader-labeled) — but the rest of the document does not actually deliver it. The floor reads as aspirational text bolted onto the end of the spine rather than a constraint the Key Flows, Component Patterns, and State Patterns were checked against: the single busiest interactive element (Card) has no stated keyboard path, both new bespoke components (Update-signal, Clipboard-suggestion) are describable only in visual/pointer terms with zero accessible-name or announcement story, the flagship NFR5 demo flow itself hedges its own keyboard-only claim mid-sentence, and the IA section's icon-collapsed sidebar is never reconciled with the "every control has a screen-reader label" line that follows it two sections later. If a developer implemented this document literally, several flows would ship keyboard-inaccessible or screen-reader-invisible on day one.

## Findings

- **critical** Card — the sole entry point into every tool from grid-home, used in Flow 1 step 4 and implicitly every session-start — is specified only as "Click anywhere opens the tool," with no stated keyboard-operable path (Tab focus, Enter/Space activation) and no ARIA role/label expectation (Component Patterns, Card row). Implemented literally, this is a click-handler on a non-focusable element — the most-traveled surface in the app would be unreachable without a mouse, directly contradicting "every flow is keyboard-drivable, no exceptions." *Fix:* add a line stating Card is focusable in DOM/tab order, activates on Enter/Space as well as click, and exposes an accessible name equal to the tool's name (not just its visual title text).

- **critical** Flow 2 (the 5-minute demo), step 5 depends on drag-and-drop with no keyboard-accessible alternative *stated in the flow itself*, and step 6's climax narration concedes the gap rather than closing it: "without a single mouse click needed for **the keyboard portion**" (line ~106) implicitly carves step 5 out of the keyboard-only claim. This directly contradicts the Accessibility Floor's "every flow is keyboard-drivable, no exceptions," which is grounded explicitly in this exact demo flow via NFR5. Interaction Primitives does mention a file-picker as the base method with drag-and-drop as "an alternative to" it — but that fact is never connected back into Flow 2's steps, so a developer reading the flow in isolation has no reason to build (or preserve) a keyboard path for the drop-zone step, and the flow's own climax line reads as tacit acknowledgment that the mouse-free claim doesn't fully hold. *Fix:* rewrite step 5 to name the keyboard-operable file-picker (e.g. "activates the drop zone's file-picker button, or drags a screenshot onto it") as the canonical path, and remove "the keyboard portion" hedge from step 6 so the climax states the sequence is fully keyboard-drivable, not partially.

- **critical** Focus management around `⌘K` is never addressed anywhere in the document, despite the prompt's own review criteria naming it directly and every Key Flow depending on it (Flow 1 step 4 origin path, Flow 2 steps 2–4, and Interaction Primitives' "⌘K invocation" bullet). Nothing states whether focus moves into the palette's input on open, or where focus returns when the palette closes (Enter-select, Esc-dismiss, or click-away). For a component invoked from every surface in the app and central to the mouse-free demo, this is a foundational keyboard-accessibility gap, not a peripheral one. *Fix:* add a line to Interaction Primitives' ⌘K bullet: focus moves to the palette's search input on open; on close (select, Esc, or click-away) focus returns to whatever element held it before invocation.

- **critical** Update-signal — one of the two new bespoke components this review was asked to check hardest — has no stated keyboard-operable path and no stated accessible name or role (Component Patterns, Update-signal row). It's described purely as a visual mark ("reuses DESIGN.md's Notification Dot... passive until clicked") and DESIGN.md's underlying Notification Dot is explicitly "No text — a pure mark, so no contrast pairing applies," meaning nothing in either document currently commits this component to having *any* text-equivalent for assistive tech. A screen-reader user has no way to discover an update exists, let alone act on it — this is the clearest concrete violation of "every control has a screen-reader label and role" in the whole spine. *Fix:* add that the update-signal is a focusable, labeled control at every escalation level (e.g. accessible name "Update available" / "Security update available"), reachable by keyboard from wherever its chrome anchor lands.

- **critical** Update-signal escalation (Flow 3) is entirely non-visual-cue-free for anyone not looking at the screen. Steps 1, 2, and 5 describe a dot "appearing," "escalating in visual weight," and "jumping straight to a distinct, more-urgent visual state" — none of which has a stated non-visual equivalent. A screen-reader user would never learn a release shipped, that it's been escalating for days, or that a security-flagged release just jumped priority, unless they happen to tab onto the (currently unlabeled — see previous finding) dot at the right moment. This is exactly the "invisible to anyone not looking at the screen" failure mode named in the review brief. *Fix:* state that each escalation level updates the signal's accessible name/state (e.g. "Update available" → "Update available — 3 days" → "Security update available"), so a screen-reader user encountering the control at any point gets the current urgency, not just a shape/color that changed silently.

- **high** Clipboard-suggestion surface — the second bespoke component flagged for hardest scrutiny — appears and disappears in the sidebar based on clipboard content with no stated announcement mechanism (Flow 4 step 3; Component Patterns, Clipboard-suggestion row). A sighted user notices a new highlighted row; a screen-reader user whose focus is elsewhere (e.g. mid-task in a tool pane, per Flow 4's own premise of "mid-task") has no way to learn the entry appeared at all, since sidebar content changing outside the user's focus is invisible to AT unless explicitly announced. This is the same category of gap as the update-signal, on the component the prompt specifically called out as easy to ship "mouse-first and accidentally... screen-reader-invisible." *Fix:* state that the clipboard-suggestion entry's appearance is announced via a polite live-region cue (e.g. "JWT Inspector suggested from clipboard") rather than relying on visual placement alone, and that its keyboard entry point (Tab reachability, accessible name) is explicit rather than only inferable from the Nav item pattern.

- **high** Information Architecture's sidebar row ("Collapses to icons; state persists via `settings` store") is never reconciled with the Accessibility Floor's "every control has a screen-reader label and role" two sections later — the two claims sit in different parts of the document with no cross-reference, and icon-only collapsed nav is one of the most common real-world screen-reader traps (a `<button>` with only an `<svg>` inside and no accessible name). As written, an implementer could satisfy the IA section literally (icons only, no visible text) while violating the Accessibility Floor, and nothing in the document flags the tension. *Fix:* add a clause to either the IA sidebar row or the Accessibility Floor explicitly stating that icon-collapsed nav items retain their full accessible name (visually-hidden label or equivalent) regardless of collapse state — the floor's blanket claim needs to survive contact with this specific, named layout detail.

- **high** Nav item (active state) specifies only a visual treatment (background tint, hover affordance) with no stated ARIA expectation for conveying "this is the current view" to assistive tech (Component Patterns, Nav item row). "Exactly one item active at a time" is a good behavioral invariant but it's stated purely as a visual fact; without an accessible-technology equivalent (e.g. a current-page/current-tool state exposed on the active element), a screen-reader user tabbing the sidebar has no way to tell which tool is currently open — information every sighted user gets for free from the orange tint. *Fix:* add a line stating the active nav item exposes its current-state to assistive tech (e.g. an aria-current-style expectation), not just a background-color change.

- **medium** Loading state (OCR) commits to "an in-tool progress indicator; never a blank pane" but never states whether that indicator's appearance and completion are announced to assistive tech (State Patterns, Loading row). OCR is called out in the same row as "potentially slow" — exactly the case where a screen-reader user needs to know work started and when it's done, not just that a sighted user would see a spinner. As written, the *visual* commitment (never a blank pane) has no accessible-technology equivalent commitment alongside it, which is precisely the "state pattern satisfiable only via a visual-only cue" the review brief asks to catch. *Fix:* add that loading and completion are exposed to assistive tech (e.g. an announced status when extraction starts and finishes), not just visually indicated.

- **medium** Error state's "precise inline error, always in-tool" (State Patterns, Error row) describes rich, well-thought-out *content* (names the failing segment) but never states whether that content is proactively announced to a screen-reader user or only discoverable by tabbing to it after the fact. Given error quality is called out repeatedly in this document as a system-wide tone commitment (FR12/18/21/26, NFR4), the same weight isn't given to whether a screen-reader user is informed the error appeared at all. *Fix:* state that inline errors are announced when they appear (e.g. a status/alert-equivalent behavior), not just present in the DOM for a user who happens to navigate to them.

- **medium** "No matches" ⌘K state (State Patterns row) is described as text ("Palette stays open with a plain 'No matches' state") but doesn't address whether that update is announced as the user types — a live, incremental-search results field needs some equivalent of "results changed, now zero" for a screen-reader user, otherwise they keep typing into what appears (to them) to be a silent void. *Fix:* state that the result count/no-matches text updates are exposed to assistive tech as the query changes, not just visually present once typing stops.

- **medium** Flow 1 step 3's "brief guided highlight" walking the sidebar and grid has no stated keyboard operability, focus handling, or screen-reader narration of its own steps — only its *dismissal* is partially addressed ("Esc or click-away" in the Failure note). Guided-tour/spotlight overlays are a well-known accessibility failure mode (focus not moved into the tour, underlying page still tabbable behind an overlay, step content never announced). The document handles the escape hatch but not the tour's own operability. *Fix:* state that the tour moves focus to each highlighted step's content, is dismissible and advanceable by keyboard throughout (not just at the end), and its step text is exposed to assistive tech as it's presented — or, alternatively, explicitly scope it as decorative/non-blocking and confirm grid-home behind it is independently keyboard-reachable throughout.

- **low** OCR empty/failed state (Bucket) — "explicit state distinguishing 'no text found' from a blank/successful-looking result" — has good content but inherits the same unaddressed announcement gap as the Loading and Error rows above (State Patterns row). Grouped here as a smaller, same-shape instance of the pattern rather than a separate root cause. *Fix:* covered by the same fix as the Loading/Error findings — extend whatever announcement mechanism is added there to this state as well.

- **low** Clipboard-suggestion surface's keyboard entry point is only inferable, not stated: because the component is described as "a highlighted/pinned entry" at the top of the sidebar, a reader might assume it inherits the Nav item component's (also under-specified — see above) click/tab behavior, but the document never says so explicitly (Component Patterns, Clipboard-suggestion row). *Fix:* state explicitly that the clipboard-suggestion entry is keyboard-reachable in the same tab sequence as other sidebar/nav items, rather than leaving that as an assumption a developer has to infer.
